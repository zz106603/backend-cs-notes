# 트랜잭셔널 아웃박스 패턴 (Transactional Outbox Pattern)

분산 시스템에서 **데이터베이스 업데이트와 메시지 발행을 하나의 원자적 트랜잭션으로 묶어** 데이터 정합성을 보장하는 디자인 패턴

---

## 1. 배경: 이중 쓰기 문제 (Dual Write Problem)

일반적인 서비스 로직에서 DB 저장과 외부 시스템(Kafka, RabbitMQ 등)으로의 이벤트 발행을 동시에 수행할 때 발생할 수 있는 문제

```java
@Transactional
public void createOrder(OrderRequest request) {
    // 1. DB에 주문 정보 저장 (성공)
    orderRepository.save(new Order(request));
    
    // 2. 외부 메시지 브로커로 이벤트 발행 (실패 가능성!)
    eventPublisher.publish(new OrderCreatedEvent(order.getId()));
}
```

*   **문제 시나리오 1**: DB 저장(`commit`)은 성공했으나, 네트워크 장애로 메시지 발행만 실패하는 경우 -> 외부 시스템은 주문 발생 사실을 모름 (데이터 불일치)
*   **문제 시나리오 2**: 메시지 발행은 성공했으나, DB 커밋 직전에 에러가 발생하여 롤백되는 경우 -> 주문은 취소됐는데 외부 시스템은 주문이 발생한 줄 알고 후속 작업(결제 등)을 진행함

---

## 2. 동작 원리

이 패턴의 핵심은 **이벤트를 외부 브로커로 직접 보내지 않고, 같은 DB 내부의 'Outbox' 테이블에 저장**하는 것

### 1) 이벤트 저장 (Local Transaction)
*   비즈니스 로직과 동일한 DB 트랜잭션 내에서 **아웃박스 테이블**에 이벤트 데이터를 함께 `INSERT` 함
*   DB 트랜잭션의 원자성 덕분에 비즈니스 데이터와 이벤트 로그는 **둘 다 저장되거나 둘 다 롤백**됨이 보장됨

### 2) 이벤트 발행 (Message Relay)
*   별도의 프로세스(Message Relay 또는 Publisher)가 아웃박스 테이블을 주기적으로 감시(Polling)함
*   아직 발행되지 않은 이벤트를 읽어 실제 메시지 브로커(Kafka 등)로 전송함
*   전송이 성공하면 아웃박스 테이블의 상태를 '발행 완료'로 변경하거나 삭제함

---

## 3. 실무 예시: "주문 생성 및 결제 요청"

### 1) DB 작업 (원자성 확보)
```java
@Transactional
public void order(OrderRequest request) {
    Order order = orderRepository.save(new Order(request));
    
    // 이벤트를 외부로 보내지 않고 DB에 담아둠
    outboxRepository.save(new OutboxEvent(
        "ORDER_CREATED", 
        objectMapper.writeValueAsString(new OrderCreatedEvent(order.getId()))
    ));
}
```

### 2) 메시지 발행 프로세스 (신뢰성 보장)
```java
@Scheduled(fixedDelay = 1000)
public void publishEvents() {
    // 아직 처리되지 않은 아웃박스 목록 조회
    List<OutboxEvent> events = outboxRepository.findByStatus("PENDING");
    
    for (OutboxEvent event : events) {
        try {
            // 외부 브로커(Kafka 등)로 전송
            kafkaTemplate.send(event.getTopic(), event.getPayload());
            
            // 성공 시 상태 업데이트
            event.markAsPublished();
            outboxRepository.save(event);
        } catch (Exception e) {
            // 실패 시 다음 주기 혹은 재시도 로직 실행
        }
    }
}
```

## 4. 장단점 및 고려사항

### 장점
1.  **최종적 일관성 (Eventual Consistency) 보장**: 네트워크 장애가 발생해도 결국에는 메시지가 발행됨을 보장함
2.  **데이터 무결성**: 비즈니스 로직과 이벤트 발행이 DB 트랜잭션으로 묶여 강력한 정합성을 유지함
3.  **메시지 브로커 독립성**: DB 작업 시점에 메시지 브로커가 다운되어 있어도 서비스는 정상 동작함

### 단점 및 고려사항
1.  **실시간성 저하**: 폴링 방식 특성상 약간의 지연(Latency)이 발생할 수 있음 (CDC 기술로 보완 가능)
2.  **메시지 중복 발행**: 전송 성공 후 DB 상태 업데이트 직전에 장애가 나면 메시지가 중복 발행될 수 있음 -> **컨슈머 측의 멱등성(Idempotency) 보장**이 필수
3.  **인프라 복잡도**: 아웃박스 테이블 관리와 메시지 발행 프로세스를 별도로 운영해야 함

### 요약
> **트랜잭셔널 아웃박스 패턴은 "DB는 믿을 수 있지만 네트워크(메시지 브로커)는 믿을 수 없다"는 가정하에 출발함.**
> 분산 환경에서 마이크로서비스 간의 데이터 정합성을 맞추기 위한 가장 신뢰도 높은 표준 패턴 중 하나
