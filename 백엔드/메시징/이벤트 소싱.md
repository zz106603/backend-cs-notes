# 이벤트 소싱 (Event Sourcing)

애플리케이션의 상태 변경을 **데이터(State)** 자체가 아닌 **일련의 사건(Event)** 으로 기록하여 저장하는 데이터 관리 패턴

---

## 1. 개념 및 동작 원리

### 전통적인 데이터 관리 (CRUD)
현재의 최종 상태값만을 데이터베이스에 유지함. 과거의 상태나 변경 이력은 별도의 로그 테이블이 없다면 알 수 없음

*   **예시**: 사용자 정보 수정 시 `UPDATE users SET address = 'Seoul' WHERE id = 1` 실행 -> 기존 주소는 덮어씌워져 사라짐

### 이벤트 소싱 (Event Sourcing)
데이터의 최종 상태가 아닌, 상태를 변경시킨 **이벤트들의 순서대로 나열된 기록**을 저장함. 현재 상태는 이 이벤트들을 처음부터 순서대로 다시 실행(Replay)하여 재구성함

*   **동작 방식**:
    1.  사용자가 주소를 변경함 -> `AddressChanged` 이벤트 발생
    2.  이벤트 저장소(Event Store)에 해당 이벤트를 저장 (Insert Only)
    3.  필요 시 저장된 모든 이벤트를 조회하여 현재 주소를 계산

---

## 2. 구성 요소

### 1) 이벤트 (Event)
시스템에서 발생한 상태 변경을 나타내는 불변 객체. 과거 시제(Past Tense)로 명명함
*   예: `OrderCreated`, `PaymentCompleted`, `ItemShipped`

### 2) 이벤트 저장소 (Event Store)
모든 이벤트를 순서대로 저장하는 데이터베이스. 주로 Append-Only 방식으로 동작하며 수정이나 삭제가 발생하지 않음

### 3) 스냅샷 (Snapshot)
이벤트가 많아질수록 상태를 재구성하는 비용이 커지므로, 특정 시점의 상태를 미리 저장해두는 기술
*   예: 1000번째 이벤트까지 적용된 상태를 저장해두고, 이후에는 1001번째 이벤트부터 리플레이하여 성능을 최적화

---

## 3. 실무 예시: 은행 계좌 시스템

은행 계좌의 잔액(Balance)은 단순히 숫자 하나로 관리되기보다, 입출금 내역의 합으로 관리되는 것이 안전함.

### 시나리오
1.  계좌 생성 (잔액 0원) -> `AccountCreated`
2.  10,000원 입금 -> `MoneyDeposited(10000)`
3.  5,000원 출금 -> `MoneyWithdrawn(5000)`

### 데이터 저장 형태
| Event ID | Event Type | Data | Timestamp |
| :--- | :--- | :--- | :--- |
| 1 | AccountCreated | { owner: "UserA" } | 2023-10-01 10:00 |
| 2 | MoneyDeposited | { amount: 10000 } | 2023-10-01 10:05 |
| 3 | MoneyWithdrawn | { amount: 5000 } | 2023-10-01 12:30 |

### 잔액 조회 (State Replay)
*   **현재 잔액 계산**: `0 + 10000 - 5000 = 5000원`
*   만약 특정 시점(10:10)의 잔액이 필요하다면, 해당 시점까지의 이벤트만 리플레이하여 **과거 상태를 완벽하게 복원**할 수 있음

---

## 4. 장단점 및 고려사항

### 장점
1.  **완벽한 감사 로그 (Audit Trail)**: 누가, 언제, 무엇을 변경했는지 모든 이력이 남음
2.  **과거 상태 복원**: 특정 시점의 데이터 상태로 롤백하거나 조회하는 것이 가능함 (Time Travel)
3.  **데이터 유실 방지**: `UPDATE`나 `DELETE` 없이 `INSERT`만 수행하므로 실수로 인한 데이터 삭제 위험이 적음

### 단점
1.  **복잡성 증가**: 단순한 CRUD 애플리케이션에 비해 구현 난이도가 높음
2.  **데이터 조회 비용**: 매번 이벤트를 리플레이해야 하므로 조회가 느릴 수 있음 -> **CQRS 패턴**과 함께 사용하여 해결
3.  **이벤트 스키마 변경**: 이벤트 구조가 변경되면 과거 이벤트와의 호환성을 관리해야 함 (Versioning 필요)

---

## 5. CQRS와의 관계

이벤트 소싱은 데이터 쓰기(Write)에는 유리하지만 읽기(Read)에는 불리함. 따라서 **명령(Command)과 조회(Query)를 분리하는 CQRS 패턴**과 찰떡궁합임

*   **Write Model**: 이벤트 저장소에 이벤트를 기록 (이벤트 소싱)
*   **Read Model**: 이벤트를 구독하여 별도의 조회 전용 DB(RDB, NoSQL 등)를 갱신
    *   예: `MoneyDeposited` 이벤트 발생 -> 이벤트 저장 -> 비동기로 RDB의 `balance` 컬럼 업데이트

### 결론
> **이벤트 소싱은 데이터의 정합성과 이력 추적이 중요한 금융, 주문, 배송 시스템 등에서 강력한 패턴.**
> 하지만 단순한 도메인에 적용하면 불필요한 복잡성을 초래할 수 있으므로 신중하게 도입해야 함
