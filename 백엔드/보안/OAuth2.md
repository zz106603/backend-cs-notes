# OAuth2

OAuth 2.0은 인가(Authorization)를 위한 산업 표준 프로토콜로, 서드파티 애플리케이션이 사용자 계정에 대한 제한된 접근 권한을 얻을 수 있도록 설계되었습니다.

---

## 1. OAuth2의 등장 배경 및 필요성

### 문제점
*   사용자가 자신의 정보를 다른 서비스(서드파티 앱)와 공유하고 싶을 때, 아이디와 비밀번호를 직접 제공해야 했음
*   이는 보안상 매우 취약하며, 서드파티 앱이 사용자 계정에 대한 모든 권한을 가지게 됨
*   사용자는 언제든지 접근 권한을 철회할 수 없었음

### 해결책
*   OAuth2는 사용자 대신 서드파티 앱이 리소스 서버(예: Google, Facebook)의 보호된 리소스에 접근할 수 있는 **권한을 위임**하는 방식을 제공
*   사용자의 아이디와 비밀번호를 직접 공유하지 않고, **접근 토큰(Access Token)**을 통해 제한된 권한을 부여

---

## 2. OAuth2의 주요 역할 및 구성 요소

### 주요 역할
*   **인가(Authorization)**: 서드파티 앱이 사용자 대신 리소스에 접근할 수 있는 권한을 부여하는 과정
*   **인증(Authentication)**: 사용자가 누구인지 확인하는 과정 (OAuth2는 인가 프로토콜이며, 인증은 OpenID Connect와 같은 다른 프로토콜과 함께 사용될 수 있음)

### 구성 요소
1.  **리소스 소유자 (Resource Owner)**: 보호된 리소스에 접근 권한을 부여하는 사용자 (End-User)
2.  **클라이언트 (Client)**: 리소스 소유자를 대신하여 보호된 리소스에 접근하려는 서드파티 애플리케이션
3.  **인가 서버 (Authorization Server)**: 클라이언트에게 접근 토큰을 발급하는 서버. 리소스 소유자의 인증을 담당하고, 클라이언트에게 인가를 부여함
4.  **리소스 서버 (Resource Server)**: 보호된 리소스를 호스팅하는 서버. 접근 토큰을 사용하여 클라이언트의 요청을 검증하고 리소스를 제공함

---

## 3. OAuth2의 동작 흐름 (Authorization Code Grant Type)

가장 일반적이고 보안성이 높은 인가 코드 부여 방식의 흐름

![OAuth2 Authorization Code Grant Flow Diagram](https://docs.cloud.google.com/static/apigee/docs/api-platform/images/oauth-abstract.png?hl=ko)

*위 이미지는 OAuth2 인가 코드 부여 방식의 전체 흐름을 시각적으로 보여줌. 클라이언트, 리소스 소유자, 인가 서버, 리소스 서버 간의 상호작용과 데이터 흐름(인가 코드, 접근 토큰 등)을 한눈에 파악할 수 있음*

1.  **클라이언트, 인가 요청**: 클라이언트가 리소스 소유자에게 인가 서버로의 리다이렉션을 요청
2.  **리소스 소유자, 인가 승인**: 리소스 소유자가 인가 서버에서 클라이언트에게 권한을 부여할지 결정 (로그인 및 동의)
3.  **인가 서버, 인가 코드 발급**: 리소스 소유자가 승인하면, 인가 서버는 클라이언트에게 **인가 코드(Authorization Code)** 를 발급하여 클라이언트의 `redirect_uri`로 리다이렉트
4.  **클라이언트, 접근 토큰 요청**: 클라이언트는 발급받은 인가 코드와 클라이언트 자격 증명(Client ID, Client Secret)을 인가 서버에 전송하여 **접근 토큰(Access Token)** 을 요청
5.  **인가 서버, 접근 토큰 발급**: 인가 서버는 인가 코드를 검증하고, 유효하면 클라이언트에게 접근 토큰과 선택적으로 **갱신 토큰(Refresh Token)** 을 발급
6.  **클라이언트, 리소스 요청**: 클라이언트는 발급받은 접근 토큰을 사용하여 리소스 서버에 보호된 리소스를 요청
7.  **리소스 서버, 리소스 제공**: 리소스 서버는 접근 토큰의 유효성을 검증하고, 유효하면 요청된 리소스를 클라이언트에게 제공

## 4. 접근 토큰 (Access Token)과 갱신 토큰 (Refresh Token)

### 접근 토큰 (Access Token)
*   보호된 리소스에 접근하기 위한 자격 증명
*   수명이 짧고 (보통 몇 분에서 몇 시간), 탈취되어도 피해를 최소화할 수 있도록 설계
*   클라이언트는 이 토큰을 HTTP `Authorization` 헤더에 담아 리소스 서버에 요청

### 갱신 토큰 (Refresh Token)
*   접근 토큰의 수명이 만료되었을 때, 새로운 접근 토큰을 발급받기 위해 사용
*   수명이 길고 (보통 몇 주에서 몇 달), 보안상 중요한 정보이므로 안전하게 보관되어야 함 (클라이언트 측에서는 보통 저장하지 않음)
*   갱신 토큰을 사용하여 새로운 접근 토큰을 요청할 때도 클라이언트 자격 증명이 필요

---

## 5. 실무 가이드 및 주의사항

### 1) 보안 고려사항
*   **Client Secret 보호**: 클라이언트 시크릿은 절대 외부에 노출되어서는 안 됨. 특히 프론트엔드(SPA, 모바일 앱)에서는 `Authorization Code Grant with PKCE` 방식을 사용하여 Client Secret 없이 인가 코드를 교환
*   **HTTPS 사용**: 모든 통신은 반드시 HTTPS를 통해 이루어져야 함
*   **토큰 만료 시간**: 접근 토큰은 짧게, 갱신 토큰은 길게 설정하되, 적절한 만료 정책을 수립
*   **토큰 폐기**: 사용자가 권한을 철회하거나 계정을 삭제할 경우, 발급된 모든 토큰을 즉시 폐기해야 함

### 2) OpenID Connect (OIDC)
*   OAuth2는 인가(Authorization) 프로토콜이지만, OIDC는 OAuth2 위에 구축된 **인증(Authentication)** 레이어
*   사용자 인증 정보를 얻기 위해 `ID Token`을 추가로 제공하며, 이는 사용자의 신원을 확인하는 데 사용됨
*   "Google로 로그인", "Facebook으로 로그인"과 같은 기능은 대부분 OAuth2 + OIDC를 함께 사용

### 요약
> **OAuth2는 사용자 계정 정보를 직접 공유하지 않고, 서드파티 앱이 보호된 리소스에 접근할 수 있는 안전한 권한 위임 메커니즘을 제공.**
> **다양한 Grant Type이 존재하며, 각 환경(웹, 모바일, SPA)에 맞는 적절한 방식을 선택하고 보안에 유의하는 것이 중요.**
