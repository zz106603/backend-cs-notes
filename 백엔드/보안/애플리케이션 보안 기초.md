# 애플리케이션 보안 기초 (Application Security)

> 정보보안의 기본 개념을 이해하고, 백엔드 개발자가 책임져야 하는 보안 영역과 OWASP의 역할을 설명

## 1. 정보보안 (Information Security)

정보와 정보시스템을 비인가 접근, 유출, 변경, 파괴 및 서비스 중단으로부터 보호하는 것을 의미

단순히 외부 공격자의 침입을 막는 것만이 아니라 정상적인 사용자도 허용된 범위 내에서만 시스템을 이용하도록 보호하는 것을 포함

### 정보보안의 3요소 (CIA Triad)

| **요소** | **의미** | **금융 서비스 침해 사례** |
| --- | --- | --- |
| 기밀성(Confidentiality) | 허가된 사용자만 정보에 접근할 수 있어야 함 | 다른 고객의 계좌 및 거래 내역 조회 |
| 무결성(Integrity) | 정보가 허가 없이 변경되거나 훼손되지 않아야 함 | 계좌 잔액이나 거래내역 조작 |
| 가용성(Availability) | 필요한 시점에 정상적으로 서비스를 이용할 수 있어야 함 | 과도한 API 요청으로 금융 서비스 중단 |

### 백엔드 개발 관점의 CIA

| **보호 목표** | **백엔드 구현 방법** |
| --- | --- |
| 기밀성 | 인증, 인가, 암호화, 민감정보 마스킹 |
| 무결성 | 전자서명, 해시 검증, 트랜잭션, 데이터 변경 권한 검증 |
| 가용성 | Rate Limiting, 타임아웃, 장애 복구, 부하 분산 |
- 현재 Financial API Defense Lab에서 계좌 소유권을 검증하고 허가받지 않은 거래내역 조회를 차단하는 것은 주로 **기밀성을 보호하기 위한 기능**
- BOLA가 데이터 수정이나 삭제 API에서 발생한다면 무결성까지 침해될 수 있음

## 2. 애플리케이션 보안 (AppSec)

애플리케이션의 설계, 개발, 배포, 운영 과정에서 발생할 수 있는 보안 취약점을 예방하고 발견하고 대응하는 활동

### 구분

| **보안 영역** | **주요 보호 대상** | **대표적인 보안 기술** |
| --- | --- | --- |
| 네트워크 보안 | 네트워크 및 통신 | 방화벽, IDS, IPS |
| 시스템 보안 | 서버 및 운영체제 | OS 패치, 계정 관리 |
| 클라우드 보안 | 클라우드 인프라 | IAM, 보안 그룹 |
| 애플리케이션 보안 | 애플리케이션 코드 및 로직 | 인증, 인가, 입력값 검증 |
| 데이터 보안 | 저장 및 전송 데이터 | 암호화, 마스킹, 접근 제어 |

### 백엔드 개발자가 보안을 알아야 하는 이유

인프라 수준의 보안 장비만으로는 애플리케이션의 비즈니스 규칙을 모두 검증할 수 없음

ex) 계좌 조회 요청

```java
GET /api/accounts/1002
Authorization: Bearer <access_token>
```

- 네트워크 통신이 정상적이고 유효한 JWT가 포함되더라도 요청한 사용자가 계좌 1002의 소유자인지는 별도로 확인해야 함
- 방화벽이나 API Gateway가 정상적인 요청으로 판단하더라도 애플리케이션에서 객체 접근 권한을 검증하지 않으면 금융정보가 유출될 수 있음
- **해당 기능을 누가, 어떤 조건에서, 어떤 데이터에 대해 실행할 수 있는지**까지 설계해야 함

## 3. 보안 기본 용어

보안 관련 문서나 취약점 분석 결과를 이해하려면 위협, 취약점, 공격, 위험을 구분

### 주요 용어

| **용어** | **의미** |
| --- | --- |
| 자산 (Asset) | 보호해야 하는 데이터, 시스템, 서비스 |
| 위협 (Threat) | 자산에 피해를 줄 가능성이 있는 행위나 상황 |
| 취약점 (Vulnerability) | 위협에 의해 악용될 수 있는 시스템의 약점 |
| 공격 (Attack) | 취약점을 악용하거나 보안 목표를 침해하려는 행위 |
| 위험 (Risk) | 위협이 현실화될 가능성과 그로 인한 피해 수준 |
| 보안 사고 (Security Incident) | 보안 정책을 위반하거나 보안 목표를 실제로 또는 잠재적으로 침해한 사건 |
| 보안 통제 (Security Control) | 보안 위험을 예방하거나 줄이기 위한 보호 조치 |

### BOLA를 예시로 구분

- 자산 → 고객 계좌정보 및 거래 내역
- 위협 → 다른 고객의 금융정보에 비인가 접근할 가능성
- 취약점 → 계좌 조회 API의 객체 단위 인가 검증 누락
- 공격 → 자신에게 권한이 없는 계좌에 접근을 시도
- 피해 발생 → 다른 고객의 금융정보 유출
- 보안 통제 → 계좌 소유권 검증, 접근 거부, 감사 로그, 이상 접근 탐지

### 위험 평가 (Risk Assessment)

위험은 일반적으로 다음 두 가지 요소를 고려하여 판단

Risk = Likelihood X impact

- **Likelihood: 위협이 실제로 발생할 가능성**
- **Impact: 발생했을 때 시스템이나 사용자에게 미치는 피해**

이는 위험을 이해하기 위한 단순화된 모델이며 모든 위험 평가에서 동일한 계산식을 사용하는 것은 아님

## OWASP (Open Worldwide Application Security Project)

### OWASP

> 소프트웨어 보안 수준을 향상하기 위해 보안 지식, 개발 가이드, 검증 기준, 오픈소스 도구 등을 제공하는 비영리 재단 및 글로벌 커뮤니티
>

특정 기업의 보안 솔루션이나 프레임워크가 아니며 개발자가 안전한 소프트웨어를 설계하고 구현할 수 있도록 공개 자료를 제공

### 주요 프로젝트

| **프로젝트** | **섦여** | **활용 시점** |
| --- | --- | --- |
| OWASP Top 10 | 웹 애플리케이션의 주요 보안 위험 | 보안 위험 파악 |
| OWASP API Security Top 10 | API 환경의 주요 보안 위험 | API 설계 및 개발 |
| OWASP Cheat Sheet Series | 보안 기능별 구현 가이드 | 보안 기능 구현 |
| OWASP ASVS | 애플리케이션 보안 요구사항 및 검증 기준 | 요구사항 정의 및 검증 |
| OWASP WSTG | 웹 애플리케이션 보안 테스트 가이드 | 취약점 테스트 |
- Top 10으로 주요 위험을 파악하고, Cheat Sheet를 참고하여 구현하며, ASVS와 WSTG를 참고하여 검증할 수 있음

### 실무에서 활용

1. **위험 파악 (OWASP API Security Top 10)**
    1. 객체 단위 인가 실패 위험 확인
2. **설계 및 구현 (Authorization Cheat Sheet)**
    1. 모든 객체 접근 요청에 대해 인가 검증
3. **검증 요구사항 정의 (OWASP ASVS)**
    1. 접근 권한이 없는 사용자의 데이터 조회 차단 여부 확인
4. **테스트 및 지속적인 관리 (보안 테스트, CI/CD)**
    1. 인가 검증이 누락되지 않도록 회귀 테스트 수행

OWASP Top 10에 포함된 모든 항목을 대응했다고 해서 애플리케이션의 보안이 완전히 보장되는 것은 아님

## 5. OWASP Top 10

| **분류** | **보안 위험** | **백엔드 발생 사례** |
| --- | --- | --- |
| A01 | Broken Access Control (접근 제어 실패) | 다른 사용자의 데이터에 접근 |
| A02 | Security Misconfiguration (보안 설정 오류) | 관리용 엔드포인트 외부 노출 |
| A03 | Software Supply Chain Failures (소프트웨어 공급망 실패) | 취약하거나 변조된 의존성 사용 |
| A04 | Cryptographic Failures (암호화 실패) | 민감정보 평문 저장 |
| A05 | Injection (인젝션) | 사용자 입력에 의한 SQL 조작 |
| A06 | Insecure Design (안전하지 않은 설계) | 인증번호 재시도 횟수 재한 누락 |
| A07 | Authentication Failures (인증 실패) | 만료된 토큰 허용 |
| A08 | Software or Data Integrity Failures (소프트웨어 또는 데이터 무결성 실패) | 무결성을 검증하지 않은 업데이트 적용 |
| A09 | Security Logging and Alerting Failures (보안 로깅 및 알림 실패) | 반복적인 비인가 접근 미탐지 |
| A10 | Mishandling of Exceptional Conditions (예외 상황의 부적절한 처리) | 권한 확인 중 예외 발생 시 접근 허용 |

## 6. OWASP API Security Top 10

### OWASP Top 10과의 차이

- OWASP Top 10은 API에서 발생할 수 있는 보안 위험에 초점을 맞춘 자료

| **구분** | **OWASP Top 10** | **API Security Top 10** |
| --- | --- | --- |
| 대상 | 웹 애플리케이션 전반 | API |
| 주요 관심사 | 접근 제어, 인젝션, 암호화, 공급망 등 | 객체 접근 권한, API 인증, 리소스 소비 등 |
| 버전 | 2025 | 2023 |
| 프로젝트 관련성 | 전체적인 보안 위험 분류 | API 취약점의 구체적인 분류 |

### API Security Top 10:2023

| 분류 | 보안 위험 | 발생 사례 |
| --- | --- | --- |
| API1 | Broken Object Level Authorization (BOLA) | 다른 고객의 계좌 조회 |
| API2 | Broken Authentication | 인증 검증 오류로 타인 계정 사용 |
| API3 | Broken Object Property Level Authorization (BOPLA) | 권한이 없는 개인정보 조회 및 수정 |
| API4 | Unrestricted Resource Consumption | 과도한 요청으로 서버 자원 고갈 |
| API5 | Broken Function Level Authorization (BFLA) | 일반 사용자의 관리자 API 실행 |
| API6 | Unrestricted Access to Sensitive Business Flows | 자동화된 요청으로 상품 및 예약 선점 |
| API7 | Server Side Request Forgery (SSRF) | 서버를 통한 내부 서비스 비인가 접근 |
| API8 | Security Misconfiguration | 불필요한 API 및 민감한 설정 정보 노출 |
| API9 | Improper Inventory Management | 취약한 구버전 API가 방치됨 |
| API10 | Unsafe Consumption of APIs | 외부 API 응답을 검증하지 않고 처리 |

### BOLA와 Broken Access Control의 관계

#### A01: Broken Access Control

접근 제어 실패라는 포괄적인 보안 위험

#### API1: BOLA → 객체 단위 인가 실패

- 다른 사용자의 계좌, 주문, 게시글에 접근

#### API3: BOPLA → 객체 속성 단위 인가 실패

- 허용되지 않은 데이터 필드 조회 및 수정

#### API5:BFLA → 기능 단위 인가 실패

- 권한이 없는 관리자 기능 실행

## CVE, CWE, CVSS

라이브러리 취약점 검사, 보안 리포트, Trivy와 같은 보안 도구를 사용하면 자주 접하는 용어

### 차이

| 구분 | 전체 명칭 | 의미 |
| --- | --- | --- |
| CVE | Common Vulnerabilities and Exposures | 공개된 개별 보안 취약점을 식별하는 체계 |
| CWE | Common Weakness Enumeration | 소프트웨어 및 하드웨어의 보안 약점 유형을 분류하는 체계 |
| CVSS | Common Vulnerability Scoring System | 취약점의 기술적 심각도를 평가하는 체계 |
| NVD | National Vulneraability Database | CVE 정보를 기반으로 분석 정보를 제공하는 데이터베이스 |

CVE → 어떤 취약점인가?

CWE → 어떤 유형의 약점 때문에 발생했는가?

CVSS → 기술적으로 얼마나 심각한가?

NVD → 해당 취약점과 관련된 분석 정보는 무엇인가?

OWASP → 개발할 때 어떤 보안 위험에 주의해야 하는가?

### BOLA를 기준으로 이해하기

#### OWASP → API1:2023 BOLA

- 해당 문제가 속하는 API 보안 위험 범주

#### CWE → CWE-639

- 사용자가 제어하는 식별자를 통한 인가 우회라는 약점 유형

#### CVE → 개별 취약점 식별 번호

- CVE 등록 요건을 충족하고 번호가 할당된 경우 해당 제품의 구체적인 취약점을 식별

#### CVSS → 취약점 심각도 점수

- 공격 조건 및 기밀성, 무결성, 가용성 등에 대한 영향을 고려하여 평가

### CVSS 심각도

CVSS 점수가 높다고 해서 모든 상황에서 가장 먼저 조치해야 하는 것은 아님

실제 서비스에서 해당 기능을 사용하는지, 외부에 노출되어 있는지, 악용 가능성이 있는지, 어떤 데이터가 영향을 받는지 등을 종합적으로 고려해야 함

또한 Trivy와 같은 의존성 취약점 검사 도구에서 발견된 CVE가 없다고 해서 직접 작성한 비즈니스 로직에 BOLA가 없다는 의미는 아님

## 보안 설계 원칙

### 최소 권한 원칙 (Principal of Least Privilege)

> 사용자가 시스템에 업무 수행에 필요한 최소한의 권한만 부여하는 원칙
>

| **접근 주체** | **허용 권한** |
| --- | --- |
| 고객 | 본인 계좌 및 거래내역 조회 |
| 제휴사 | 권한을 위임받은 계좌의 거래내역 조회 |
| DB 조회 전용 계정 | SELECT |
| 모니터링 담당자 | 감사 로그 및 탐지 결과 조회 |

### 기본 거부 (Deny by Default)

> 명시적으로 허용되지 않은 모든 접근은 기본적으로 거부하는 원칙
>

ex) 제휴사의 계좌 접근 권한이 DB에 존재하지 않으면 접근을 허용하지 않아야 함

새로운 사용자 유형이나 API가 추가되었을 때도 별도의 허용 정책이 정의되지 않았다면 접근을 거부하는 것이 안전

### 심층 방어 (Defense in Depth)

> 하나의 보안 기능에만 의존하지 않고 여러 계층에 보호 장치를 구성하는 원칙
>
1. 네트워크 계층 (방화벽, WAF)
2. API Gateway 계층 (요청 제한, 토큰 검증)
3. 애플리케이션 계층 (인증, 기능 단위 인가, 입력값 검증)
4. 데이터 접근 계층 (객체 소유권 및 접근 권한 검증)

각 계층의 책임은 서로 다름. JWT 검증이 성공했다고 해서 데이터에 대한 인가 검증을 생략하면 안 됨

### 모든 요청에 대한 권한 검증 (Complete Mediation)

> 사용자가 이전에 접근 권한을 가지고 있었다는 이유로 이후의 요청까지 무조건 허용하지 않는 원칙
>

ex)

1. 고객이 제휴사에 거래내역 조회 권한을 부여
2. 제휴사가 거래내역을 조회
3. 고객이 제휴사의 접근 권한을 회수
4. 제휴사가 기존 JWT로 다시 조회를 요청
5. 서버가 현재 권한 상태를 확인하고 접근을 거부

최소 권한, 기본 거부, 요청마다 권한 검증은 OWASP Authorization Cheat Sheet에서도 권장하는 인가 구현 원칙

### 안전한 실패 (Fail Secure)

> 보안 검증 과정에서 오류가 발생하면 보안이 유지되는 방향으로 처리하는 원칙
>

| **상황** | **잘못된 처리** | **안전한 처리** |
| --- | --- | --- |
| JWT 검증 실패 | 인증 없이 요청 처리 | 인증 거부 |
| 권한 조회 DB 오류 | 임시로 데이터 접근 허용 | 접근 차단 및 오류 응다 |
| 서명 검증 실패 | 검증 생략 후 처리 | 요청 거부 |

---

## 보안 통제의 종류

목적에 따라 예방, 탐지, 교정 통제로 구분

| **종류** | **대표적인 방법** | **현재 프로젝트** |
| --- | --- | --- |
| 예방 통제 | 인증, 인가, 입력값 검증 | JWT, 객체 단위 인가 |
| 탐지 통제 | 감사 로그, 이상 탐지, 보안 알림 | 반복 비인가 접근 탐지 및 모니터링 |
| 교정 통제 | 취약점 수정, 사고 복구, 침해된 권한 회수 | 사고 대응 자동화는 별도 확장 영역 |

## 프로젝트 보안 영역 정리

| 구현 내용 | 보안 개념 | 목적 |
| --- | --- | --- |
| JWT RS256 검증 | Authentication | 인증된 접근 주체 확인 |
| 계좌 소유권 검증 | Object Level Authorization | 타인 데이터 접근 방지 |
| 제휴사 권한 위임 | Least Privilege | 필요한 범위의 권한 부여 |
| SQL 조회 조건 내 인가 검증 | BOLA Prevention | 비인가 데이터 조회 방지 |
| 권한 부여 및 회수 동시성 처리 | Authorization Consistency | 권한 상태의 일관성 유지 |
| 금융정보 접근 이력 기록 | Audit Logging | 접근 행위 추적 |
| 계좌 식별자 가명 처리 | Data Protection | 로그 내 민감정보 보호 |
| 반복적인 접근 위반 탐지 | Anomaly Detection | 비정상 접근 패턴 식별 |
| 보안 모니터링 화면 | Security Monitoring | 이상 행위 및 접근 이력 확인 |
| 인가 테스트 및 결함 주입 | Security Testing | 보안 기능의 유효성 검증 |

> **OWASP API Security Top 10의 BOLA를 중심으로 금융 API의 객체 단위 접근 제어를 구현하고, 감사 로그와 규칙 기반 이상 접근 탐지, 보안 테스트를 통해 방어 기능을 검증하는 프로젝트**
