# 2. 인증과 인가 (Authentication & Authorization)

> 인증과 인가의 차이를 이해하고 세션, JWT, OAuth 2.0, OIDC의 동작 원리와 접근 제어 모델을 설명할 수 있음. 이를 Spring Security 및 현재 프로젝트의 구현 구조와 연결

## 1. 인증과 인가

### 인증 (Authentication)

요청을 보낸 사용자가 누구인지 확인하는 과정

- 아이디와 비밀번호
- OTP 및 MFA (다중 요소 인증)
- 인증서 및 전자서명
- 세션 ID
- Access Token

로그인 과정에서는 사용자의 신원을 확인하고, 이후 요청에서는 세션 ID나 토큰 등의 자격 증명을 검증하여 인증된 사용자를 식별

### 인가 (Authorization)

인증된 사용자 등이 특정 리소스에 접근하거나 기능을 실행할 권한이 있는지 판단하는 과정

| **구분** | **인증** | **인가** |
| --- | --- | --- |
| 핵심 질문 | 누구인가? | 무엇을 할 수 있는가? |
| 영문 | Authentication | Authorization |
| 검증 대상 | 신원 및 자격 증명 | 역할, 권한, 소유권 |
| 구현 기술 | Session, JWT, OIDC | RABC, ABAC, ReBAC |
| 실패 응답 | 주로 401 | 주로 403 또는 404 |
| 금융 서비스 예시 | 고객 신원 확인 | 고객의 계좌 조회 권한 확인 |

### 인증, 인가 처리 흐름

#### GET /api/accounts/1002 → 고객 A의 계좌 조회 요청

1. **인증 (Authentication)**
    1. 유효한 자격 증명인가?
    2. JWT 검증 및 고객 A 식별
    3. 실패하면 401
2. **기능 단위 인가**
    1. 계좌 조회 기능을 사용할 수 있는가?
    2. 실패하면 403
3. **객체 단위 인가**
    1. 계좌 1002에 접근할 권한이 있는가?
    2. 소유권 및 위임 권한 검증
    3. 실패하면 403 또는 404

## 2. HTTP와 인증 상태 관리

### HTTP의 Stateless 특성

- HTTP는 기본적으로 이전 요청의 상태를 기억하지 않는 프로토콜
- 사용자가 로그인에 성공하더라도 별도의 인증 상태 관리 수단이 없다면 서버는 다음 요청을 동일한 사용자가 보낸 것인지 알 수 없음
- 대표적인 방식이 **세션 기반 인증과 토큰 기반 인증**

### 세션, 쿠키, JWT의 관계

| **개념** | **역할** |
| --- | --- |
| Session | 서버에서 사용자의 인증 상태 등을 관리하는 방식 |
| Cookie | 브라우저에 정보를 저장하고 HTTP 요청에 전달하는 수단 |
| JWT | 사용자 식별 정보 등의 Claim을 담을 수 있는 토큰 형식 |
| Authorization Header | HTTP 요청에 인증 자격 증명을 전달하는 수단 |
- 쿠키에는 세션 ID를 저장할 수도 있고 JWT를 저장할 수도 있음

## 3. 세션 기반 인증 (Session-based Authentication)

### 동작 원리

> 서버에 사용자의 인증 상태를 저장하고 클라이언트에는 해당 상태를 식별할 수 있는 세션 ID를 전달하는 방식
>

!download.svg

서버는 다음과 같은 정보를 저장할 수 있음

```java
{
  "sessionId": "random-session-id",
  "userId": 1001,
  "role": "CUSTOMER",
  "expiresAt": "..."
}
```

실제 브라우저에는 일반적으로 사용자 정보 전체가 아닌 세션 ID가 전달됨

```java
Set-Cookie: JSESSIONID=random-session-id; HttpOnly; Secure; SameSite=Lax
```

이후 브라우저는 쿠키 전송 조건에 맞는 요청에 세션 ID를 자동으로 포함

### 세션 저장 위치

| **저장 위치** | **특징** |
| --- | --- |
| 서버 메모리 | 구현이 간단하지만 서버 재시작 시 세션 유실 가능 |
| Redis | 여러 서버에서 세션 공유 가능, TTL 관리 용이 |
| RDBMS | 영속적인 저장 가능, 조회 비용 고려 필요 |
- 서버가 여러 대라면 Redis와 같은 공유 세션 저장소를 사용하여 서버마다 인증 상태가 달라지는 문제를 해결할 수 있음

### 장단점 및 보안 고려사항

| **장점** | **단점** |
| --- | --- |
| 서버에서 세션을 즉시 폐기 가능 | 서버 측 세션 저장 공간 필요 |
| 인증 상태를 중앙에서 관리 | 분산 환경에서 세션 공유 필요 |
| 클라이언트에 전달하는 정보가 적음 | 요청 처리 시 세션 정보 조회 필요 |
- 세션 ID가 탈취되면 공격자가 해당 사용자의 인증 상태를 악용할 수 있음
- 충분히 예측하기 어려운 세션 ID를 사용하고 로그인 성공 시 세션 ID를 갱신하며 로그아웃과 만료 시 서버에서도 세션을 폐기해야 함

## 4. JWT 기반 인증 (Token-based Authentication)

### JWT (Json Web Token)

> 사용자 식별 정보나 권한 정보 등의 Claim을 JSON 기반으로 표현하는 표준 토큰 형식
>
- 서명된 JWT를 사용하면 서버에 인증 세션을 저장하지 않고도 토큰의 무결성과 유효성을 검증할 수 있음
- 다만 JWT 자체가 인증 프로토콜은 아님. 인증 과정에서 발급하거나 전달하는 토큰의 형식

### 구조

일반적으로 사용하는 서명된 JWT (JWS Compact Serialization)는 Header, Payload, Signature로 구성

#### Header → 토큰 형식 및 서명 알고리즘

```java
{
  "alg": "RS256",
  "typ": "JWT"
}
```

#### Payload → 사용자 식별 정보 및 Claim

```java
{
  "sub": "1001",
  "principal_type": "CUSTOMER",
  "iss": "financial-api",
  "aud": "financial-api",
  "iat": 1800000000,
  "exp": 1800000900
}
```

#### Signature → 토큰 변조 여부 검증

- 인코딩된 Header와 Payload를 대상으로 생성한 서명

Header와 Payload는 Base64URL로 인코딩되어 있음. 암호화된 것이 아니므로 토큰을 가진 사람은 내용을 확인할 수 있음

따라서 비밀번호, 주민등록번호, 계좌번호와 같은 민감정보를 일반적인 서명형 JWT의 Payload에 넣어서는 안 됨

### 주요 Claim

| **Claim** | **의미** |
| --- | --- |
| `sub` (Subject) | 토큰의 주체를 식별하는 값 |
| `iss` (Issuer) | 토큰 발급자 |
| `aud` (Audience) | 토큰을 사용할 대상 서비스 |
| `iat` (Issued At) | 토큰 발급 시각 |
| `exp` (Expiration Time) | 토큰 만료 시각 |
| `nbf` (Not Before) | 토큰 사용 가능 시작 시각 |
| `jti` (JWT ID) | 토큰 고유 식별자 |
| `principal_type` | 프로젝트에서 정의한 사용자 유형 |
| `roles`, `scope` | 토큰에 포함될 수 있는 역할 및 접근 범위 정보 |
- JWT 표준에서 정의한 Claim과 애플리케이션에서 직접 정의한 Claim을 구분해야 함
- `principal_type`은 고객과 제휴사를 구분하기 위해 정의한 커스텀 Claim

### JWT 기반 인증 흐름

!download.svg

- 서버는 요청마다 JWT의 서명과 만료 시간 등을 검증하고 토큰에 포함된 사용자 식별 정보를 사용
- 인증 세션을 별도로 관리하지 않는 구조를 Stateless Authentication이라고 함
- 단, Stateless라고 해서 DB 조회가 없어야 한다는 의미는 아님. 사용자 활성 상태나 최신 접근 권한을 검증하기 위해 DB를 조회할 수 있음

## 5. JWT 서명 알고리즘 (HS256, RS256)

### JWT에 서명이 필요한 이유

- JWT의 Payload는 클라이언트에서도 읽고 변경할 수 있음
- 만약 서버가 Payload의 내용을 그대로 신뢰한다면 사용자가 자신의 역할이나 사용자 ID를 변경하여 다른 권한을 가진 사용자로 처리될 수 있음
- 이를 방지하기 위해 토큰을 발급할 때 서명을 생성하고 요청을 받을 때 서명을 검증

### HS256과 RS256의 차이

| 구분 | HS256 | RS256 |
| --- | --- | --- |
| 방식 | 대칭키 기반 MAC | 비대칭키 기반 전자서명 |
| 알고리즘 | HMAC-SHA256 | RSA PKCS#1 v1.5 + SHA-256 |
| 서명 생성 | Secret Key | Private Key |
| 키 공유 | 발급자와 검증자가 비밀 키 공유 | 검증자에게 공개키만 제공 |
| 활용 | 신뢰 경계가 단순한 서비스 | 발급 서버와 검증 서버가 분리된 환경 |

### RS256 동작 원리

#### 1. 토큰 발급 서버

Private Key (개인키) → 발급 서버만 보유하며 외부에 공개하지 않음

`Header + Payload -> 전자서명 생성`

#### 2. 서명된 JWT

#### 3. API 서버

Public Key (공개키) → 발급 서버의 공개키로 서명을 검증

`JWT 서명 검증 -> Claim 검증 -> 인증 처리`

- RS256의 장점은 토큰 발급 권한과 검증 권한을 분리할 수 있다는 점
- API 서버가 공개키를 가지고 있어도 해당 공개키만으로 새로운 유효한 JWT를 서명할 수 없음
- 반면 HS256에서는 토큰 검증에 필요한 Secret Key로 새로운 토큰도 생성할 수 있기 때문에 여러 서비스에 키를 공유할 경우 신뢰 범위를 고려해야 함
- RS256이 모든 환경에서 HS256보다 안전하다는 의미는 아님. 시스템 구조와 키 관리 방식에 따라 적절한 알고리즘을 선택해야 함

### JWT 검증 시 확인할 사항

| **검증 항목** | **목적** |
| --- | --- |
| Signature | 토큰 변조 여부 확인 |
| Algorithm | 서버에서 허용한 서명 알고리즘인지 확인 |
| `exp` | 만료된 토큰인지 확인 |
| `nbf` | 사용 가능 시각이 되었는지 확인 |
| `iss` | 신뢰하는 발급자가 생성했는지 확인 |
| `aud` | 현재 서비스에 사용하도록 발급했는지 확인 |
| `sub` | 유효한 접근 주체를 나타내는지 확인 |
| Token Type | 해당 용도로 발급한 토큰인지 확인 |
- 서버는 JWT Header에 명시된 알고리즘을 그대로 신뢰하면 안 되며 사전에 허용한 알고리즘을 기준으로 검증해야 함
- **서명은 토큰의 기밀성을 보장하지 않음**
    - 토큰 자체가 탈취되면 서명을 변경하지 않고도 유효기간 동안 재사용될 수 있으므로 HTTPS와 안전한 저장 방식이 필요함

## 6. Access Token과 Refresh Token

### 역할

| **구분** | **Access Token** | **Refresh Token** |
| --- | --- | --- |
| 목적 | 보호된 API 접근 | 새로운 Access Token 발급 |
| 유효기간 | 상대적으로 짧음 | 상대적으로 길 수 있음 |
| 전달 대상 | Resource Server | Authorization Server의 토큰 엔드포인트 |
| 사용 빈도 | API 요청 시 | Access Token 갱신 시 |
| 탈취 시 위험 | API 접근 권한 악용 | 지속적인 토큰 재발급 가능 |

Access Token과 Refresh Token 모두 반드시 JWT 형식일 필요는 없음

불투명 토큰(Opaque Token)으로도 구현할 수 있음

### Access Token 만료 및 갱신 과정

1. 로그인
2. Access Token 및 Refresh Token 발급
3. Access Token으로 API 요청
4. Access Token 만료
5. Refresh Token으로 토큰 갱신 요청
6. 유효하면 재발급, 무효하면 재인증 필요

### 토큰 폐기와 로그아웃

- 서버에 상태를 저장하지 않는 JWT 기반 인증은 이미 발급한 Access Token을 즉시 무효화하기 어렵다는 특징이 있음
- 브라우저에서 JWT를 삭제하더라도 별도로 복사된 JWT는 만료 전까지 사용될 수 있음

| 방법 | 설명 |
| --- | --- |
| 짧은 Access Token 만료 시간 | 탈취된 토큰이 사용 가능한 시간을 제한 |
| Refresh Token 폐기 | 새로운 Access Token 발급 방지 |
| Token Denylist | 폐기된 토큰 식별자를 Redis 등에 저장하여 검증 |
| Token Version | 사용자별 토큰 버전을 변경하여 기존 토큰 무효화 |
| Token Introspection | 인증 서버에서 토큰의 활성 상태 확인 |
- Refresh Token Rotation은 갱신 요청마다 새로운 Refresh Token을 발급하고 기존 토큰을 무효화하는 방식
- 적절하게 구현하면 Refresh Token 재사용을 탐지하는 데에도 활용할 수 있음
- 즉시 토큰을 폐기하기 위해 별도의 서버 상태를 관리하면 완전한 Stateless 구조와는 달라질 수 있음

## 7. 세션 기반 인증과 JWT 기반 인증 비교

| 구분 | 세션 기반 | Stateless JWT 기반 |
| --- | --- | --- |
| 인증 상태 저장 | 서버 | 서명된 토큰 |
| 클라이언트 보유 정보 | 세션 ID | JWT |
| 요청마다 처리 | 세션 정보 조회 | 서명 및 Claim 검증 |
| 서버 확장 | 세션 공유 구조 고려 | 검증키 공유 및 관리 |
| 즉시 로그아웃 | 비교적 용이 | 별도 폐기 정책 필요 |
| 권한 변경 반영 | 구현 방식에 따라 다름 | 토큰 내 권한은 만료 전까지 유지될 수 있음 |
| 주요 보안 위험 | 세션 탈취, 세션 고정, CSRF | 토큰 탈취, 검증 오류, 권한 변경 미반영 |

### 실무에서의 선택 기준

#### 세션 기반

- 서버에서 로그인 상태를 중앙 관리해야 하는 서비스
- 즉각적인 세션 종료와 접속 제어가 중요한 서비스
- 브라우저 중심의 단일 애플리케이션

#### JWT 기반

- 여러 API 서버가 동일한 발급자의 토큰을 검증하는 환경
- 인증 서버와 리소스 서버의 책임을 분리하는 환경
- 서버 측 인증 세션에 대한 의존성을 줄이려는 서비스

JWT가 세션보다 항상 빠르거나 안전한 것은 아님. JWT 검증에도 연산 비용이 발생하고 권한 확인을 위해 추가적인 데이터 조회가 필요할 수 있음

## 8. Cookie와 AUthorization Header

JWT를 선택한 이후에는 토큰을 어디에 저장하고 어떻게 전달할 것인지 결정해야 함

### 결정 방식

#### Cookie 방식

1. 브라우저 Cookie 저장소 → JWT 저장
2. HTTP 요청 → 브라우저가 조건에 따라 자동 첨부
3. 백엔드 서버

```java
GET /api/accounts/1001
Cookie: access_token=eyJ...
```

#### Header 방식

1. 클라이언트 저장소 → 메모리 등에 JWT 저장
2. HTTP 요청 → 클라이언트가 직접 첨부
3. 백엔드 서버

```java
GET /api/accounts/1001
Authorization: Bearer eyJ...
```

### 방식별 보안 차이

| 구분 | HttpOnly Cookie | Authorization Header |
| --- | --- | --- |
| 요청 시 전달 | 브라우저가 자동 첨부 | 일반적으로 클라이언트가 직접 첨부 |
| JavaScript 접근 | HttpOnly 적용 시 불가능 | 저장 위치에 따라 가능 |
| XSS에 의한 토큰 탈취 | 직접적인 쿠키 탈취 위험 감소 | JS 접근 가능한 저장소라면 탈취 가능 |
| CSRF 위험 | 존재 | 토큰을 직접 첨부하는 구조라면 상대적으로 낮음 |
| 주요 활용 환경 | 브라우저 기반 서비스 | 모바일, 외부 API, 서버 간 통신 등 |
- Authorization Header는 토큰의 전달 수단이고 LocalStorage는 저장 수단

### Cookie의 주요 보안 속성

```java
Set-Cookie: access_token=eyJ...;
HttpOnly;
Secure;
SameSite=Lax;
Path=/
```

| 속성 | 역할 |
| --- | --- |
| `HttpOnly` | JavaScript에서 쿠키를 직접 읽는 것을 제한 |
| `Secure` | HTTPS 통신에서만 쿠키 전송 |
| `SameSite` (Strict, Lax, None) | Cross-site 요청에서 쿠키 전송 조건 제한 |
| `Path` | 쿠키를 전송할 URL 경로 지정 |
| `Domain` | 쿠키를 전송할 도메인 범위 지정 |
| `Max-age` | 쿠키 유지 시간 지정 |

### JWT를 Cookie에 저장하면 CSRF가 발생할 수 있는 이유

- CSRF(Cross-Site Request Forgery)는 사용자가 의도하지 않은 요청을 인증된 브라우저에서 실행하도록 유도하는 공격
- Cookie는 전송 조건이 충족되면 브라우저가 자동으로 첨부
    - 따라서 세션 ID를 사용하는지 JWT를 사용하는지와 관계없이 Cookie 기반 인증이라면 CSRF 위험을 검토해야 함
- 또한 HttpOnly는 JavaScript가 쿠키 값을 직접 읽지 못하게 하는 속성이지 CSRF를 방어하는 기능은 아님

| 보안 대첵 | 보호 목적 |
| --- | --- |
| HttpOnly Cookie | JavaScript에 의한 직접적인 토큰 탈취 제한 |
| Secure Cookie | 평문 통신을 통한 토큰 노출 방지 |
| SameSite | Cross-site 쿠키 전송 제한 |
| CSRF Token | 요청의 정당성 검증 |
| XSS 방어 | 악성 스크립트 실행 방지 |

**JWT + Cookie + Stateless 구조라고 해서 CSRF 보호를 무조건 비활성화하면 안 됨**

| 보안 대첵 | 보호 목적 |
| --- | --- |
| HttpOnly Cookie | JavaScript에 의한 직접적인 토큰 탈취 제한 |
| Secure Cookie | 평문 통신을 통한 토큰 노출 방지 |
| SameSite | Cross-site 쿠키 전송 제한 |
| CSRF Token | 요청의 정당성 검증 |
| XSS 방어 | 악성 스크립트 실행 방지 |

**JWT + Cookie + Stateless 구조라고 해서 CSRF 보호를 무조건 비활성화하면 안 됨**

## 9. OAuth 2.0

### OAuth 2.0(Open Authorization 2.0)

> 사용자가 자신의 자격 증명을 외부 애플리케이션에 직접 제공하지 않고도 제한된 리소스 접근 권한을 부여할 수 있도록 하는 인가 프레임워크
>

ex) 일정 관리 서비스가 사용자의 Google Calendar를 조회해야 한다면 사용자의 Google 비밀번호를 직접 받는 대신 Google이 발급한 Access Token을 사용하여 허용된 범위의 API를 호출할 수 있음

OAuth 2.0에서 중요한 개념은 **접근 권한의 위임(Delegated Authorization)**

### 구성 요소

| 구성 요소 | 역할 | 예시 |
| --- | --- | --- |
| Resource Owner | 리소스에 대한 접근을 승인할 수 있는 주체 | Google 계정 사용자 |
| Client | 리소스에 접근하려는 애플리케이션 | 일정 관리 서비스 |
| Authorization Server | 권한 승인 및 토큰 발급 | Google 인증/인가 서버 |
| Resource Server | 보호된 리소스를 제공하는 서버 | Google Calender API |

!download.svg

### Authorization Code Flow

1. Client가 사용자를 Authorization Server의 인증/인가 화면으로 이동시킴
2. 사용자가 로그인하고 필요한 권한을 승인
3. Authorization Server가 Client의 Redirect URI로 Authorization Code를 전달
4. Client가 Authorization Code를 토큰 엔드포인트에 전달
5. Authorization Server가 검증 후 Access Token 등을 발급
6. Client가 Access Token으로 Resource Server의 API를 호출
7. Resource Server가 토큰과 접근 권한을 검증한 후 리소스를 반환

**Authorization Code는 Access Token 자체가 아니라 토큰을 발급받기 위한 일회성 코드**

### PKCE, State, Redirect URI

보안 관련 개념

| 개념 | 역할 |
| --- | --- |
| PKCE | Authorization Code를 탈취한 제3자가 토큰으로 교환하는 것을 방지 |
| `state` | 인증 요청과 콜백을 연결하고 로그인 과정의 CSRF 등을 방어 |
| Redirect URI | 인증 완료 후 돌아올 Client 주소 |
| Scope | Client에 위임할 접근 권한의 범위 |
- PKCE는 Client가 생성한 `code_verifier`와 이를 변환한 `code_challenge`를 이용
- 토큰을 발급받을 때 최초 요청을 시작한 Client인지 확인하는 역할을 함
- 실무에서는 Authorization Code Flow와 PKCE 조합을 중심으로 이해하면 됨
- Redirect URI도 사전에 등록되니 주소와 엄격하게 검증해야 함

### 주요 OAuth 2.0 방식

| 방식 | 활용 목적 | 실무 권장 여부 |
| --- | --- | --- |
| Authorization Code + PKCE | 사용자 기반 권한 위임 | 권장 |
| Client Credentials | 서버 간 통신 | 적합한 환경에서 사용 |
| Refresh Token Grant | Access Token 갱신 | 필요에 따라 사용 |
| Implicit Grant | 브라우저에 Access Token 직접 전달 | 일반적으로 비권장 |
| Password Grant | Client가 사용자 비밀번호 직접 수집 | 사용하지 않아야 함 |
- Client Credentials 방식에서는 일반적으로 개별 사용자가 아닌 Client 자체의 권한으로 API를 호출

## 10. OIDC (OpenID Connect)

### OIDC

> OAuth 2.0을 기반으로 사용자 인증 기능을 제공하는 표준 프로토콜
>

OAuth 2.0 만으로는 Client가 사용자의 인증 결과와 신원을 표준화된 방법으로 확인할 수 없음

OIDC는 이를 위해 ID Token과 사용자 정보 조회 등의 기능을 정의

| 구분  | OAuth 2.0 | OIDC |
| --- | --- | --- |
| 주요 목적 | 접근 권한 위임 | 사용자 인증 |
| 핵심 질문 | 어떤 리소스에 접근할 수 있는가? | 로그인한 사용자는 누구인가? |
| 핵심 토큰 | Access Token | ID Token |
| 대표 사례 | 외부 서비스 API 접근 | Google 계정을 이용한 로그인 |

### ID Token과 Access Token

| 구분 | ID Token | Access Token |
| --- | --- | --- |
| 목적 | 사용자 인증 결과 전달 | 보호된 API 접근 |
| 주요 사용 대상 | Client | Resource Server |
| 주요 정보 | 사용자 식별자, 발급자, 인증 관련 정보 | 접근 범위 및 권한 정보 등 |
| JWT 사용 여부 | JWT 형식 | JWT 또는 다른 형식 |
- ID Token은 Client가 사용자의 인증 결과를 확인하기 위한 것이므로 Access Token을 대신하여 일반적인 리소스 API 호출에 사용하면 안 됨
- OIDC에서 `nonce`는 인증 요청과 ID Token을 연결하고 토큰 재사용 공격을 방어하는 데 활용

### OAuth, OIDC, JWT의 관계

#### OIDC → 사용자 인증 프로토콜

- OAuth 2.0 → OIDC의 기반이 되는 인가 프레임워크

#### JWT → 위 프로토콜에서 활용할 수 있는 형식

- ID Token → JWT 형식
- Access Token → JWT 또는 다른 형식

### 소셜 로그인과 자체 JWT

1. **사용자 → 외부 계정을 이용한 로그인 요청**
2. **외부 OAuth/OIDC Provider → 사용자 인증 및 인증 관련 제공**
3. **Financial API Defense Lab → 외부 사용자와 내부 사용자 계정 매핑**
4. **서비스 자체 JWT 발근(RS256) → sub, principal_type 등 내부 사용자 정보 포함**
5. **HttpOnly Cookie 전달**
6. **이후 API 요청 → (자체 JWT 검증 → 사용자 식별 → 객체 단위 인가)**
- 외부 인증 Provider가 발급한 토큰과 애플리케이션 자체적으로 발급한 JWT는 서로 목적이 다름
- 외부 인증 결과를 이용하여 내부 사용자를 식별한 이후에는 서비스 자체의 인증 정책과 접근 제어 정책을 적용할 수 있음
- 이 구조에서 API 요청마다 외부 Provider에 사용자 인증을 다시 요청할 필요는 없음

## 11. 접근 제어 모델 (Access Control Model)

어떤 기준으로 접근 권한을 판단할 것인지 결정해야 함

### 종류

| 모델 | 전체 명칭 | 권한 판단 기준 | 활용 사례 |
| --- | --- | --- | --- |
| DAC | Discretionary Access Control | 객체 소유자의 권한 설정 | 파일 공유 |
| MAC | Mandatory Access Control | 시스템이 강제하는 보안 정책 | 군사 및 기밀 시스템 |
| RBAC | Role-Based Access Control | 사용자의 역할 | 관리자, 일반 사용자 |
| ABAC | Attribute-Based Aeess Control | 사용자, 리소스, 환경의 속성 | 부서, 접근 시간, 데이터 등급 |
| ReBAC | Relationship-Based Access Control | 사용자와 객체 사이의 관계 | 소유권, 조직 소속, 공유 권한 |

### RBAC (역할 기반 접근 제어)

사용자에게 역할을 부여하고 해당 역할에 정의된 권한을 사용할 수 있도록 하는 방식

!download.svg

Spring Security의 대표적인 구현 방식

```java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long userId) {
    // 사용자 삭제
}
```

- RBAC는 기능 단위 접근 제어에 효과적
- 그러나 A와 B 모두 CUSTOMER 역할을 가지고 있다면 역할만으로는 어느 계좌가 본인 소유인지 판단할 수 없음
- **객체 소유권이나 별도의 관계 및 속성 검증이 필요함**

### ABAC (속성 기반 접근 제어)

사용자, 리소스, 요청 행위, 환경 등의 속성을 기반으로 접근 권한을 판단하는 방식

| 속성 종류 | 예시 |
| --- | --- |
| Subject | 사용자 ID, 부서, 직급 |
| Resource | 계좌 소유자 ID, 문서 보안 등급 |
| Action | READ, UPDATE, DELETE |
| Enviroment | 접근 시간, 접속 위치 |

```java
허용 조건:
- 사용자의 부서가 재무팀이고
- 문서 보안 등급이 INTERNAL이며
- 요청 행위가 READ이고
- 접근 시간이 업무 시간인 경우
```

- 객체의 소유자 ID와 요청자의 ID를 비교하는 정책도 속성 기반으로 표현할 수 있음
- RBAC보다 세밀한 정책을 구성할 수 있지만 조건이 복잡해질수록 정책 관리와 검증이 어려워질 수 있음

### ReBAC (관계 기반 접근 제어)

사용자와 리소스 사이에 어떤 관계가 존재하는지를 기반으로 접근 권한을 판단하는 방식

!download.svg

```java
customer:A → owner → account:1001
partner:B  → transaction_reader → account:1001
customer:C → owner → account:1002
```

인가 정책

```java
계좌정보 조회:
    owner 관계가 존재하는 경우 허용

거래내역 조회:
    owner 또는 transaction_reader 관계가
    존재하는 경우 허용
```

- 역할 기반으로 표현하기 어려운 객체별 소유권, 공유 권한, 조직 계층 등의 관계를 표현하는 데 적합

### RBAC, ABAC, ReBAC 비교

| 구분 | RBAC | ABAC | ReBAC |
| --- | --- | --- | --- |
| 판단 기준 | 역할 | 속성 | 관계 |
| 핵심 질문 | 어떤 역할인가? | 어떤 조건을 만족하는가? | 객체와 어떤 관계인가? |
| 장점 | 단순한 권한 관리 | 유연하고 세밀한 정책 | 객체별 권한 표현 |
| 단점 | 복잡한 권한에서 역할 증가 | 정책 복잡도 증가 | 관계 모델 및 데이터 관리 필요 |
| 금융 예시 | 관리자 API | 고객 ID 및 계좌 소유자 비교 | 제휴가 거래내역 접근 위임 |
- 세 모델은 상호 배타적이지 않으며 함께 사용할 수 있음
- OWASP에서도 복잡한 애플리케이션의 접근 제어를 설계할 때 ABAC와 ReBAC를 고려하도록 권고
- 현재 프로젝트는 고객과 제휴사를 구분하는 접근 주체 유형과 계좌 소유권 및 위임 관계를 함께 사용
- 전용 ReBAC 엔진을 사용하지 않고 PostgreSQL과 MyBatis로 이러한 인가 정책을 구현

## 13. Spring Security 인증 및 인가 처리 흐름

### Spring Security

> Spring 기반 애플리케이션에서 인증, 인가 및 주요 웹 보안 기능을 제공하는 프레임워크
>
- 사용자 인증
- URL 접근 제어
- 메서드 접근 제어
- CSRF 보호
- SecurityContext 관리
- OAuth 2.0 및 JWT 지원 등

### 주요 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| DelegatingFilterProxy | Servlet Container와 Spring Security 연결 |
| FilterChainProxy | 요청에 적용할 SecurityFilterChain 선택 |
| SecurityFilterChain | 요청에 적용할 보안 필터 구성 |
| AuthenticationManager | 인증 처리 요청 |
| AuthenticationProvider | 실제 인증 수행 |
| SecuriryContext | 현재 인증 정보 보관 |
| SecurityContextHolder | 현재 실행 흐름에서 SecurityContext 관리 |
| AuthorizationManager | 접근 허용 여부 판단 |
| AuthenticationEntryPoint | 인증이 필요한 요청에 대한 응답 처리 |
| AccessDeniedHandler | 권한이 부족한 요청에 대한 응답 처리 |

### JWT 기반 API 요청 처리 흐름

1. **HTTP Request**
2. **DelegatingFilterProxy**
    1. Spring Security로 요청 전달
3. **FilterChainProxy**
    1. 요청에 맞는 SecurityFilterChain 선택
4. **SecurityFIlterChain**
    1. SecurityContextHolderFilter
        1. SecurityContext 준비
    2. BearerTokenAuthenticationFilter

### SecurityContext와 Session의 차이

`SecurityContext`는 현재 실행 흐름에서 사용할 인증 정보를 보관

```java
Authentication authentication =
    SecurityContextHolder.getContext()
        .getAuthentication();
```

| 정보 | 의미 |
| --- | --- |
| Principal | 인증된 접근 주체 |
| Credentials | 인증에 사용된 자격 증명 |
| Authorities | 부여된 역할 및 권한 |
| Authenticated | 인증된 상태인지 여부 |
- Spring MVC 환경에서는 일반적으로 ThreadLocal을 이용해 현재 요청을 처리하는 스레드에서 인증 정보에 접근할 수 있도록 함
- Stateless JWT 인증에서도 `SecurityContext`는 사용함. 차이는 해당 인증 정보를 다음 요청까지 HTTP Session에 저장하지 않고 요청마다 토큰을 검증하여 구성한다는 것
- **즉, SecurityContext가 존재한다는 사실은 세션 기반 인증을 사용한다는 의미가 아님**

### SecurityFilterChain 설정 예시

```java
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http)
        throws Exception {

    http
        .sessionManagement(session -> session
            .sessionCreationPolicy(
                SessionCreationPolicy.STATELESS
            )
        )
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/public/**").permitAll()
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .requestMatchers("/api/**").authenticated()
            .anyRequest().denyAll()
        )
        .oauth2ResourceServer(oauth2 -> oauth2
            .jwt(Customizer.withDefaults())
        );

    return http.build();
}
```

- `STATELESS`: Spring Security가 HTTP Session을 이용해 인증 상태를 유지하지 않음
- `permitAll()`: 인증 없이 접근 허용
- `hasRole()`: 특정 역할 보유 여부 검증
- `authenticated()`: 인증되니 접근 주체만 허용
- `denyAll()`: 접근 거부
- `oauth2ResourceServer.jwt()`: JWT 기반 Resource Server 인증 구성

### Stateless와 OAuth 로그인

- `SessionCreationPolicy.STATELESS`는 Spring Security가 HTTP Session을 인증 상태 유지에 사용하지 않도록 하는 설정
- 애플리케이션의 다른 기능이 HTTP Session을 생성하는 것까지 무조건 차단하는 설정은 아님
- Spring Security의 OAuth 로그인 과정에서는 기본적으로 `HttpSessionOAuth2AuthorizationRequestRepository`를 통해 인증 요청 정보를 임시 저장할 수 있음

| 구분 | 상태 관리 |
| --- | --- |
| OAuth 로그인 과정 | Authorization Request, State 등의 임시 상태 관리 |
| 로그인 이후 API 요청 | 자체 JWT를 매번 검증하는 Stateless 인증 |
- **완전히 HTTP Session을 사용하지 않는 구조를 목표로 한다면 OAuth 로그인 과정의 임시 상태 저장 방식도 확인해야 함**

### Spring Security와 객체 단위 인가

```java
.requestMatchers("/api/accounts/**").authenticated()
```

- 이 설정은 인증된 사용자만 계좌 관련 PAI를 호출
- 소유자가 누구인지까지 확인하지는 않음

```java
GET /api/accounts/1001
```

- 객체 단위 인가를 별도로 구현해야 함

```java
@PreAuthorize(
    "@accountAuthorization.canRead(authentication, #accountId)"
)
public Account getAccount(Long accountId) {
    // 계좌 조회
}
```

- 또는 데이터 조회 조건에 접근 권한을 포함할 수 있음

```java
SELECT id, bank_name, balance
FROM accounts
WHERE id = #{accountId}
  AND customer_id = #{customerId}
```

## 14. HTTP 상태 코드와 접근 제어

| 상태 코드 | 의미 | 발생 사례 |
| --- | --- | --- |
| 400 Bad Request | 잘못된 요청 | 계좌 ID 형식 오류 |
| 401 Unauthorized | 유효한 인증 정보 없음 | JWT 누락, 만료, 서명 오류 |
| 403 Forbidden | 요청에 대한 접근 거부 | 관리자 권한 부족 |
| 404 Not Found | 리소스가 없거나 존재 여부를 공개하지 않음 | 존재하지 않는 계좌 또는 접근 불가 계좌 |
| 503 Server Unavailable | 일시적으로 요청 처리 불가 | 필수 인가/감사 기능 장애로 요청 처리 중단 |

일반적인 Bearer Token 기반 API 예시

```java
JWT 없음           → 401
JWT 만료           → 401
JWT 서명 검증 실패 → 401
JWT 유효, 권한 부족 → 403
```

### 인가 실패 시 404 반환 이유

| 요청 대상 | 응답 |
| --- | --- |
| 존재하지 않는 계좌 | 404 |
| 존재하지만 접근 권한이 없는 계좌 | 403 |
| 접근 권한이 있는 계좌 | 200 |
- 403과 404를 구분하면 접근 권한이 없는 사용자도 특정 계좌의 존재 여부를 알아낼 수 있음
- 이를 방지하기 위해 동일한 404 응답을 반환하는 정책 사용
- 내부 감사 로그에서는 객체 미존재와 권한 부족을 구분하여 기록할 수 있음

## 15. Keycloak과 OpenFGA

### Keycloak

> 오픈소스 IAM(Identity and Access Management) 솔루션

사용자 인증, 사용자 관리, SSO, OAuth 2.0, OIDC, 토큰 발급 및 역할 관리 등의 기능을 제공
>

개별 백엔드 서비스마다 로그인 기능을 직접 구현하는 대신 인증 관련 기능을 중앙화할 수 있음

### OpenFGA

> 세분화된 접근 제어(Fine-Grained Authorization)를 구현하기 위한 오픈소스 인가 솔루션

사용자와 객체 사이의 관계를 관리하고 특정 사용자가 해당 객체에 접근할 수 있는지를 판단
>

```java
{
  "user": "partner:B",
  "relation": "can_read_transactions",
  "object": "account:1001"
}
```

```java
{
  "allowed": true
}
```
