# 분산 시스템에서의 일관성 모델 (Consistency Model)

분산 환경에서 여러 노드 간 데이터가 얼마나 동일하게 유지되는지를 정의한 규칙

가용성과 성능을 유지하면서도 데이터 정합성을 어느 수준까지 보장할지 결정하기 위한 핵심 아키텍처 설계 지침

---

## 1. 배경: CAP 이론과 트레이드오프

분산 시스템 설계 시 **일관성(Consistency)**, **가용성(Availability)**, **분할 내성(Partition Tolerance)** 이라는 세 가지 가치 중 동시에 두 가지만 선택할 수 있다는 이론

*   **CP 시스템**: 네트워크 분할 시 가용성을 포기하고 일관성을 선택 (예: 분산 DB의 쓰기 작업)
*   **AP 시스템**: 네트워크 분할 시 일관성을 포기하고 가용성을 선택 (예: 카산드라, 대부분의 웹 서비스)

---

## 2. 주요 일관성 모델

### 1) 강한 일관성 (Strong Consistency)
*   **정의**: 모든 노드가 항상 동일한 최신 데이터를 반환함. 데이터 쓰기가 완료되기 전까지 모든 읽기 요청을 차단하여 불일치를 방지함
*   **실무 예시**: 금융 시스템의 계좌 잔액 조회, 결제 처리 등
*   **특징**: 정합성은 완벽하지만 응답 지연(Latency)이 크고 가용성이 떨어짐

### 2) 최종적 일관성 (Eventual Consistency)
*   **정의**: 즉시 일치하지는 않더라도, 시간이 지나면 결국 모든 노드의 데이터가 일치하게 됨
*   **실무 예시**: SNS의 '좋아요' 수, 쇼핑몰의 추천 상품 목록, 대규모 트래픽의 통계 데이터
*   **특징**: 응답 속도가 빠르고 가용성이 높지만, 사용자마다 일시적으로 다른 데이터를 볼 수 있음

### 3) 인과적 일관성 (Causal Consistency)
*   **정의**: 원인과 결과 관계가 있는 작업의 순서는 엄격히 보장하고, 관련 없는 작업은 순서를 따지지 않음
*   **실무 예시**: SNS 댓글 시스템 (A의 댓글에 대한 B의 답글은 항상 A의 댓글 뒤에 보임)

## 3. 실무 예시 및 코드: 최종적 일관성 처리 전략

실무에서 `Eventual Consistency`를 채택했을 때 발생하는 데이터 불일치 문제를 백엔드에서 해결하는 방법

### 1) 메시지 큐를 활용한 비동기 정합성 맞추기
주문 생성과 재고 차감을 하나의 트랜잭션으로 묶지 않고 이벤트를 통해 처리함

```java
// 주문 서비스 (OrderService)
@Transactional
public void createOrder(OrderRequest request) {
    Order order = orderRepository.save(new Order(request));
    
    // 이 시점에서 재고 서비스의 DB는 아직 반영되지 않음 (일시적 불일치)
    eventPublisher.publish(new OrderCreatedEvent(order.getId(), order.getProductId()));
}

// 재고 서비스 (InventoryService)
@Transactional
public void onOrderCreated(OrderCreatedEvent event) {
    // 메시지를 컨슘하여 결국(Eventual) 재고를 차감함
    inventoryRepository.decreaseStock(event.getProductId());
}
```

### 2) 보상 트랜잭션 (Saga 패턴)
최종적 일관성을 유지하다가 특정 단계에서 실패할 경우, 이미 성공한 작업을 취소하는 로직을 수행함

```java
// 결제 실패 시 주문을 취소하는 보상 로직
public void onPaymentFailed(PaymentFailedEvent event) {
    Order order = orderRepository.findById(event.getOrderId());
    order.cancel(); // 이미 '성공' 처리되었던 주문을 다시 '취소' 상태로 변경
}
```

## 4. 백엔드 설계 가이드

1.  **비즈니스 성격에 따른 분리**:
    *   **강한 일관성 영역**: 결제, 포인트 차감, 정산, 회원 탈퇴
    *   **최종적 일관성 영역**: 조회수, 댓글 수, 사용자 선호도, 알림 발송
2.  **멱등성(Idempotency) 보장**: 네트워크 재시도로 인해 동일한 이벤트가 여러 번 올 수 있으므로, 항상 같은 결과를 내도록 설계해야 함
3.  **데이터 보정 도구**: 정기적인 배치(Batch) 작업을 돌려 불일치된 데이터를 강제로 동기화하는 'Anti-entropy' 프로세스를 구축하는 경우가 많음

---

### 요약 가이드

| 구분 | 강한 일관성 (Strong) | 최종적 일관성 (Eventual) |
| :--- | :--- | :--- |
| **정합성** | 최상 | 일시적 불일치 허용 |
| **가용성** | 낮음 (장애 시 서비스 중단) | 최상 (네트워크 장애에도 응답) |
| **복잡도** | 상대적으로 낮음 (DB가 해결) | 높음 (애플리케이션에서 보정 필요) |
| **추천 상황** | 자산 관리, 데이터 무결성 필수 | 대규모 트래픽, 사용자 경험(속도) 중시 |

### 결론
> **분산 시스템에서의 일관성은 "기술적 한계(CAP)"와 "사용자 경험" 사이의 타협점.**
> 백엔드 개발자는 무조건적인 강한 일관성보다는, 서비스의 성격에 맞춰 유연하게 모델을 선택하고 그로 인해 발생하는 예외 상황을 설계로 풀어낼 줄 알아야 함
