# 레이어드 아키텍처 (Layered Architecture)

소프트웨어를 시스템의 **관심사(Concern)** 에 따라 계층별로 나누어 수직적으로 배열한 가장 보편적인 아키텍처 패턴

---

## 1. 계층별 역할 (Spring Boot 기준)

일반적으로 3계층 또는 4계층으로 구성하며, 상위 계층은 인접한 하위 계층에만 의존하는 **단방향 의존성**을 가짐

### 1) 표현 계층 (Presentation Layer / Controller)
*   **역할**: 사용자의 요청(HTTP Request)을 받고, 응답(HTTP Response)을 반환함
*   **주요 작업**: 파라미터 유효성 검증(Validation), 데이터 포맷팅(JSON 변환), 결과 반환

### 2) 서비스 계층 (Service Layer / Business Layer)
*   **역할**: 비즈니스 로직을 수행하며, 여러 데이터 계층의 작업을 하나의 트랜잭션으로 묶음
*   **주요 작업**: 정책 검증, 데이터 가공, 트랜잭션(@Transactional) 관리

### 3) 데이터 계층 (Data Access Layer / Repository)
*   **역할**: 데이터베이스나 외부 저장소와의 통신을 전담함
*   **주요 작업**: CRUD 연산, 데이터 영속화

---

## 2. 실무 예시: "상품 주문 처리" 시나리오

레이어드 아키텍처에서 주문 요청이 들어오면 각 계층은 다음과 같이 움직임

1.  **Controller (표현)**: 사용자의 주문 요청(상품 ID, 수량)을 받고, 데이터가 형식에 맞는지 검사함
2.  **Service (서비스)**:
    *   상품의 재고가 충분한지 비즈니스 규칙을 확인함
    *   사용자의 등급에 따른 할인 혜택을 계산함
    *   주문 정보를 생성하고 결제 요청을 수행함 (트랜잭션 시작)
3.  **Repository (데이터)**:
    *   `ProductRepository`를 통해 재고 정보를 DB에서 읽어옴
    *   `OrderRepository`를 통해 주문 정보를 DB에 저장함 (트랜잭션 종료/커밋)

## 3. 싱크홀 안티 패턴 (Architecture Sinkhole Anti-Pattern)

상위 레이어가 하위 레이어의 작업을 단순히 전달만 하고, **중간 레이어(주로 Service)에서 아무런 비즈니스 로직도 수행하지 않는 경우**

*   **문제**: 불필요한 위임 코드(Delegate)를 작성해야 하며, 자원 소모와 코드 복잡성을 증가시킴
*   **실무 예시**: 단순히 ID로 엔티티를 하나 조회하는 기능인데, Controller -> Service -> Repository를 모두 거쳐야 함

```java
// Service에서 하는 일이 단순 위임뿐인 경우
@Service
public class OrderService {
    private final OrderRepository orderRepository;

    public Order getOrder(Long id) {
        // 비즈니스 로직 없이 단순히 Repository 호출만 함
        return orderRepository.findById(id).orElseThrow();
    }
}
```

### 실무적 트레이드오프 (Trade-off)
*   싱크홀 패턴을 피하기 위해 Controller에서 직접 Repository를 부르는 방식을 허용할 수도 있습니다. 하지만 이는 **"계층 분리"라는 일관성을 깨뜨리게 됨** 
*   프로젝트 규모가 커질수록 "어떤 건 Service를 거치고 어떤 건 안 거치나?"라는 혼란이 생길 수 있으므로, 성능이 매우 중요한 지점이 아니라면 일관성을 위해 모든 요청이 계층을 순서대로 통과하도록 규칙을 정하는 경우가 많음

---

## 4. 장점과 단점

### 장점
1.  **관심사 분리**: 각 계층은 자신의 역할에만 집중함
2.  **테스트 용이성**: 하위 계층을 모킹(Mocking)하여 특정 레이어만 독립적으로 테스트할 수 있음
3.  **유지보수성**: DB 기술이 바뀌면 데이터 계층만 수정하면 됨

### 단점
1.  **유연성 부족**: 계층을 엄격히 지키다 보면 코드량이 많아지고 개발 속도가 늦어질 수 있음
2.  **성능 오버헤드**: 단순한 작업도 여러 계층을 통과하며 데이터 변환(DTO <-> Entity)이 발생함

### 요약
> **레이어드 아키텍처는 "단순함"과 "일관성"이 가장 큰 무기임.**
> 대규모 팀 개발에서 코드의 위치를 예측 가능하게 해주며, 계층 간의 책임을 명확히 함으로써 코드의 품질을 일정 수준 이상으로 유지할 수 있게 도와줌
