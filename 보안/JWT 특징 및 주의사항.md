# JWT (JSON Web Token) 특징 및 주의사항

JSON 포맷을 사용하여 사용자의 정보를 안전하게 전송하기 위한 **자가 수용적(Self-contained)** 인 토큰 방식

---

## 1. JWT의 구조

JWT는 점(`.`)으로 구분된 세 부분으로 구성됨

### 1) Header (헤더)
*   **내용**: 토큰의 타입(JWT)과 사용할 암호화 알고리즘(HS256, RS256 등)을 정의
*   **예**: `{"alg": "HS256", "typ": "JWT"}`

### 2) Payload (페이로드)
*   **내용**: 토큰에 담을 정보(**Claim**)가 들어있음. 사용자 ID, 이름, 권한, 만료 시간(`exp`) 등이 포함됨
*   **주의**: 단순히 **Base64로 인코딩**된 것이므로 누구나 디코딩하여 내용을 볼 수 있음. **민감한 정보(비밀번호, 주민번호 등)는 절대 담으면 안 됨**

### 3) Signature (서명)
*   **내용**: 헤더와 페이로드를 서버만 알고 있는 **비밀 키(Secret Key)** 로 암호화한 값
*   **역할**: 토큰이 도중에 변조되지 않았음을 증명함. 서버는 수신한 토큰의 헤더와 페이로드를 다시 암호화하여 서명 값과 일치하는지 확인함

---

## 2. JWT의 주요 특징 및 장점

### 1) 무상태성 (Stateless)
*   서버는 사용자의 세션 상태를 저장할 필요가 없음. 토큰 자체가 정보를 들고 있기 때문에, 어떤 서버로 요청이 가더라도 검증이 가능함 (Scale-out에 유리)

### 2) 자가 수용적 (Self-contained)
*   토큰 안에 사용자 정보와 권한이 포함되어 있어, DB를 매번 조회하지 않고도 즉시 인가(Authorization) 처리가 가능함

### 3) 플랫폼 독립성
*   HTTP 헤더에 담아 보내기 때문에 웹, 모바일 앱, 외부 서비스 간의 통신에서 표준화된 방식으로 사용하기 편리함

---

## 3. 실무 적용 시 주의사항 및 보안 대책

### 1) 페이로드 노출 주의
JWT는 암호화가 아닌 **인코딩** 방식
*   **실무 예시**: 브라우저 개발자 도구에서 JWT를 복사해 `jwt.io` 사이트에 붙여넣으면 사용자의 이메일이나 PK 값을 바로 확인할 수 있음. 중요한 비즈니스 정보는 담으면 안 됨

### 2) 토큰 탈취 대응 (Access & Refresh Token)
JWT는 한 번 발급되면 서버에서 강제로 만료시키기 어려움
*   **해결책**:
    *   **Access Token**: 만료 시간을 매우 짧게(15분~1시간) 설정하여 탈취 시 피해를 최소화 함
    *   **Refresh Token**: 만료 시간을 길게(1~2주) 설정하고 서버(DB/Redis)에 저장하여 Access Token 재발급 시에만 사용함
    *   **RT Rotation**: Access Token 재발급 시 Refresh Token도 새로 발급하여 보안을 강화함

### 3) 시크릿 키(Secret Key) 관리
시크릿 키가 유출되면 누구나 서버인 척 토큰을 위조할 수 있음
*   **관리**: 하드코딩하지 말고 환경변수나 AWS Secrets Manager 같은 안전한 곳에 보관. 키의 복잡도가 낮으면 무차별 대입 공격(Brute-force)에 뚫릴 수 있으므로 충분히 길고 복잡하게 설정해야 함

### 4) 사용자 경험과 슬라이딩 세션 (Sliding Session)
*   **문제**: 글을 작성 중인데 갑자기 토큰이 만료되어 로그아웃되면 작업 내용이 날아갈 수 있음
*   **해결**: 사용자가 활동 중일 때(API 호출 시) 만료 시간이 얼마 남지 않았다면 자동으로 토큰을 갱신해주는 **슬라이딩 세션** 전략을 고려해야 함

### 5) 'none' 알고리즘 공격 방어
*   일부 취약한 라이브러리는 헤더의 `alg`를 `none`으로 설정하면 서명 검증을 건너뛰는 버그가 있었음. 항상 최신 라이브러리를 사용하고, 서버에서 허용하지 않는 알고리즘은 거부하도록 설정해야 함

---

## 4. 결론: 세션 vs JWT 선택 기준

| 구분 | 세션 (Session) | JWT |
| :--- | :--- | :--- |
| **로그아웃** | 즉시 가능 (서버에서 삭제) | 어려움 (만료 대기 필요) |
| **서버 부하** | 메모리/DB 점유 발생 | 연산 부하 발생 (서버 무상태) |
| **적합한 환경** | 단일 서버, 강력한 보안 필요 | MSA, 모바일 앱, 확장성 중시 |

### 요약
> **JWT는 서버의 확장성을 높여주지만, 한 번 발급되면 통제가 어렵다는 양날의 검을 가지고 있음.**
> 반드시 짧은 만료 시간과 리프레시 토큰 전략을 병행하고, 페이로드에는 공개되어도 무방한 최소한의 정보만 담는 것이 실무의 핵심
