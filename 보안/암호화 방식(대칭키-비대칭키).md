# 암호화 방식 (대칭키 vs 비대칭키)

데이터를 안전하게 전송하고 저장하기 위해 평문을 암호문으로 바꾸는 **암호화(Encryption)** 와 이를 다시 읽을 수 있게 복구하는 **복호화(Decryption)** 방식의 차이를 설명함

---

## 1. 대칭키 암호화 (Symmetric Key Encryption)
암호화와 복호화에 **동일한 하나의 키**를 사용하는 방식

*   **특징**: 계산 속도가 매우 빠르고 대용량 데이터를 처리하기에 적합함
*   **단점**: **키 배송 문제(Key Distribution Problem)** 가 있음. 상대방에게 키를 전달하는 과정에서 탈취당하면 보안이 완전히 무너짐
*   **대표 알고리즘**: AES (Advanced Encryption Standard), ChaCha20 등
*   **실무 예시**: 로컬 파일 암호화, 데이터베이스 필드 암호화

---

## 2. 비대칭키 암호화 (Asymmetric Key Encryption)
암호화와 복호화에 **서로 다른 두 개의 키(공개키, 개인키)** 를 사용하는 방식

*   **공개키 (Public Key)**: 누구나 알 수 있도록 공개된 키. 주로 **데이터 암호화**에 사용됨
*   **개인키 (Private Key)**: 소유자만이 가지고 있는 비밀 키. 주로 **데이터 복호화**에 사용됨
*   **동작**: 공개키로 암호화한 데이터는 오직 그와 쌍을 이루는 개인키로만 풀 수 있음
*   **장점**: 키를 공개해도 복호화는 불가능하므로 키 배송 문제가 발생하지 않음
*   **단점**: 복잡한 수학적 연산이 필요하여 대칭키 방식보다 속도가 현저히 느림
*   **대표 알고리즘**: RSA, ECC (Elliptic Curve Cryptography)
*   **실무 예시**: 전자 서명, SSH 접속, SSL/TLS 초기 인증

---

## 3. 혼합 암호화 방식 (Hybrid Encryption)
대칭키의 **속도**와 비대칭키의 **보안성**을 결합하여 실무에서 가장 널리 쓰이는 방식

### 동작 흐름 (HTTPS/TLS 예시)
1.  **비대칭키 활용**: 클라이언트는 서버의 공개키를 얻고, 이를 이용해 통신에 사용할 **임시 대칭키(세션키)** 를 암호화하여 서버에 보냄
2.  **안전한 키 공유**: 서버는 자신의 개인키로 이를 복호화하여 임시 대칭키를 안전하게 획득함 (키 배송 문제 해결)
3.  **대칭키 활용**: 이제 양측 모두 동일한 대칭키를 가지고 있으므로, 이후의 실제 데이터 통신은 이 **대칭키를 사용하여 빠르게 수행**함 (속도 문제 해결)

---

## 4. 실무 적용 가이드

### 상황별 암호화 선택
| 구분 | 대칭키 (AES 등) | 비대칭키 (RSA 등) |
| :--- | :--- | :--- |
| **속도** | 매우 빠름 | 느림 |
| **보안** | 키 관리 어려움 (탈취 위험) | **매우 안전** (개인키만 보호) |
| **용도** | 대량의 실시간 데이터 통신 | 초기 인증, 키 교환, 전자 서명 |

### 개발 시 주의사항
*   **HTTPS 사용**: 웹 통신은 기본적으로 TLS(혼합 암호화)를 통해 보호되어야 함
*   **개인키 관리**: 비대칭키 방식에서 개인키(`*.pem`, `*.key`)가 유출되면 해당 서버의 모든 보안이 무효화됨. 절대 Git에 올리지 말고 안전한 인프라(Vault, KMS 등)에서 관리
*   **키 길이**: 알고리즘 성능이 좋아짐에 따라 RSA는 2048비트 이상, AES는 256비트 사용을 권장함

### 요약
> **대칭키는 "빠른 속도"를 위해, 비대칭키는 "안전한 키 교환"을 위해 사용됨.**
> 현대의 보안 통신은 비대칭키로 안전하게 문을 열고(Handshake), 대칭키로 빠르게 짐을 나르는(Data Transfer) **혼합 방식**이 표준
