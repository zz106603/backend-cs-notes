# 페이지 교체 알고리즘 (Page Replacement Algorithm)

운영체제가 메모리를 효율적으로 관리하기 위해, **"꽉 찬 메모리에서 누구를 쫓아낼 것인가?"** 를 결정하는 전략

---

## 1. 왜 필요한가요? (실무 관점)

### 상황: 한정된 메모리, 무한한 욕망
*   **물리 메모리(RAM)** 는 16GB인데, 실행 중인 프로그램(게임, 브라우저, 카톡 등)이 요구하는 메모리 총합은 20GB
*   운영체제는 **가상 메모리(Virtual Memory)** 기법을 사용하여 당장 안 쓰는 데이터는 디스크(스왑 영역)로 내리고, 필요한 데이터만 RAM에 올림
*   이때 RAM이 꽉 찼다면, **누군가는 방을 빼줘야(Swap Out)** 새로운 데이터가 들어올 수 있음
*   **문제**: 만약 방금 막 사용한 데이터를 쫓아내면, 1초 뒤에 다시 필요해져서 또 불러와야 함. 이러면 디스크 I/O가 폭증하여 컴퓨터가 멈춘 것처럼 느려짐 (Thrashing)
*   **해결**: "앞으로 가장 안 쓸 것 같은 녀석"을 잘 골라내서 쫓아내야 시스템 성능이 유지됨. 이것이 페이지 교체 알고리즘의 목표

---

## 2. 주요 알고리즘 종류

### 1) FIFO (First In First Out)
*   **전략**: "가장 먼저 들어온 놈이 가장 먼저 나간다." (선착순)
*   **특징**: 구현이 매우 간단함. 큐(Queue) 하나만 있으면 됨.
*   **단점**: **오래되었지만 자주 쓰이는 데이터** (예: OS 핵심 커널 코드, 공통 라이브러리)를 쫓아낼 위험이 있음. 성능이 좋지 않아 실제로는 잘 안 씀

### 2) OPT (Optimal)
*   **전략**: "앞으로 가장 오랫동안 안 쓸 놈을 쫓아낸다."
*   **특징**: 이론상 가장 완벽한 알고리즘입. 페이지 부재(Page Fault) 횟수가 가장 적음
*   **단점**: **미래를 알 수 없음.** 실제 구현이 불가능하며, 다른 알고리즘 성능 평가의 기준(Benchmark)으로만 사용됨

### 3) LRU (Least Recently Used) - 실무 표준
*   **전략**: "**가장 오랫동안 사용하지 않은 놈**을 쫓아낸다."
*   **논리**: "최근에 안 썼으면, 앞으로도 안 쓰겠지?" (과거의 기록으로 미래를 예측)
*   **실무 예시**:
    *   **웹 브라우저 캐시**: 방문한 지 오래된 사이트의 이미지부터 삭제
    *   **Redis 캐시**: 메모리가 가득 차면 LRU 정책으로 오래된 키를 삭제
*   **단점**: 데이터를 접근할 때마다 시간을 기록해야 하므로 오버헤드가 있음

### 4) LFU (Least Frequently Used)
*   **전략**: "**사용 횟수가 가장 적은 놈**을 쫓아낸다."
*   **논리**: "많이 썼으면 앞으로도 많이 쓰겠지?"
*   **단점**:
    *   방금 막 들어온 데이터는 사용 횟수가 적어서 바로 쫓겨날 수 있음
    *   초반에만 반짝 많이 쓰고 이제 안 쓰는 데이터가 계속 메모리에 남아있을 수 있음 (과거의 영광 문제)

### 5) NUR (Not Used Recently) / Clock Algorithm
*   **전략**: LRU는 시간을 일일이 기록하기 힘드니까, **"최근에 썼니? (0/1)"** 비트 하나만 가지고 대충 LRU 흉내를 내자
*   **동작**: 시계바늘(Clock)이 돌면서 참조 비트가 0인 페이지를 찾으면 쫓아냄. 1이면 0으로 바꾸고 넘어감
*   **특징**: 적은 오버헤드로 LRU와 비슷한 성능을 내므로, **실제 운영체제에서 가장 많이 사용**되는 방식

---

## 3. 요약: 무엇을 쓰나요?

| 알고리즘 | 기준 | 장점 | 단점 |
| :--- | :--- | :--- | :--- |
| **FIFO** | 들어온 시간 | 간단함 | 성능 나쁨 (Belady의 모순) |
| **OPT** | 미래 사용 시간 | 이론상 최고 | 구현 불가능 |
| **LRU** | **마지막 참조 시간** | **가장 일반적** | 시간 기록 오버헤드 |
| **LFU** | 참조 횟수 | 빈도 반영 | 최근 데이터 보호 못함 |
| **NUR (Clock)** | **참조 비트 (0/1)** | **가성비 최고** | LRU보다 정교함은 떨어짐 |

> **결론**: 대부분의 OS는 **LRU**의 아이디어를 차용한 **NUR(Clock)** 알고리즘이나 그 변형을 사용하여 성능과 오버헤드 사이의 균형을 맞춤
