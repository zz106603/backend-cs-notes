### 동시성 문제: 경쟁 상태 (Race Condition) 해결

**경쟁 상태란?**
- 두 개 이상의 스레드가 **공유 자원(변수, 파일, DB 등)** 에 동시에 접근하여 읽거나 쓸 때, 실행 순서에 따라 결과가 엉망이 되는 현상
- 이를 해결하기 위해서는 **원자성(Atomicity)** 과 **가시성(Visibility)** 이 보장되어야 함

---

### 핵심 개념: 원자성과 가시성

#### 1. 원자성 (Atomicity)
- **정의:** 어떤 작업이 **더 이상 쪼개질 수 없는 하나의 단위**처럼 실행되는 성질. 작업 도중에 다른 스레드가 끼어들 수 없어야 함
- **문제 상황 예시 (카운터 증가):**
    - `count++` 코드는 한 줄이지만, 컴퓨터 내부(CPU)에서는 3단계로 실행됨
        1. **Read:** 메모리에서 `count` 값(예: 0)을 읽어온다.
        2. **Modify:** 읽어온 값에 1을 더한다. (0 + 1 = 1)
        3. **Write:** 계산된 값(1)을 다시 메모리에 저장한다.
    - **동시성 문제:** 스레드 A가 2번(더하기)을 하고 있을 때, 스레드 B가 끼어들어 1번(읽기)을 수행하면 둘 다 0을 읽어서 결과적으로 2가 아닌 1이 저장

#### 2. 가시성 (Visibility)
- **정의:** 한 스레드가 공유 변수의 값을 변경했을 때, **다른 스레드가 그 변경된 값을 즉시 볼 수 있어야** 하는 성질
- **문제 상황 예시 (CPU 캐시):**
    - 현대 CPU는 성능을 위해 메인 메모리(RAM)의 값을 **CPU 캐시(Cache)**에 복사해서 사용
    - 스레드 A가 값을 바꿔도 자기 캐시만 바꾸고 RAM에 늦게 반영하면, 스레드 B는 여전히 RAM에 있는 옛날 값을 읽게 됨

### Java에서의 해결 방법 및 예시

#### 1. synchronized 키워드 (가장 확실하지만 무거움)
- **특징:** 원자성과 가시성을 모두 보장. 한 번에 하나의 스레드만 해당 블록(임계 영역)에 들어갈 수 있게 잠금(Lock)을 검
- **예시:**
    ```java
    public class Counter {
        private int count = 0;
    
        // 한 번에 한 명만 들어오세요!
        public synchronized void increment() {
            count++; 
        }
    }
    ```

#### 2. Atomic 클래스 (가볍고 빠름)
- **특징:** **CAS(Compare-And-Swap)** 알고리즘을 사용하여 락(Lock) 없이 원자성을 보장. `synchronized`보다 성능이 좋음
- **CAS란?** "내가 읽었던 값이 여전히 그대로라면 변경하고, 누가 바꿨다면 다시 시도해!"라는 방식
- **예시:**
    ```java
    import java.util.concurrent.atomic.AtomicInteger;
    
    public class AtomicCounter {
        // int 대신 AtomicInteger 사용
        private AtomicInteger count = new AtomicInteger(0);
    
        public void increment() {
            // 내부적으로 CAS 알고리즘으로 안전하게 1 증가
            count.incrementAndGet(); 
        }
    }
    ```

#### 3. volatile 키워드 (가시성만 보장)
- **특징:** 변수를 CPU 캐시가 아닌 **메인 메모리(RAM)에서 직접 읽고 쓰도록** 강제
- **주의:** **원자성은 보장하지 않음.** 여러 스레드가 동시에 값을 쓰는 상황에서는 여전히 경쟁 상태가 발생
- **사용처:** 하나의 스레드만 값을 쓰고, 나머지 스레드는 값을 읽기만 하는 경우(예: Flag 변수)에 적합
- **예시:**
    ```java
    public class FlagExample {
        // 모든 스레드가 항상 최신 값을 보장받음
        private volatile boolean isRunning = true;
    
        public void stop() {
            isRunning = false;
        }
    }
    ```

### 요약: 언제 무엇을 써야 할까?

| 상황 | 해결 방법 | 설명 |
| :--- | :--- | :--- |
| **단순 카운터, 숫자 연산** | `AtomicInteger`, `AtomicLong` | 락 없이 빠르고 안전함 (CAS 사용) |
| **복잡한 로직 동기화** | `synchronized` | 코드 블록 전체를 안전하게 보호해야 할 때 |
| **단순 상태 플래그 (On/Off)** | `volatile` | 한 놈만 쓰고 나머지는 읽기만 할 때 (가시성 확보) |

### Q&A: synchronized vs @Transactional

**Q. synchronized와 @Transactional은 비슷한 개념인가요?**
- **X, 제어하는 대상과 범위가 완전히 다름**
- 둘 다 "동시성"과 관련이 있어 보이지만, 역할이 구분됨

**1. synchronized (Java 애플리케이션 레벨)**
- **대상:** 메모리 내의 객체나 메서드
- **역할:** 하나의 프로세스(JVM) 안에서 스레드끼리 순서를 정해줌
- **한계:** 서버가 여러 대(분산 환경)라면, 각 서버 안에서만 순서가 지켜질 뿐 서버끼리는 동시성 제어가 안 됨 (이때는 Redis 분산 락 등을 써야 함)

**2. @Transactional (데이터베이스 레벨)**
- **대상:** 데이터베이스의 트랜잭션
- **역할:** 작업의 완전성(ACID)을 보장. 작업 중 에러가 나면 **롤백(Rollback)** 해주는 것이 주 목적
- **동시성 제어:** DB의 격리 수준(Isolation Level)이나 락(Lock)을 통해 데이터의 정합성을 맞춤

**주의: 둘을 같이 쓸 때의 문제점**
- `@Transactional`은 AOP(프록시) 기반으로 동작
- `synchronized` 메서드에 `@Transactional`을 붙이면, **트랜잭션이 커밋되기 전에 락이 먼저 풀려버리는 문제**가 발생할 수 있음
- 락이 풀린 직후(아직 DB 커밋 전) 다른 스레드가 들어와서 변경 전 데이터를 읽어가면 동시성 처리가 실패할 수 있음
