# 하네스 엔지니어링 (Harness Engineering)

## 하네스 엔지니어링 (Harness Engineering)

### 개요

Harness Engineering은 **AI 에이전트가 주어진 작업을 안정적으로 수행할 수 있도록 실행 환경, 작업 규칙, 도구, 검증 절차, 피드백 구조를 설계하고 개선하는 엔지니어링 방식**

하네스는 AI 모델이 실제 작업을 수행할 수 있도록 주변에서 지원하는 실행 시스템을 의미

ex) LLM은 코드를 생성하거나 문제를 분석할 수 있지만, 모델 자체만으로는 프로젝트의 요구사항을 파악하고 파일을 수정하거나 테스트를 실행할 수 없음

이러한 작업을 수행하려면 프로젝트 정보를 제공하고 파일 시스템이나 터미널에 접근할 수 있는 도구와 실행 환경이 필요함. 또한 작업 결과가 올바른지 확인하는 검증 절차도 있어야 함

Harness Engineering은 이러한 요소를 구성하여 AI 에이전트가 일관된 기준에 따라 작업하도록 만드는 것

### 핵심 목적
- AI 에이전트가 작업에 필요한 정보를 정확하게 파악하도록 지원
- 반복되는 개발 작업의 수행 절차 표준화
- 테스트와 검증을 통해 잘못된 결과를 발견
- 작업 실패 원인을 분석하고 재발 방지 구조 마련
- 개발자의 반복적인 개입을 줄이면서 작업의 신뢰성 확보

## 필요 이유

### 일반적인 AI 개발 방식
```
좋아요 기능을 구현해 줘.
동시성 문제도 고려해서 작성해 줘.
```

Codex는 프로젝트 코드를 분석하고 기능을 구현할 수 있지만 문제가 있음

- 프로젝트에서 사용하는 기존 설계 패턴을 무시
- 동시성 문제가 있는데도 정상 구현으로 판단
- 테스트를 실행하지 않고 작업 완료를 보고
- 기존 API와의 호환성 문제를 확인하지 않음

이러한 문제가 발생하면 개발자가 추가 프롬프트로 수정과 검증을 반복해야 함

### 하네스 엔지니어링 적용

AI가 따를 규칙과 검증 환경을 미리 구성
```
사용자 요구사항
    ↓
프로젝트 규칙 및 구조 확인
    ↓
기능 구현
    ↓
빌드 및 테스트 실행
    ↓
코드 리뷰 및 문제 검토
    ↓
검증 실패 시 수정 후 재검증
    ↓
검증 결과 보고
```

- Codex가 기능 구현 후 테스트를 실행하도록 하고 실패하면 원인을 분석하게 할 수 있음
- 리뷰 Skill을 활용해 별도의 Subagent에게 코드 검토를 맡기고 발견된 문제를 수정한 뒤 다시 테스트하도록 구성할 수 있음

> **이러한 작업 절차를 매번 긴 프롬프트로 요청하는 것이 아니라 재사용 가능한 개발 환경과 규칙으로 구성한다는 것**

## Harness의 주요 구성 요소
하나의 파일이나 특정 기술을 의미하지 않음

AI 에이전트가 작업을 수행하는 데 필요한 여러 요소를 조합한 시스템

| 구성 요소 | 역할 | 예시 |
| --- | --- | --- |
| Context | 작업에 필요한 정보 제공 | AGENTS.md, 설계 문서 |
| Instruction | 공통 작업 규칙 정의 | 코딩 규칙, 작업 제한 |
| Tools | 외부 환경 및 기능에 접근 | 터미널, Git, MCP |
| Skills | 반복적인 작업 절차 재사용 | 코드 리뷰, 테스트 |
| Subagents | 특정 작업을 별도 에이전트에 위임 | 코드 리뷰 담당 |
| Environment | 코드 실행 및 검증 환경 제공 | Docker, Testcontainers |
| Validation | 작업 결과의 정확성 검증 | JUnit, CI, 정적 분석 |
| Feedback | 검증 결과를 다음 작업에 반영 | 오류 수정, 규칙 개선 |

모든 구성 요소가 반드시 필요한 것은 아님. 프로젝트 규모와 작업 목적에 따라 필요한 요소만 선택할 수 있음

### Context와 Instructions
- AI가 프로젝트를 이해하고 올바른 방향으로 작업하도록 정보를 제공
- Codex에서는 `AGENTS.md`에 공통 개발 규칙과 주요 문서의 위치를 작성할 수 있음
- 아키텍처나 데이터 모델과 같은 상세 정보는 별도의 문서로 관리하고 필요할 때 참고하도록 함

### Tools와 Environment
- AI가 실제 개발 작업을 수행할 수 있도록 지원
- Codex는 터미널을 통해 Gradle 테스트를 실행하고 Git으로 변경 사항을 확인할 수 있음
- MCP를 연결하면 외부 시스템이나 전문 도구에도 접근할 수 있음

### Validation과 Feedback
- AI가 생성한 결과가 요구사항을 충족하는지 확인하고 문제가 발견되면 개선하는 단계
- 코드 리뷰와 테스트를 통해 오류를 발견하는 것뿐 아니라 반복적으로 발생하는 문제를 프로젝트 규칙이나 자동 검사에 반영하는 과정까지 포함

> **중요한 것은 AI가 작업을 수행할 수 있는 환경과 그 결과를 검증할 수 있는 환경을 함께 제공하는 것**

## 핵심 원칙

### 1. 필요한 정보를 쉽게 찾을 수 있도록 구성
- AI가 프로젝트를 이해하려면 기술 스택, 아키텍처, 데이터 처리 흐름, 설계 결정 등을 파악할 수 있어야 함
- 모든 정보를 하나의 `AGENTS.md`에 작성하면 문서가 지나치게 길어지고 중요한 규칙을 구분하기 어려움
- `AGENTS.md`는 간결하게 유지하고 상세 내용은 별도 문서로 관리하는 것이 좋음
```
project/
├── AGENTS.md
├── docs/
│   ├── architecture.md
│   ├── database.md
│   └── development.md
├── src/
└── build.gradle
```
- OpenAI 실제 사례에서도 필요한 문서를 찾을 수 있는 진입점으로 사용함

### 2. 규칙은 가능한 한 자동으로 검증
- `AGENTS.md`에 규칙을 작성했다고 해서 AI가 반드시 지키는 것은 아님

```
Controller에서 Repository를 직접 호출하지 않는다.
``` 

- 하지만 지침만으로는 위반 여부를 확실히 검증하기 어려움
- Java 프로젝트라면 ArchUnit 같은 도구를 활용해 계층 간 의존 관계를 자동으로 검사하도록 구성할 수 있음
- AI가 규칙을 위반하는 코드를 작성하더라도 테스트가 실패하므로 문제를 발견할 수 있음
- 즉, **중요한 규칙은 문서로 설명하는 것에서 끝내지 않고 테스트나 자동 검사로 검증하는 것이 효과적**

### 3. Feedback Loop 구성
- **작업 결과를 검증하고 발견된 문제를 다음 작업에 반영하는 반복적인 개선 구조**

```
작업 수행
    ↓
검증
    ↓
문제 발견
    ↓
원인 분석 및 수정
    ↓
재검증
    ↓
결과 확인
```
- AI가 작성한 코드에서 동일한 유형의 트랜잭션 문제가 반복적으로 발견된다면 해당 문제를 검증하는 테스트를 추가하거나 코드 리뷰 Skill의 검토 기준을 개선할 수 있음
- 단순히 한 번의 코드 수정으로 끝나는 것이 아니라 이후의 작업에서도 같은 문제가 반복되지 않도록 개발 환경을 개선하는 과정

## Spring Boot 프로젝트 적용 예시

### 구성
```
spring-project/
├── AGENTS.md
├── .agents/
│   └── skills/
│       └── code-review/
│           └── SKILL.md
├── docs/
│   └── architecture.md
├── src/
│   ├── main/
│   └── test/
├── build.gradle
└── gradlew
```

### AGENTS.md
- 프로젝트에서 사용할 기술 스택과 공통 작업 규칙을 정의
- Java 17, Spring Boot 3, 기존 패키지 구조 유지, 변경 후 관련 테스트 실행

### SKILL.md
- 코드 리뷰 수행 절차를 정의
- 변경 파일 분석, 트랜잭션 검토, 동시성 확인, 테스트 누락 검토 등을 재사용 가능한 절차로 관리

### architecture.md
- 프로젝트의 주요 구성 요소와 데이터 처리 흐름을 설명
- AI가 기능을 개발하거나 변경할 때 기존 구조를 이해하기 위한 참고 자료로 활용

### Gradle / JUnit
- 실제로 코드를 빌드하고 테스트할 수 있는 검증 수단을 제공

### 작업 수행 예시
```
RabbitMQ 메시지 처리 과정에서
중복 처리가 발생하지 않도록 개선해 줘.
```

1. `AGENTS.md`와 관련 설계 문서를 읽고 프로젝트 구조를 확인
2. 기존 메시지 처리 흐름과 멱등성 처리 방식 분석
3. 개선 방안을 결정하고 코드 수정
4. Gradle을 통한 관련 테스트 실행
5. 코드 리뷰 Skill 또는 Subagent를 활용하여 변경 사항 검토
6. 발견된 문제를 수정하고 재검증한 뒤 결과 보고

가능한 워크플로의 예시이고 Codex가 자동으로 모든 단계를 실행하려면 해당 규칙과 실행 조건이 실제로 구성되어 있어야 함

## Prompt, Skill, Subagent와의 관계
앞서 학습한 개념들은 Harness Engineering을 구성하는 데 활용할 수 있음

| 개념 | 핵심 역할 |
| --- | --- |
| Prompt Engineering | AI에게 작업을 효과적으로 지시 |
| AGENTS.md | 프로젝트 공통 규칙과 정보 제공 |
| Agent Skills | 반복되는 작업 절차 정의 |
| Subagent | 독립적인 컨텍스트에서 특정 작업 수행 |
| Harness Engineering | 위 요소들과 도구, 환경, 검증, 피드백을 종합적으로 설계 |

ex) Superpowers의 `requesting-code-review` Skill은 코드 리뷰 절차를 정의하고 Subagent를 통해 해당 작업을 수행
- 그러나 이 Skill 하나를 설치했다고 프로젝트 전체의 하네스가 완성되는 것은 아님
- 실제 코드가 정상 동작하는지 테스트할 환경이 필요하고, 프로젝트 구조를 이해할 문서와 작업 결과를 판단할 검증 기준도 필요함

> Harness Engineering은 Skill이나 Subagent 자체를 만드는 기술이라기보다 **여러 요소를 조합하여 AI 에이전트가 신뢰할 수 있는 결과를 만들도록 작업 환경을 설계하는 접근 방식**

## 적용 시 주의사항

### 모든 작업을 자동화할 필요는 없음
- 간단한 코드 수정까지 복잡한 계획 수립, 다중 Subagent 리뷰, 전체 테스트를 강제하면 오히려 작업 효율이 떨어질 수 있음
- 작업의 복잡도와 위험도에 따라 필요한 검증 수준을 다르게 적용하는 것이 좋음

### AI에게 모든 권한을 제공해서는 안 됨
- 파일 삭제, 데이터베이스 변경, 외부 서비스 접근, 배포 등은 실패했을 때 영향을 크게 미칠 수 있음
- 작업 범위에 맞는 권한을 부여하고 중요한 변경은 승인 절차를 거치도록 구성해야 함

### 하네스도 지속적으로 관리해야 함
- 프로젝트의 기술 스택과 구조가 변경되면 `AGENTS.md`, Skills, 테스트, 참고 문서도 함께 수정해야 함
- 오래된 규칙이나 실제 코드와 다른 설명이 남아 있다면 AI가 잘못된 정보를 바탕으로 작업할 수 있기 때문임

## 핵심 정리
Harness Engineering은 AI 에이전트가 안정적으로 작업할 수 있도록 실행 환경, 규칙 ,도구, 검증 및 피드백 체계를 설계하고 개선하는 방식

단순히 프롬프트를 잘 작성하는 것보다 더 넓은 개념이며 AI가 프로젝트를 이해하고 작업을 실행한 뒤 결과를 검증할 수 있는 환경을 만드는 데 중점

### 핵심 원칙
- Context: 작업에 필요한 정보를 제공
- Execution: 정해진 규칙과 도구를 활용해 작업
- Validation: 테스트와 리뷰를 통해 결과를 검증
- Feedback: 발견된 문제를 개선하고 다음 작업에 반영

최종적으로 Harness Engineering의 목적은 AI가 코드를 많이 생성하게 만드는 것이 아니라 **AI가 수행한 작업을 검증할 수 있고 반복적으로 발생하는 문제를 줄일 수 있는 개발 환경을 만드는 것**
