# LLM 토큰 (Token) 개념 및 실무 가이드

LLM(Large Language Model)이 텍스트를 처리하는 **최소 연산 단위**

단순히 글자 수(Character)나 단어 수(Word)와는 다른 개념

---

## 1. 토큰의 정의와 특징

### 1) 서브워드(Subword) 분할 방식
LLM은 텍스트를 통째로 처리하지 않고, 자주 쓰이는 뭉치는 하나로, 드문 단어는 여러 개로 쪼개서 관리함
*   **예시**: `unbelievable` -> `un` + `believ` + `able` (3 tokens)
*   **특징**: 자주 등장하는 단어는 1토큰으로 처리되어 효율적이지만, 드문 단어나 신조어는 여러 토큰으로 쪼개져 연산량이 늘어남

### 2) 언어별 불균형 (영어 vs 한국어)
*   **영어**: 보통 1단어가 1~1.3토큰 정도임 (대략 4글자당 1토큰)
*   **한국어**: 형태소 분석의 복잡성으로 인해 영어보다 토큰 효율이 떨어짐
    *   **영어**: `Hello` (1 token)
    *   **한국어**: `안녕하세요` (약 3~5 tokens - 토크나이저에 따라 다름)
*   **실무 포인트**: 동일한 의미를 전달할 때 한국어가 영어보다 약 2~3배 많은 토큰을 소모하며, 이는 **비용 상승**과 **응답 속도 저하**로 직결됨

---

## 2. 토큰과 비용/성능의 관계

### 1) 비용 산정 (Input vs Output)
대부분의 LLM API(OpenAI, Claude 등)는 사용한 토큰 수에 따라 과금함
*   **입력(Input) 토큰**: 사용자가 보낸 프롬프트 + 시스템 메시지 + 이전 대화 내역
*   **출력(Output) 토큰**: 모델이 생성한 답변 (보통 입력보다 단가가 비쌈)
*   **실무 팁**: 불필요하게 긴 시스템 프롬프트는 매 요청마다 비용을 발생시키므로 최적화가 필요함

### 2) 응답 속도 (Latency)
*   **입력 처리**: 입력 토큰이 많아지면 모델이 이를 해석하는 초기 지연 시간이 길어짐 (O(N²)의 연산량 증가)
*   **출력 처리**: LLM은 **한 번에 한 토큰씩 생성**함. 따라서 출력 토큰이 길어질수록 전체 응답 시간은 정비례하여 늘어남
*   **해결책**: 실무에서는 사용자 경험(UX)을 위해 **Streaming** 방식을 사용하여 첫 토큰이 생성되는 즉시 화면에 보여줌

---

## 3. Context Window (맥락 제한)

모델이 한 번에 기억하고 처리할 수 있는 최대 토큰 용량
*   **구조**: `[시스템 프롬프트] + [이전 대화 기록] + [현재 질문] + [모델의 답변]` 의 합계가 제한을 넘지 않아야 함
*   **제한 초과 시**: 가장 오래된 대화 내용부터 잘려나가며(Truncation), 모델이 이전 맥락을 잊어버리는 현상이 발생함
*   **실무 전략**: 긴 문서를 처리할 때는 전체를 넣지 않고 **RAG (Retrieval-Augmented Generation)** 를 통해 필요한 부분만 추출하여 주입함

---

## 4. 백엔드 개발자를 위한 실무 최적화 전략

### 1) 프롬프트 다이어트
매 요청마다 반복되는 긴 지시 사항은 토큰 낭비임. 핵심 지시사항만 남기거나, 자주 쓰이는 컨텍스트는 필요한 부분만 주입함

### 2) API 파라미터 제어
*   **max_tokens**: 모델이 내놓을 답변의 최대 길이를 제한하여 예상치 못한 비용 폭증을 방지함
*   **stop sequences**: 특정 단어(예: `\n`, `User:`)가 나오면 생성을 멈추게 하여 불필요한 토큰 생성을 막음

### 3) 토큰 사용량 모니터링
실무 서비스에서는 사용자별/API별 토큰 사용량을 반드시 로깅해야 함 (`prompt_tokens`, `completion_tokens`)

### 4) 캐싱 전략
자주 묻는 질문이나 동일한 프롬프트에 대한 응답은 **Redis** 등에 캐싱하여 LLM 호출 자체를 줄임

### 요약
> **토큰은 LLM 서비스의 "돈"이자 "시간"임.**
> 백엔드 엔지니어는 적은 토큰으로 정확한 결과를 얻을 수 있도록 프롬프트를 설계하고, RAG나 캐싱 등을 통해 효율적으로 토큰 수명(Context Window)을 관리해야 함
