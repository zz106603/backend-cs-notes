# AI Coding Agent 실무 환경 구성

## AI Coding Agent 개발 환경 개요

AI Coding Agent를 효율적으로 활용하려면 단순히 프롬프트를 잘 작성하는 것뿐 아니라 프로젝트 규칙, 작업 절차, 도구 접근 권한, 검증 환경을 적절하게 구성해야 함

Codex는 프로젝트의 소스 코드를 읽고 수정할 수 있으며 터미널을 통해 테스트를 실행하거나 Git 변경 사항을 분석할 수 있음

하지만 프로젝트의 구조와 개발 규칙을 충분히 이해하지 못한다면 기존 설계와 일치하지 않는 코드를 작성하거나 중요한 검증 절차를 누락할 수 있음

| 구성 요소 | 주요 역할 |
| --- | --- |
| `AGENST.md` | 프로젝트 공통 규칙과 작업 지침 |
| `config.toml` | Codex 실행 환경과 권한 설정 |
| Skills | 반복적인 개발 작업 절차 |
| Subagents | 전문화된 작업의 분리와 위임 |
| MCP | 외부 도구와 시스템 연결 |
| Test/CI | 코드 변경 결과 자동 검증 |

**프로젝트의 규모와 개발 과정에서 반복적으로 발생하는 문제에 맞춰 필요한 기능부터 적용하는 것이 중요함**

> OpenAI는 2026년 9월 공개한 가이드에서 모델의 성능이 발전함에 따라 불필요하게 많은 지침을 작성하는 방식보다 간결하고 목적이 분명한 지침을 유지할 것을 권장

## AGENTS.md 작성 및 관리

### 역할
- Codex가 프로젝트에서 작업할 때 참고하는 공통 지침 파일
- 프로젝트의 기술 스택, 디렉터리 구조, 코딩 규칙, 테스트 방법, 변경 시 주의사항 등을 정의
- 작업을 시작할 때 적용 범위에 해당하는 `AGENTS.md`를 읽어 프로젝트의 규칙을 파악

### 적용 범위

| 구분 | 파일 위치 | 역할 |
| --- | --- | --- |
| Global | `~/.codex/AGENTS.md` | 모든 프로젝트에 공통 적용 |
| Project | 프로젝트 루트의 `AGENTS.md` | 해당 프로젝트의 공통 규칙 |
| Directory | 하위 디렉터리의 `AGENTS.md` | 특정 모듈이나 디렉터리 규칙 |

- 전역 지침에는 작업 결과를 한국어로 설명하고 코드 수정 후 변경 사항을 요약하도록 설정할 수 있음
- 프로젝트 지침에는 Java 버전, Spring Boot 구조, 테스트 실행 방법 등을 작성
- 여러 파일이 존재한다면 Codex는 전역에서 프로젝트의 현재 작업 디렉터리까지 지침을 순서대로 적용
- 하위 디렉터리의 지침은 더 구체적인 규칙을 정의하는 데 사용

### 예시
```markdown
# Project Guidelines

## Project Overview

- Java 17 / Spring Boot 3 기반 백엔드 프로젝트
- Gradle을 빌드 도구로 사용
- PostgreSQL과 Spring Data JPA 사용
- RabbitMQ를 통한 비동기 메시지 처리

## Architecture

- 기존 Controller, Service, Repository 구조를 유지한다.
- 새로운 패키지나 추상화 계층이 필요하다면 이유를 설명한다.
- 관련 기능을 수정하기 전에 호출 흐름과 의존성을 확인한다.

## Implementation

- 기존 API의 응답 계약을 임의로 변경하지 않는다.
- 트랜잭션 경계와 데이터 정합성을 고려한다.
- 메시지 처리 로직을 변경할 경우 중복 처리 및 재처리 영향을 검토한다.
- 불필요한 의존성 추가를 피한다.

## Verification

- 코드 변경 후 관련 테스트를 실행한다.
- 필요한 경우 ./gradlew.bat test 명령을 사용한다.
- 테스트 실패 시 실패 원인과 수정 내용을 설명한다.
- 실행하지 않은 테스트는 통과했다고 보고하지 않는다.

## Constraints

- 요청하지 않은 대규모 리팩토링은 진행하지 않는다.
- 환경 변수와 인증 정보를 노출하지 않는다.
- 배포 및 운영 데이터 변경은 사용자 승인 후 진행한다.
```

### 좋은 AGENTS.md 작성 기준
많은 내용을 작성하는 것이 목적이 아님

AI가 반복적으로 잘못 판단하거나 반드시 지켜야 하는 규칙을 중심으로 구성하는 것이 좋음

- 프로젝트의 핵심 기술과 주요 구조
- 기존 설계를 유지하기 위한 규칙
- 테스트 및 빌드 명령어
- 데이터 변경과 외부 시스템 접근 시 주의사항
- 중요한 설계 문서의 위치

Java나 Spring Boot의 일반적인 개념, 지나치게 상세한 구현 절차, 모든 작업에 동일한 대규모 테스트를 강제하는 지침은 필요한 경우가 아니라면 제외하는 것이 좋음

상세 아키텍처는 `docs/architecture.md`에 작성하고 AGENTS.md에서는 해당 문서의 위치를 안내하는 방식이 효율적

> AGENTS.md는 프로젝트 전체 설명서가 아니라 AI가 작업할 때 참고할 핵심 규칙과 문서의 진입점으로 관리

## Codex 실행 환경 구성
`config.toml`을 통해 실행 환경과 권한을 설정할 수 있음

`AGENTS.md`가 AI의 작업 지침을 정의한다면 `config.toml`은 실제 도구 실행과 접근 권한을 설정하는 파일

### 기본 구조
```
Windows:
C:\Users\<사용자>\.codex\config.toml

macOS / Linux:
~/.codex/config.toml
```
프로젝트마다 다른 설정이 필요하다면 프로젝트 내부의 `.codex/config.toml`을 활용

### 설정 예시
```toml
# 명령 실행 시 필요한 승인을 요청
approval_policy = "on-request"

# 작업 공간 내부의 파일 쓰기를 허용
sandbox_mode = "workspace-write"

# 멀티 에이전트 기능
[features]
multi_agent = true
```

| 설정 | 의미 |
| --- | --- |
| `approval_policy` | 명령 실행 승인 정책 |
| `sandbox_mode` | 파일 및 실행 환경 접근 범위 |
| `features.multi_agent` | Subagent 협업 기능 사용 여부 |

#### Sandbox는 Codex가 어디까지 접근할 수 있는지 제한
- `read-only`: 파일 수정 없이 읽기 중심 작업
- `workspace-write`: 허용된 작업 공간에서 파일 수정 가능
- `danger-full-access`: 광범위한 접근 권한 제공

#### Approval은 특정 작업 수행 전 사용자에게 승인을 요청할지를 결정

일반적인 로컬 개발 환경에서는 workspace-write와 on-request 조합을 시작점으로 고려할 수 있음

다만 Sandbox 설정만으로 모든 파일 변경이나 위험한 작업이 완벽하게 차단되는 것은 아님

Git 브랜치를 활용하고 중요한 변경은 diff를 검토. 접근 권한을 불필요하게 넓히는 설정은 피하는 것이 좋음

## Skills 및 MCP 활용 환경

### Skills 선택 기준
- 자주 반복되는 작업의 절차를 표준화할 때 사용
- 기존 Skill을 설치하기 전에 현재 프로젝트에서 반복적으로 수행하는 작업인지, 이미 사용하는 Skill과 기능이 중복되지 않는지 확인하는 것이 좋음

| 작업 유형 | Skill 활용 목적 |
| --- | --- |
| Code Review | 버그, 동시성, 예외 처리 검토 |
| Debugging | 오류 재현과 원인 분석 |
| Testing | 테스트 케이스 작성 및 실행 |
| Verification | 작업 완료 전 검증 |
| Planning | 복잡한 기능 개발 계획 수립 |

### Skill 관리 위치
```
사용자 공통 Skill
~/.agents/skills/

프로젝트 전용 Skill
프로젝트/.agents/skills/
```
- 사용자 공통 Skill은 여러 프로젝트에서 반복 사용하는 작업에 적합
- 프로젝트 전용 Skill은 특정 서비스의 배포 절차나 테스트 방식처럼 해당 프로젝트에 종속적인 작업에 적합
- ex) 공통 코드 리뷰 Skill은 사용자 디렉터리 관리, 특정 프로젝트의 RabbitMQ 장애 분석 절차는 프로젝트 내부에서 관리

### MCP 활용 기준
AI 에이전트가 외부 시스템이나 도구와 상호작용할 수 있도록 연결하는 표준

Skills가 작업 방법을 정의한다면 MCP는 작업에 필요한 실제 기능이나 데이터를 제공할 수 있음

ex) Codex 최신 문서를 조회하려면 OpenAI 문서 MCP 서버를 연결
```
codex mcp add openaiDeveloperDocs --url https://developers.openai.com/mcp
```
```
codex mcp list
```
- OpenAI 개발 문서의 검색과 조회에 사용되는 읽기 전용 MCP
- MCP 서버가 많다고 개발 효율이 높아지는 것은 아님. 외부 도구가 많아질수록 접근 권한과 인증 정보 관리가 복잡해질 수 있으므로 실제 필요한 서비스만 연결하는 것이 좋음

## 개발 작업별 Codex 활용 워크플로
AI Coding Agent를 효율적으로 활용하려면 모든 개발 작업에 동일한 절차를 적용하기보다 작업의 복잡도와 위험도에 따라 검증 수준을 구분하는 것이 좋음

### 단순한 코드 변경
- 메서드 수정이나 명확한 버그 수정처럼 영향 범위가 작은 작업은 메인 Codex가 수행하도록 함

```
요구사항 확인
    ↓
관련 코드 분석
    ↓
코드 수정
    ↓
관련 테스트 실행
    ↓
변경 사항 보고
```
- 이런 작업까지 별도의 Subagent나 복잡한 계획 수립 절차를 사용할 필요는 없음

### 복잡한 기능 개발
- 새로운 API를 추가하거나 메시지 처리 구조를 변경하는 작업은 먼저 영향을 분석하고 구현 계획을 수립하는 방식이 적합

```
요구사항 분석
    ↓
기존 구조 및 영향 범위 확인
    ↓
구현 계획 수립
    ↓
기능 구현
    ↓
테스트 실행
    ↓
Skill / Subagent 기반 코드 리뷰
    ↓
문제 수정 및 재검증
    ↓
최종 결과 보고
```
- 이때 Skill은 테스트나 코드 리뷰 절차를 재사용하는 데 활용할 수 있으며 Subagent는 독립적인 코드 검토나 구조 분석을 맡는데 활용할 수 있음

### 작업 완료 기준 정의
Codex가 작업을 완료했다고 보고하더라도 실제 검증이 완료되었다는 의미는 아님

- 요청한 요구사항이 충족되었는가?
- 의도하지 않은 파일까지 수정했는가?
- 관련 테스트를 실제로 실행했는가?
- 테스트가 실패했다면 원인과 한계를 설명했는가?
- 데이터 정합성과 기존 기능에 영향을 주지 않는가?

Spring Boot 프로젝트에서는 다음과 같은 명령을 활용
```
# 전체 테스트 실행
.\gradlew.bat test

# Git 변경 사항 확인
git diff

# 공백 오류 등 검사
git diff --check

# 수정된 파일 확인
git status --short
```
전체 테스트가 Testcontainers나 외부 서비스에 의존한다면 Docker 실행 여부와 테스트 환경도 확인해야 함

**테스트가 실제로 실행되었고 결과를 확인했는지가 중요**

## 추천 Skills 및 오픈 소스

실제 사용자 수나 설치 횟수에 대한 통일된 순위는 없으므로 인기 순위가 아닌 활용 목적으로 선정

| 프로젝트 | 주요 특징 | 활용 대상 |
| --- | --- | --- |
| Superpowers | 개발 계획, TDD, 디버깅, 코드 리뷰 워크플로 | 전반적인 개발 과정 |
| Matt Pocock Skills | 코드 리뷰, 설계 및 개발 작업 Skill | 코드 품질 개선 |
| Addy Osmani Agent Skills | 프로덕션 엔지니어링 중심 지침 | API 설계 및 품질 검증 |
| Vercel Agent Skills | React/Next.js 개발 모범 사례 | 프론트엔드 개발 |
| OpenAI Plugins | 공식 Plugin 구성 및 Skill 예제 | Plugin 구조 학습 |

### Superpowers
- 전체 개발 작업의 절차를 관리하고 싶은 경우에 적합
- `writing-plans`, `systematic-debugging`, `requesting-code-review`, `verification-before-completion` 등
- 모든 작업에 엄격한 절차를 적용하면 간단한 수정에도 불필요한 작업이 증가할 수 있음

### Matt Pocock Skills
- 코드 구조와 설계 판단 등 특정 개발 작업에 집중하기 좋은 SKill 모음
- Superpowers처럼 전체 개발 워크플로를 구성하기보다 특정 작업에서 참고하거나 비교하기에 적합

### OpenAI Plugins
- Plugin 예제를 통해 Skill과 MCP가 하나의 패키지로 구성되는 방식을 살펴볼 수 있음
- 개별 Skill을 직접 작성하거나 여러 Skill을 하나의 Plugin으로 배포하는 방법을 학습할 때 유용

### 기존 SKill 도입 시 주의사항
외부 SKill은 설치하기 전에 `SKILL.md`와 관련 스크립트를 확인해야 함

특히 자동으로 파일을 수정하거나 셸 명령을 실행하는 SKill은 예상하지 못한 변경을 발생시킬 수 있음

신뢰할 수 있는 저장소에서 제공하는지 확인하고 실제 프로젝트에 적용하기 전에 수행 절차를 검토하는 것이 좋음

또한 여러 SKill이 비슷한 목적을 가지고 있다면 전부 설치하기보다 현재 작업에 가장 적합한 하나를 먼저 사용하는 것이 효율적

## 실무 환경 구성 권장 순서

- **1단계**: AGENTS.md (프로젝트 규칙과 테스트 기준 정리)
- **2단계**: Codex 설정 (작업 권한과 실행 환경 확인)
- **3단계**: Skills (코드 리뷰와 검증 절차 재사용)
- **4단계**: Test / CI (자동 검증 환경 구축)
- **5단계**: MCP / Subagent (필요한 작업에 한해 기능 확장)

ex) 기존 Spring Boot에 `AGENTS.md`가 있고 Gradle 테스트와 GitHub Actions가 구성되어 있다면 기본적인 작업 환경은 이미 갖춰져 있는 것

이 상태에서 코드 리뷰 Skill을 활용하고 결과 검증 절차를 정리하는 것만으로도 개발 과정의 일관성 개선

## 핵심 정리
AI Coding Agent를 실무에서 활용하기 위해서는 프로젝트에 대한 이해, 작업 절차, 실행 환경, 검증 체계를 함께 관리해야 함

- `AGENTS.md`는 프로젝트 규칙을 제공
- `config.toml`은 Codex의 실행 환경과 접근 권한을 설정
- SKills는 반복적인 작업 절차를 재사용
- Subagent는 특정 작업을 별도의 컨텍스트에서 수행하도록 지원

AI가 작성한 코드가 요구사항을 충족하는지 확인하고 테스트 결과와 변경 사항을 검토하는 과정이 중요함

1. **필요한 규칙만 명확하게 제공**: AGENTS.md와 문서를 간결하게 관리
2. **반복 작업을 재사용 가능한 절차로 구성**: SKills와 Subagent를 목적에 맞게 활용
3. **검증 가능한 환경 마련**: 테스트, Git diff, CI를 통해 결과를 확인

AI Coding Agent 활용 역량은 **프로젝트에 적합한 작업 환경을 설계하고 결과의 정확성을 검증할 수 있는지**에 달려 있음
