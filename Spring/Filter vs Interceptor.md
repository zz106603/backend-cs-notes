# Filter vs Interceptor

Spring 웹 애플리케이션에서 요청을 가로채어 공통 기능을 처리하는 두 메커니즘의 차이점을 설명함

---

## 1. 사전 개념 이해

### 서블릿 (Servlet)
자바를 사용하여 웹 페이지를 동적으로 생성하는 서버측 프로그램. 클라이언트의 요청을 받고 응답을 돌려주는 역할을 수행함

### 디스패처 서블릿 (Dispatcher Servlet)
Spring MVC의 핵심 요소로, 모든 HTTP 요청을 한곳에서 받아 적절한 컨트롤러(핸들러)로 배분해주는 **프론트 컨트롤러(Front Controller)**

---

## 2. 동작 위치 및 흐름

두 기술은 실행되는 시점과 소속된 컨테이너가 다릅니다.

*   **Filter**: **서블릿 컨테이너(Tomcat 등)** 수준에서 실행됨. 디스패처 서블릿에 요청이 도달하기 전/후에 동작
*   **Interceptor**: **Spring 컨테이너** 수준에서 실행됨. 디스패처 서블릿이 컨트롤러를 호출하기 전/후에 동작

**[전체 흐름]**
`HTTP 요청 -> 필터(Filter) -> 디스패처 서블릿 -> 인터셉터(Interceptor) -> 컨트롤러`

---

## 3. 주요 차이점 비교

| 구분 | 필터 (Filter) | 인터셉터 (Interceptor) |
| :--- | :--- | :--- |
| **관리 컨테이너** | 서블릿 컨테이너 | 스프링 컨테이너 (Spring Context) |
| **동작 위치** | HTTP 요청/응답의 최전방 | 디스패처 서블릿과 컨트롤러 사이 |
| **접근 가능 객체** | ServletRequest, ServletResponse | **Handler(컨트롤러 객체)**, ModelAndView |
| **스프링 빈 사용** | 과거엔 어려웠으나 현재는 가능함 | 매우 자유로움 |
| **중단 처리** | `FilterChain.doFilter()` 호출 여부로 제어 | `preHandle`의 리턴값(boolean)으로 제어 |

---

## 4. 실무 활용 예시

### 1) 필터 (Filter)의 실무 예시
주로 애플리케이션의 **비즈니스 로직과 무관한 전역적인 처리**에 사용됨

*   **인코딩 설정**: 모든 요청의 문자셋을 UTF-8로 고정
*   **보안 처리**: XSS(Cross-Site Scripting) 방어, CORS 설정
*   **로깅**: 전체 HTTP 요청에 대한 원본 데이터 로깅 (RequestID 부여)
*   **이미지 변환**: 업로드된 이미지의 리사이징 처리 등

### 2) 인터셉터 (Interceptor)의 실무 예시
주로 **비즈니스 로직(컨트롤러)과 밀접한 공통 작업**에 사용됨

*   **로그인 체크**: 세션이나 토큰(JWT)이 유효한지 검사하여 미인증 사용자를 차단
*   **권한 확인**: 현재 사용자가 특정 컨트롤러 메서드를 실행할 권한이 있는지 확인
*   **데이터 가공**: 컨트롤러로 넘겨줄 데이터를 미리 전처리하거나, 공통으로 쓰이는 모델 데이터를 추가
*   **API 실행 시간 측정**: 성능 모니터링을 위해 핸들러 실행 시간을 기록

---

## 5. 요약 및 선택 가이드

*   **필터를 선택해야 할 때**:
    *   Spring 프레임워크에 의존하지 않는 독립적인 기술(보안, 인코딩 등)을 적용할 때
    *   Request/Response 객체 자체를 다른 객체로 바꿔치기해야 할 때 (인터셉터는 불가능)

*   **인터셉터를 선택해야 할 때**:
    *   실행될 컨트롤러(Handler) 정보를 파악해야 할 때 (예: 특정 어노테이션 확인)
    *   Spring의 다양한 빈(Service, Repository 등)을 적극 활용하여 비즈니스 권한을 체크해야 할 때

### 결론
> **필터는 "문지기" 역할을 하며 전체적인 요청을 걸러내고, 인터셉터는 "비서" 역할을 하며 컨트롤러를 돕는 세밀한 작업을 수행함**
