# 서버리스 (Serverless)

"서버가 없다(Server-less)"는 뜻이 아니라, 개발자가 **"서버를 직접 관리할 필요가 없다"** 는 의미의 클라우드 컴퓨팅 모델

인프라 구축, 스케일링, OS 패치, 보안 관리 등을 모두 클라우드 제공업체(AWS, GCP, Azure 등)에 위임함

---

## 1. 서버리스의 핵심 모델

### 1) FaaS (Function as a Service) - 함수 단위 실행
*   **개념**: 미리 작성해 둔 코드(함수)를 특정 이벤트가 발생했을 때만 실행하고, 실행된 시간만큼만 비용을 지불하는 모델. 가장 대표적인 서버리스 형태
*   **대표 서비스**: **AWS Lambda**, GCP Cloud Functions, Azure Functions

#### 실무 예시: "이미지 썸네일 생성"
1.  **이벤트 발생**: 사용자가 웹사이트에 원본 이미지를 업로드함 (S3 버킷에 파일 생성)
2.  **함수 실행**: S3 업로드 이벤트를 감지하여, 미리 작성해 둔 이미지 리사이징 Lambda 함수가 자동으로 실행됨
3.  **결과**: Lambda 함수가 원본 이미지를 읽어 썸네일을 만든 후, 다른 S3 버킷에 저장함
4.  **종료**: 함수 실행이 끝나면 서버는 다시 잠든 상태가 되며, 이 과정에서 개발자는 어떤 서버도 켜거나 관리하지 않음

### 2) BaaS (Backend as a Service) - 기성품 백엔드
*   **개념**: 인증, 데이터베이스, 푸시 알림 등 웹/앱 개발에 필요한 공통적인 백엔드 기능을 클라우드 제공업체가 API 형태로 미리 만들어 제공하는 모델
*   **대표 서비스**: **Google Firebase**, AWS Cognito, AWS Amplify

#### 실무 예시: "로그인 기능 구현"
*   **전통 방식**: 로그인/회원가입 API 개발, DB 테이블 설계, 비밀번호 암호화, 세션/토큰 관리 등을 모두 직접 구현해야 함
*   **BaaS 방식**: Firebase Authentication SDK를 클라이언트에 추가하고 몇 줄의 코드만 작성하면, 구글/페이스북/이메일 등 다양한 소셜 로그인을 즉시 구현할 수 있음. 사용자 정보는 모두 Firebase가 안전하게 관리함

## 2. 전통적인 서버 모델과의 비교

| 구분 | **전통 서버 (EC2/VM)** | **컨테이너 (Docker/K8s)** | **서버리스 (FaaS)** |
| :--- | :--- | :--- | :--- |
| **관리 단위** | OS, 애플리케이션 | 애플리케이션, 라이브러리 | **함수 (Function)** |
| **관리 주체** | **개발자** (OS 패치, 보안 설정 등) | **개발자** (컨테이너 이미지, 오케스트레이션) | **클라우드 제공업체** |
| **비용 모델** | 시간당 요금 (켜두면 계속 발생) | 시간당 요금 (켜두면 계속 발생) | **호출당/실행 시간당 요금** |
| **스케일링** | 수동 또는 오토스케일링 설정 필요 | 수평 확장 (Pod 개수 조절) | **자동 (요청 수에 따라)** |

## 3. 장단점 및 실무적 고려사항

### 장점
*   **비용 효율성**: 유휴 시간에는 비용이 거의 발생하지 않음 (Pay-per-use)
*   **운영 부담 감소**: 인프라 관리에 신경 쓸 필요 없이 비즈니스 로직 개발에만 집중할 수 있음
*   **자동 스케일링**: 트래픽이 폭증해도 클라우드가 알아서 스케일링해주므로, 서버 다운 걱정이 없음

### 단점 및 주의사항
*   **콜드 스타트 (Cold Start)**: 한동안 호출되지 않은 함수는 잠들어 있다가, 첫 호출 시 깨어나는 데 시간이 걸려 응답 지연이 발생할 수 있음 (초기 로딩 딜레이)
*   **벤더 종속성 (Vendor Lock-in)**: AWS Lambda로 만든 코드는 GCP Functions에서 바로 동작하지 않음. 특정 클라우드 플랫폼에 코드가 종속되기 쉬움
*   **제한된 실행 환경**: 실행 시간이 보통 15분 이내로 제한되며, 사용할 수 있는 메모리나 CPU에도 한계가 있음
*   **디버깅 및 모니터링**: 상태가 없는(Stateless) 함수 단위로 실행되므로, 전체적인 흐름을 추적하고 디버깅하기가 기존 방식보다 까다로움

## 4. 언제 사용하는 것이 좋을까?

*   **이벤트 기반의 비동기 작업**: 이미지 처리, 데이터 변환, 알림 발송 등
*   **주기적인 스케줄링 작업 (Cron Job)**: 매일 자정에 통계 데이터를 집계하는 배치 작업
*   **간단한 API 백엔드**: 트래픽이 많지 않거나 예측이 불가능한 소규모 API 서버
*   **챗봇, IoT 백엔드** 등 간헐적으로 발생하는 요청을 처리하는 경우
