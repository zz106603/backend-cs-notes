### 가상화 (Virtualization)

**1. 가상화란?**

> **"물리적인 컴퓨터 한 대를 논리적으로 쪼개서 여러 대처럼 사용하는 기술"**

가상화는 물리적인 하드웨어(CPU, 메모리, 디스크 등)와 운영체제(OS) 사이에 **하이퍼바이저(Hypervisor)** 라는 중간 계층을 두어, 물리적 자원을 추상화하는 기술

- **비유**: 큰 피자 한 판(물리 서버)을 여러 조각(가상 머신)으로 나누어 여러 사람이 나눠 먹는 것과 같음. 하지만 각 사람은 자신이 피자 한 판을 온전히 다 가지고 있다고 착각하게 만드는 기술

---

**2. 실무에서 가상화를 왜 사용하나요?**

실무 관점에서 가상화가 주는 이점은 명확

1.  **비용 절감 (서버 통합)**
    *   **상황**: 회사에 웹 서버, DB 서버, 메일 서버가 필요한데 각각 물리 서버를 사면 돈이 많이 듬. 게다가 각 서버는 성능의 10%만 쓰고 있음
    *   **해결**: 고성능 물리 서버 1대에 가상 머신(VM) 3개를 띄워 각각 웹, DB, 메일 서버로 사용함. 하드웨어 비용과 전력 비용을 획기적으로 줄일 수 있음

2.  **격리성 (Isolation)**
    *   **상황**: 한 서버에 여러 프로그램을 돌리다가 하나가 에러를 내서 서버 전체가 다운. 다른 프로그램도 다 같이 죽음
    *   **해결**: 각 프로그램을 별도의 VM이나 컨테이너에 격리함. 하나가 죽어도 옆집(다른 VM)에는 아무런 영향이 없음

3.  **유연성과 빠른 복구 (스냅샷)**
    *   **상황**: 운영체제 업데이트를 하다가 설정이 꼬여서 부팅이 안 됨. 포맷하고 다시 세팅하려면 하루가 걸림
    *   **해결**: 작업 전에 '스냅샷(Snapshot)'을 찍어둠. 문제가 생기면 버튼 하나로 작업 전 상태로 즉시 되돌릴 수 있음 (게임의 세이브/로드 기능과 유사)

---

**3. VM (Virtual Machine) vs 컨테이너 (Container)**

이 두 기술은 **"격리의 수준"** 과 **"무게"** 에서 차이가 남

| 구분 | 가상 머신 (VM) | 컨테이너 (Container) |
| :--- | :--- | :--- |
| **비유** | **단독 주택** | **아파트 (또는 호텔 방)** |
| **구조** | 하드웨어 > 하이퍼바이저 > **게스트 OS** > 앱 | 하드웨어 > 호스트 OS > **컨테이너 엔진** > 앱 |
| **OS 포함 여부** | 포함 (무거움) | 미포함 (호스트 OS 커널 공유) |
| **부팅 속도** | 느림 (수 분, OS 부팅 필요) | 빠름 (수 초, 프로세스 실행 수준) |
| **용량** | 큼 (GB 단위) | 작음 (MB 단위) |
| **대표 기술** | VMware, VirtualBox, AWS EC2 | Docker, Kubernetes |

#### VM (가상 머신) - "무겁지만 완벽한 격리"
*   **특징**: 호스트 OS 위에 '게스트 OS'를 통째로 설치함
*   **장점**: 보안이 강력하고, 서로 다른 OS(윈도우 위에서 리눅스 등)를 돌릴 수 있음
*   **단점**: OS를 통째로 띄우니 무겁고 느림
*   **실무 예시**: **AWS EC2** 인스턴스를 생성하면 기본적으로 VM을 할당받음

#### 컨테이너 (Container) - "가볍고 빠른 배포"
*   **특징**: OS는 공유하고, 애플리케이션 실행에 필요한 라이브러리와 설정만 묶어서 격리
*   **장점**: 매우 가볍고 시작이 빠름. 배포가 쉬움
*   **단점**: 호스트 OS(커널)를 공유하므로, 리눅스 컨테이너를 윈도우에서 바로 돌릴 수 없음(별도 설정 필요). 보안 격리 수준이 VM보다 낮을 수 있음
*   **실무 예시**: **Docker**를 사용하여 개발한 서버를 이미지로 만들고, 어디서든 똑같이 실행되도록 배포함

---

**4. 실무 활용 예시 (시나리오)**

*   **개발 환경 구축 (Docker 활용)**
    *   신입 개발자가 입사. 예전에는 개발 환경 세팅(Java 설치, DB 설치, 환경 변수 설정 등)에만 3일이 걸림
    *   이제는 `docker-compose up` 명령어 하나면 DB, Redis, 웹 서버가 컨테이너로 3분 만에 실행됨

*   **클라우드 마이그레이션 (VM 활용)**
    *   기존 온프레미스(사내 전산실)에 있던 물리 서버들을 클라우드(AWS, Azure)로 옮김
    *   물리 서버의 내용을 그대로 이미지로 떠서 클라우드 상의 VM으로 옮기면(Lift and Shift), 코드 수정 없이 클라우드로 이사할 수 있음

*   **MSA (마이크로서비스 아키텍처)**
    *   거대한 모놀리식 서비스를 수십 개의 작은 서비스로 쪼갬
    *   각 서비스를 VM으로 띄우면 오버헤드가 너무 큼. 가벼운 **컨테이너**로 띄우고 **Kubernetes**로 관리하는 것이 표준
