# 템플릿 메서드 패턴 (Template Method Pattern)

"알고리즘의 **구조(뼈대)** 는 부모 클래스에서 정의하고, **구체적인 단계(내용)** 는 자식 클래스에서 구현하게 하는 패턴"

---

## 1. 왜 필요한가요?

### 문제 상황: 여러 종류의 파일 처리기
`CSV` 파일과 `JSON` 파일을 읽어서 DB에 저장하는 기능을 만든다고 가정

1.  **CsvFileProcessor**: 파일 읽기 -> **쉼표로 분리(Parsing)** -> DB 저장
2.  **JsonFileProcessor**: 파일 읽기 -> **JSON 객체로 변환(Parsing)** -> DB 저장

두 클래스를 보면 **"파일을 읽고, DB에 저장하는"** 흐름은 100% 똑같음. 오직 **"데이터를 파싱하는 부분"** 만 다를 뿐. 이런 중복 코드가 많아지면 유지보수가 힘들어짐

---

## 2. 해결 방법 (패턴 적용)

변하지 않는 부분(전체 흐름)은 부모 클래스에 두고, 변하는 부분(파싱 로직)만 추상 메서드로 만들어서 자식이 채워 넣게 함

### 1) 부모 클래스 (템플릿 정의)
```java
public abstract class FileProcessor {

    // 템플릿 메서드 (전체 흐름을 정의, final로 오버라이딩 막음)
    public final void process(String filePath) {
        String data = readFile(filePath); // 공통 로직
        Object parsedData = parse(data);  // 변하는 부분 (추상 메서드 호출)
        saveToDb(parsedData);             // 공통 로직
    }

    private String readFile(String path) {
        System.out.println(path + " 파일을 읽습니다.");
        return "파일 내용";
    }

    // 자식이 반드시 구현해야 하는 부분 (Hook Method)
    protected abstract Object parse(String data);

    private void saveToDb(Object data) {
        System.out.println("데이터를 DB에 저장합니다: " + data);
    }
}
```

### 2) 자식 클래스 (구체적인 구현)
```java
public class CsvFileProcessor extends FileProcessor {
    @Override
    protected Object parse(String data) {
        System.out.println("쉼표(,) 기준으로 데이터를 자릅니다.");
        return "CSV 파싱 결과";
    }
}

public class JsonFileProcessor extends FileProcessor {
    @Override
    protected Object parse(String data) {
        System.out.println("JSON 포맷으로 변환합니다.");
        return "JSON 파싱 결과";
    }
}
```

### 3) 사용 코드
```java
FileProcessor processor = new CsvFileProcessor();
processor.process("data.csv"); 
// 출력:
// 1. data.csv 파일을 읽습니다.
// 2. 쉼표(,) 기준으로 데이터를 자릅니다. (자식 클래스 로직 실행)
// 3. 데이터를 DB에 저장합니다: CSV 파싱 결과
```

## 3. 장단점 및 주의사항

### 장점
*   **코드 중복 제거**: 공통 로직(파일 읽기, DB 저장)을 부모 클래스 한 곳에서만 관리하면 됨. 버그 수정 시 부모만 고치면 모든 자식에게 반영됨
*   **일관된 구조**: 모든 파일 처리기가 `process()`라는 동일한 흐름을 따르도록 강제할 수 있음

### 단점
*   **상속의 한계**: 자식 클래스가 부모 클래스에 강하게 결합됨. 부모가 바뀌면 자식도 영향을 받음
*   **유연성 부족**: 상속은 컴파일 시점에 결정되므로, 실행 중에 알고리즘을 마음대로 교체하기 어려움. (이 문제를 해결하려면 **전략 패턴(Strategy Pattern)** 을 써야 함)

## 4. 실무 활용 예시 (Spring Framework)

Spring은 템플릿 메서드 패턴을 매우 적극적으로 사용함. 다만, 상속보다는 **콜백(Callback)** 을 활용한 변형된 형태인 **템플릿 콜백 패턴**을 주로 씀

*   **`JdbcTemplate`**: DB 연결, 예외 처리, 자원 해제 같은 지루한 반복 작업은 템플릿이 다 해주고, 개발자는 SQL만 작성해서 넘겨주면 됨
*   **`RestTemplate`**: HTTP 연결 관리, 에러 처리 등은 템플릿이 하고, 개발자는 URL과 요청 데이터만 넘겨줌
*   **`AbstractTransactionalJUnit4SpringContextTests`**: 테스트 시작 시 트랜잭션을 걸고, 끝날 때 롤백하는 공통 로직을 부모 클래스가 처리해줌
