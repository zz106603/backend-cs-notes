# 싱글톤 패턴 (Singleton Pattern)

애플리케이션 전체에서 **단 하나의 인스턴스만 생성**되도록 보장하는 디자인 패턴

이 유일한 인스턴스에 어디서든 접근할 수 있도록 전역적인 접근점을 제공함

---

## 1. 왜 필요한가요? (실무 관점)

메모리와 성능 관점에서, 여러 번 생성할 필요가 없는 객체들이 있음

### 실무 예시
1.  **데이터베이스 커넥션 풀 (Connection Pool)**
    *   DB 커넥션을 맺는 작업은 비용이 매우 비쌈 
    *   커넥션 풀은 미리 여러 개의 커넥션을 만들어두고 재사용하는데, 이 커넥션 풀 관리자(DataSource)가 여러 개 존재한다면 자원 관리가 비효율적이고 혼란스러워짐
    *   따라서 단 하나의 인스턴스로 관리하는 것이 일반적

2.  **애플리케이션 설정(Configuration) 관리 클래스**
    *   `application.yml`이나 `.properties` 파일의 내용을 애플리케이션 시작 시 한 번만 읽어서 메모리에 올려두고, 여러 곳에서 이 설정 값을 참조
    *   설정 객체가 여러 개 생성되면 메모리 낭비

3.  **로깅(Logging) 객체**
    *   애플리케이션의 로그를 기록하는 로거(Logger)는 시스템 전반에 걸쳐 하나의 인스턴스로 동작하여 로그를 일관되게 관리함

---

## 2. Java 구현 방법

싱글톤을 구현하는 방법은 여러 가지가 있지만, 각각 장단점이 있음

### 1) Eager Initialization (이른 초기화)
클래스가 로드될 때부터 인스턴스를 미리 생성해두는 가장 간단한 방법

```java
public class Settings {
    // 클래스 로딩 시점에 인스턴스를 생성
    private static final Settings INSTANCE = new Settings();

    private Settings() {} // 외부에서 new로 생성하는 것을 막음

    public static Settings getInstance() {
        return INSTANCE;
    }
}
```
*   **장점**: 구현이 매우 간단하고, 멀티스레드 환경에서도 안전함
*   **단점**: 사용하지 않더라도 인스턴스가 무조건 생성되므로, 자원을 미리 차지함

### 2) Lazy Initialization (늦은 초기화) + Double-Checked Locking
`getInstance()`가 처음 호출될 때 인스턴스를 생성하는 방식

멀티스레드 환경에서의 동기화 문제를 해결하기 위해 Double-Checked Locking 기법이 사용됨

```java
public class DatabaseConnectionPool {
    // volatile 키워드로 가시성 문제 해결
    private static volatile DatabaseConnectionPool INSTANCE;

    private DatabaseConnectionPool() {}

    public static DatabaseConnectionPool getInstance() {
        if (INSTANCE == null) { // 첫 번째 체크 (성능 향상)
            synchronized (DatabaseConnectionPool.class) {
                if (INSTANCE == null) { // 두 번째 체크 (인스턴스 생성 보장)
                    INSTANCE = new DatabaseConnectionPool();
                }
            }
        }
        return INSTANCE;
    }
}
```
*   **장점**: 실제로 필요할 때만 인스턴스를 생성하여 메모리를 효율적으로 사용함
*   **단점**: 코드가 복잡하고, `volatile` 키워드를 이해해야 함

### 3) Initialization-on-demand holder idiom (권장)
클래스 로딩 시점을 이용한 가장 널리 추천되는 방법

```java
public class Settings {
    private Settings() {}

    private static class SettingsHolder {
        private static final Settings INSTANCE = new Settings();
    }

    public static Settings getInstance() {
        return SettingsHolder.INSTANCE;
    }
}
```
*   **장점**: `synchronized` 없이도 멀티스레드 환경에서 안전하며, `getInstance()`가 호출될 때만 인스턴스가 생성되어 Lazy Loading이 가능함 
*   코드가 간결하고 직관적

### 4) Enum을 사용한 방법 (가장 안전)
Enum 타입은 그 자체로 인스턴스가 하나만 생성되는 것이 보장됨

```java
public enum Settings {
    INSTANCE;

    // 필요한 메서드 추가
    public void someMethod() {
        // ...
    }
}
```
*   **장점**: 구현이 극도로 간단함. 리플렉션(Reflection)이나 직렬화/역직렬화 공격에도 안전하여 가장 견고한 방법으로 알려져 있음
*   **단점**: Enum의 특성상 상속을 사용할 수 없음

## 3. 싱글톤 패턴의 단점과 주의사항

싱글톤 패턴은 편리하지만, 과도하게 사용하면 여러 문제를 일으킬 수 있음

*   **단일 책임 원칙(SRP) 위배**: 비즈니스 로직과 인스턴스 관리 책임을 모두 갖게 됨
*   **테스트의 어려움**: 전역 상태를 갖기 때문에 단위 테스트(Unit Test)가 어려움. 인스턴스를 Mock 객체로 교체하기가 까다로움
*   **유연성 저하**: 클라이언트가 싱글톤 클래스와 강하게 결합(Tight Coupling)됨

> **Spring Framework와 싱글톤**
> 
> 현대적인 프레임워크인 Spring에서는 개발자가 직접 싱글톤 패턴을 구현할 일이 거의 없음. Spring의 **IoC 컨테이너**가 기본적으로 모든 빈(Bean)을 **싱글톤**으로 관리하고 주입(DI)해주기 때문임. 개발자는 그냥 빈을 등록하고 필요한 곳에 주입받아 사용하면 됨
