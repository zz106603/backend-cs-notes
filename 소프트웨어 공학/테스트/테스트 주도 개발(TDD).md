# 테스트 주도 개발 (TDD, Test Driven Development)

실제 코드를 작성하기 전에 **테스트 코드를 먼저 작성**하고, 이를 통과시키기 위한 최소한의 코드를 구현하며 점진적으로 시스템을 완성해 나가는 소프트웨어 개발 방법론

---

## 1. TDD의 3단계 사이클

TDD는 **Red -> Green -> Refactor**라고 불리는 짧은 주기를 반복하며 진행됨

### 1) Red (실패하는 테스트 작성)
*   **목표**: 구현하려는 기능의 요구사항을 반영하는 실패하는 테스트 코드를 먼저 작성함
*   **주의**: 프로덕션 코드(실제 로직)가 없으므로 컴파일 에러나 테스트 실패가 발생하는 것이 정상. 이 단계는 **"무엇을 만들 것인가"** 를 정의하는 과정

### 2) Green (테스트 통과)
*   **목표**: 테스트를 통과하기 위한 **최소한의 코드**를 작성함
*   **주의**: 코드의 퀄리티나 중복 제거보다는, 일단 테스트가 성공(초록색 불)하게 만드는 것에 집중함. 심지어 값을 상수로 하드코딩해서 통과시키는 것도 허용됨

### 3) Refactor (리팩토링)
*   **목표**: 테스트 성공 상태를 유지하면서 코드의 가독성을 높이고 중복을 제거함
*   **주의**: 테스트 코드가 이미 존재하므로, 안심하고 구조를 개선할 수 있음. 리팩토링 후에도 여전히 테스트가 통과해야 함

---

## 2. 실무 예시: 문자열 계산기 개발

"쉼표(,)로 구분된 숫자 문자열을 더하는 기능을 만든다"는 요구사항이 있다고 가정

### Step 1: Red (실패하는 테스트)
```java
@Test
void add_string_with_comma_returns_sum() {
    Calculator calc = new Calculator();
    int result = calc.add("1,2"); // 아직 Calculator 클래스나 add 메서드가 없음
    assertThat(result).isEqualTo(3);
}
```

### Step 2: Green (최소 구현)
```java
public class Calculator {
    public int add(String input) {
        // 테스트만 통과시키기 위한 가장 단순한 로직
        String[] numbers = input.split(",");
        return Integer.parseInt(numbers[0]) + Integer.parseInt(numbers[1]);
    }
}
```

### Step 3: Refactor (구조 개선)
*   만약 빈 문자열 처리가 추가되거나, 숫자가 3개 이상 들어올 경우를 대비해 로직을 더 범용적으로 다듬음. 이미 `add("1,2")` 테스트가 있으므로 로직 변경 시 실수를 바로 잡아낼 수 있음

## 3. TDD의 장점과 단점

### 장점
1.  **설계 품질 향상**: 테스트를 먼저 고민하다 보면 자연스럽게 객체 간의 결합도가 낮아지고 인터페이스가 깔끔해짐
2.  **디버깅 비용 감소**: 기능 구현 즉시 오류를 발견할 수 있어, 나중에 통합 테스트에서 버그를 잡는 것보다 훨씬 비용이 저렴함
3.  **코드에 대한 자신감**: 리팩토링이나 새로운 기능을 추가할 때 기존 기능이 망가지지 않았음을 보장받을 수 있음 (회귀 테스트 자동화)

### 단점
1.  **초기 개발 속도 저하**: 테스트 코드를 먼저 짜야 하므로 초기에는 일반적인 개발 방식보다 시간이 1.5 ~ 2배 정도 더 걸릴 수 있음
2.  **높은 숙련도 요구**: 테스트하기 쉬운 코드를 설계하는 것 자체가 실력이 필요하며, 익숙해지기까지 러닝 커브가 있음

---

## 4. 실무 가이드: 언제 TDD를 해야 할까?

모든 코드에 TDD를 적용하는 것은 비효율적일 수 있음

*   **TDD가 강력 추천되는 경우**:
    *   복잡한 비즈니스 로직 (세금 계산, 할인 정책 등)
    *   요구사항이 명확한 유틸리티 클래스
    *   장기적으로 유지보수가 중요한 프로젝트
*   **TDD가 비효율적인 경우**:
    *   단순한 CRUD API (단순히 DB 데이터를 옮기기만 하는 경우)
    *   UI/UX 중심의 프론트엔드 작업 (자주 변경되는 디자인)
    *   빠르게 프로토타입을 만들어야 하는 스타트업 초기 단계

### 요약
> **TDD는 단순히 테스트를 만드는 기술이 아니라, "테스트를 통해 설계를 개선해 나가는 과정".**
> 처음에는 느려 보일 수 있지만, 프로젝트가 커질수록 안정성과 유지보수성 측면에서 압도적인 효율을 발휘함
