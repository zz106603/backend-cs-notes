# 테스트 격리 (Test Isolation)

테스트 코드를 실행할 때, **각각의 테스트가 서로의 상태(주로 데이터베이스)에 영향을 주지 않도록 독립적인 환경을 보장**하는 것

---

## 1. 왜 필요한가요?

### 상황: 회원 가입 테스트
1.  **테스트 A (회원가입)**: `test@example.com` 유저를 `INSERT` 하고 성공 여부를 검증
2.  **테스트 B (중복 가입 방지)**: `test@example.com` 유저를 또 `INSERT` 해보고, 예외가 터지는지 검증

### 격리가 안 됐을 때의 문제 (비결정적 테스트)
*   **A -> B 순서로 실행**: 테스트 A가 DB에 데이터를 남겨두고 끝났으므로, 테스트 B는 이미 데이터가 있어서 의도대로 성공할 수 있음
*   **B -> A 순서로 실행**: 테스트 B가 먼저 실행되면 중복 데이터가 없으므로 예외가 안 터져서 실패할 수 있음. 또는 A가 실행될 때 이미 B가 데이터를 넣어놔서 A가 실패할 수 있음
*   **결론**: **"실행 순서에 따라 테스트 결과가 바뀌는 최악의 상황"** 이 발생함. 이를 방지하려면 테스트 하나가 끝날 때마다 DB를 **"초기화(Clean)"** 해줘야 함

---

## 2. Spring Boot에서의 격리 전략

### 전략 1: `@Transactional` (가장 기본적이고 추천하는 방법)
Spring Boot 테스트(`@SpringBootTest`)에서는 테스트 메서드에 `@Transactional`을 붙이면, **테스트 시작 시 트랜잭션을 걸고 종료 시 자동으로 롤백(Rollback)** 해줌

```java
@SpringBootTest
@Transactional // 테스트 끝나면 데이터가 롤백됨 (DB에 안 남음)
class MemberServiceTest {

    @Autowired MemberRepository memberRepository;

    @Test
    void 회원가입() {
        Member member = new Member("test@example.com");
        memberRepository.save(member);
        // 검증 로직...
    } 
    // 여기서 트랜잭션 롤백 -> DB는 깨끗해짐
}
```
*   **장점**: 사용하기 매우 쉽고, 롤백 속도가 빠름
*   **단점(한계)**:
    *   **비동기 로직 테스트 불가**: 별도의 스레드에서 동작하는 로직은 이 트랜잭션의 범위를 벗어나므로 롤백되지 않음
    *   **Auto Increment 미초기화**: 데이터는 지워지지만, PK(ID) 값은 계속 증가한 상태로 남음 (다음 테스트에서 ID가 1이 아니라 2, 3... 으로 생성됨)

### 전략 2: Table Truncate (SQL 실행)
`@Transactional`의 한계를 극복하기 위해, 매 테스트 시작 전에 **"모든 테이블의 데이터를 `TRUNCATE`(비우기) 하는 쿼리"** 를 실행하는 방법

```java
@Component
public class DatabaseCleanup implements InitializingBean {
    
    @PersistenceContext
    private EntityManager entityManager;
    private List<String> tableNames;

    // 모든 테이블 이름 추출
    @Override
    public void afterPropertiesSet() {
        tableNames = entityManager.getMetamodel().getEntities().stream()
                .map(e -> CaseFormat.UPPER_CAMEL.to(CaseFormat.LOWER_UNDERSCORE, e.getName()))
                .collect(Collectors.toList());
    }

    @Transactional
    public void execute() {
        entityManager.flush();
        // 외래 키 제약조건 잠시 해제 -> Truncate -> 제약조건 다시 설정
        entityManager.createNativeQuery("SET REFERENTIAL_INTEGRITY FALSE").executeUpdate();
        for (String tableName : tableNames) {
            entityManager.createNativeQuery("TRUNCATE TABLE " + tableName).executeUpdate();
        }
        entityManager.createNativeQuery("SET REFERENTIAL_INTEGRITY TRUE").executeUpdate();
    }
}
```
*   **장점**: 가장 확실하게 DB를 깨끗하게 만듬. Auto Increment 값도 1로 초기화됨
*   **단점**: 별도의 유틸리티 클래스(`DatabaseCleanup`)를 만들어야 하는 번거로움이 있음

### 전략 3: `@DirtiesContext` (비추천)
테스트 실행 시 Spring Context(애플리케이션)를 아예 새로 띄우는 방법

```java
@SpringBootTest
@DirtiesContext(classMode = ClassMode.AFTER_EACH_TEST_METHOD) // 매번 재시작
class MemberServiceTest { ... }
```
*   **장점**: 격리는 확실함
*   **단점**: **치명적으로 느림.** 테스트가 100개면 스프링을 100번 껐다 켜야 하므로 전체 테스트 시간이 수십 분~수 시간이 걸릴 수 있음. 실무에서는 거의 쓰지 않음

---

## 3. 요약: 실무 가이드

| 전략 | 속도 | 격리 수준 | 추천 상황 |
| :--- | :--- | :--- | :--- |
| **@Transactional** | 빠름 | 높음 (데이터 롤백) | **일반적인 대부분의 로직 테스트** |
| **Table Truncate** | 보통 | 매우 높음 (ID까지 초기화) | **비동기 로직**, 인수 테스트(`@SpringBootTest` webEnvironment 사용 시) |
| **@DirtiesContext** | **매우 느림** | 완전 초기화 | Context 설정 자체가 바뀌는 특수한 경우에만 사용 |

> **Best Practice**
> 1. 기본적으로는 **`@Transactional`** 을 사용하세요.
> 2. `@Transactional`로 해결 안 되는 경우(예: `AcceptanceTest` 등 포트 띄워서 하는 테스트)에는 **Truncate 방식**을 사용하세요.
