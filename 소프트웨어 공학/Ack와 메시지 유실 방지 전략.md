## 메시지 큐의 Ack(확인 응답)와 메시지 유실 방지 전략

### 1. Ack(확인 응답)란?

*   **정의**: 소비자가 메시지를 성공적으로 처리했음을 브로커(메시지 큐 서버)에게 알리는 메커니즘. "메시지 처리 완료" 신호라고 이해할 수 있음
*   **필요성**: 분산 시스템에서 네트워크 오류, 소비자 크래시, 처리 실패 등으로 인한 메시지 유실 및 중복 처리를 방지하고 안정적인 메시지 처리를 보장함

### 2. Ack의 동작 방식 및 종류

**기본 동작 흐름:**

1.  **생산자**: 메시지를 생성하여 브로커로 전송
2.  **브로커**: 메시지를 안전하게 저장
3.  **소비자**: 브로커로부터 메시지를 수신하여 처리
4.  **Ack 전송**: 소비자가 메시지 처리를 완료하면 브로커에게 Ack를 보냄
5.  **메시지 관리**: 브로커는 Ack 수신 후 해당 메시지를 큐에서 삭제하거나 오프셋(Offset)을 업데이트

**Ack 방식의 종류:**

*   **자동 Ack (Auto Acknowledge)**
    *   **특징**: 메시지 수신 즉시 자동으로 Ack를 보냄
    *   **장점**: 구현이 간단하고 처리 속도가 빠흠
    *   **단점**: 메시지 수신 후 실제 처리 과정에서 실패하더라도 브로커는 이미 Ack를 받았으므로 메시지를 삭제함. 이 경우 **메시지 유실 위험**이 있음
    *   **적합한 경우**: 메시지 유실이 크게 문제되지 않는 경우 (예: 실시간 로그 수집, 통계 데이터 전송)

*   **수동 Ack (Manual Acknowledge)**
    *   **특징**: 소비자가 메시지 처리를 완전히 완료한 후에 명시적으로 Ack를 보냄
    *   **장점**: 메시지 처리의 안정성을 높임. 처리 실패 시 Ack를 보내지 않아 브로커가 메시지를 재전송하거나 재처리 큐로 이동시킬 수 있음
    *   **단점**: 구현이 복잡하며, Ack 전송 시점에 따라 메시지 중복 처리 가능성이 있음 (예: 처리 완료 후 Ack 전송 전 소비자 크래시)
    *   **적합한 경우**: 메시지 유실이 치명적인 경우 (예: 결제, 주문 처리, 중요한 알림 발송)

### 3. Ack의 중요성 (메시지 유실 방지 및 안정성 확보)

Ack 메커니즘은 분산 시스템에서 다음과 같은 핵심 문제를 해결함

*   **메시지 유실 방지**: 처리 실패 시 브로커가 재전송하여 유실을 막음
*   **장애 복구**: 소비자 애플리케이션 종료 시, 처리되지 않은 메시지는 Ack가 없어 재처리되어 시스템 복원력을 높임
*   **비동기 시스템 신뢰성**: 각 단계의 성공을 보장하여 전체 시스템의 신뢰도를 향상시킴

**Ack가 없을 때 발생할 수 있는 비즈니스 문제:**

*   **결제 누락**: 주문 메시지 유실로 고객 결제 미반영 (치명적)
*   **알림 미전송**: 중요 알림(주문 완료, 배송 시작 등) 메시지 유실
*   **데이터 불일치**: 시스템 간 데이터 정합성 훼손
*   **장애 복구 불가능**: 처리 여부 파악 불가로 복구 어려움

**메시지 전달 보장 수준:**

Ack 방식과 재처리 전략에 따라 메시지 전달 보장 수준이 달라짐

*   **At-most-once (최대 한 번)**: 메시지가 최대 한 번 전달되거나 아예 전달되지 않을 수 있음 (자동 Ack 유실 시나리오)
*   **At-least-once (최소 한 번)**: 메시지가 최소 한 번 이상 전달됨을 보장. 중복 처리될 가능성이 있음 (수동 Ack + 재처리 전략)
*   **Exactly-once (정확히 한 번)**: 메시지가 정확히 한 번만 전달됨을 보장. 가장 강력하지만 구현이 매우 복잡하며, 멱등성(Idempotency) 등의 추가 전략이 필요함

### 4. 실무에서의 Ack 및 메시지 유실 방지 전략 (예시)

**1) Spring Framework 기반 애플리케이션:**

*   **RabbitMQ (Spring AMQP)**
    *   `@RabbitListener` 사용 시 `ackMode`를 `MANUAL`로 설정
    *   성공 시 `channel.basicAck(deliveryTag, false);` 호출.
    *   실패 시 `channel.basicNack(deliveryTag, false, true);` (재큐) 또는 `channel.basicReject(deliveryTag, false);` (DLQ 이동) 호출
    *   **실무 예시**: 결제 요청 메시지 처리 후 DB 저장 성공 시에만 Ack, 실패 시 Nack로 재처리 유도

*   **Kafka (Spring Kafka)**
    *   `ContainerProperties.AckMode` 설정 (예: `MANUAL`)
    *   `MANUAL` 모드에서는 `Acknowledgment.acknowledge()` 호출로 오프셋 커밋
    *   Kafka는 메시지 삭제 대신 `오프셋(Offset)` 관리. 소비자는 마지막 커밋된 오프셋부터 다시 읽어옴
    *   **실무 예시**: 사용자 행동 로그 처리 후 `Acknowledgment.acknowledge()`로 오프셋 커밋. 처리 중 오류 발생 시 오프셋 커밋을 하지 않아 해당 로그부터 재처리되도록 함

**2) 결제 시스템에서의 메시지 유실 방지:**

*   **문제**: 주문 생성 후 결제 요청 메시지 유실은 치명적
*   **전략**:
    *   **수동 Ack**: 결제 처리(DB 업데이트, 외부 결제사 연동) 완료 후에만 Ack
    *   **재처리 (Retry)**: 일시적 오류 시 Ack 미전송으로 메시지 재전송 (예: 3회 재시도)
    *   **DLQ (Dead Letter Queue)**: 재처리 횟수 소진 후에도 실패한 메시지는 DLQ로 이동시켜 수동 처리
    *   **멱등성(Idempotency)**: 동일한 결제 요청 메시지가 여러 번 와도 한 번만 처리되도록 설계 (예: 주문 ID 기반 중복 결제 방지). `at-least-once` 보장 시 중복 처리가 발생할 수 있으므로 필수적

**3) 분산 시스템 전반의 운영 고려사항:**

*   **"Producer Success != Consumer Success"**: 생산자가 메시지를 브로커에 보냈다고 소비자가 성공적으로 처리했음을 의미하지 않음. End-to-End (생산자 -> 브로커 -> 소비자 -> 최종 처리) 성공 보장 전략 필요
*   **운영 관점**:
    *   **Consumer Lag 모니터링**: 소비자의 메시지 처리 속도가 생산자를 따라가지 못할 때 발생하는 `Lag` 모니터링. Lag 증가는 처리 지연 및 큐 과부하로 이어질 수 있음
    *   **Poison Message (독성 메시지) 처리**: 특정 메시지가 계속 처리 실패를 유발하는 경우. 재처리 횟수 제한 및 DLQ 이동 전략 필수
    *   **재처리 무한 루프 방지**: 최대 재시도 횟수, 지수 백오프(Exponential Backoff) 등 전략 적용
