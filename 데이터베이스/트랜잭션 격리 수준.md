# 트랜잭션 격리 수준 (Transaction Isolation Level)

여러 트랜잭션이 동시에 실행될 때, 특정 트랜잭션이 다른 트랜잭션에서 변경하거나 조회하는 데이터를 볼 수 있게 허용할지 결정하는 설정입니다.

---

## 1. 데이터베이스 이상 현상 (Read Phenomena)

격리 수준이 낮을 때 발생할 수 있는 3가지 부정합 현상입니다.

### 1) Dirty Read
커밋되지 않은 트랜잭션의 데이터를 읽는 현상입니다. (트랜잭션이 롤백되면 존재하지 않는 데이터를 읽은 셈이 됨)

```sql
-- Transaction A
UPDATE users SET age = 21 WHERE id = 1; -- 아직 COMMIT 안 함

-- Transaction B
SELECT age FROM users WHERE id = 1; -- 21 (Dirty 데이터 읽음)

-- Transaction A
ROLLBACK; -- 나중에 A가 롤백하면 B는 존재하지 않는 값을 읽은 셈이 됨
```

### 2) Non-repeatable Read
하나의 트랜잭션 내에서 같은 데이터를 두 번 읽었을 때 결과가 다른 현상입니다. (그사이 다른 트랜잭션이 `UPDATE` 후 커밋)

```sql
-- Transaction A
SELECT balance FROM account WHERE id = 1; -- 100,000원 조회

-- Transaction B
UPDATE account SET balance = 0 WHERE id = 1;
COMMIT; -- B가 중간에 값을 바꾸고 커밋

-- Transaction A
SELECT balance FROM account WHERE id = 1; -- 0원 조회 (결과가 달라짐!)
```

### 3) Phantom Read
하나의 트랜잭션 내에서 같은 조건의 쿼리를 두 번 실행했을 때, 첫 번째에 없던 레코드가 나타나는 현상입니다. (그사이 다른 트랜잭션이 `INSERT` 후 커밋)

```sql
-- Transaction A
SELECT COUNT(*) FROM users WHERE age > 20; -- 10명 조회

-- Transaction B
INSERT INTO users (name, age) VALUES ('Kim', 25);
COMMIT; -- B가 새로운 데이터를 넣고 커밋

-- Transaction A
SELECT COUNT(*) FROM users WHERE age > 20; -- 11명 조회 (유령 레코드 등장!)
```

---

## 2. 4가지 격리 수준 (Isolation Levels)

| 격리 수준 | Dirty Read | Non-repeatable Read | Phantom Read | 주요 특징 |
| :--- | :---: | :---: | :---: | :--- |
| **Read Uncommitted** | 발생 | 발생 | 발생 | 커밋 전 데이터도 읽음 (실무 사용 금지) |
| **Read Committed** | - | 발생 | 발생 | 커밋된 데이터만 읽음 (Oracle, PostgreSQL 기본) |
| **Repeatable Read** | - | - | 발생 | 트랜잭션 내에서 동일 결과 보장 (**MySQL 기본**) |
| **Serializable** | - | - | - | 가장 엄격함 (성능 매우 저하) |

## 3. 핵심 포인트 및 면접 단골 질문

### Q1. 왜 격리 수준이 올라가면 성능이 떨어지나요?
*   **답변**: 격리 수준이 높아질수록 데이터의 정합성을 지키기 위해 더 많은 **잠금(Lock)**을 걸거나, 데이터의 여러 버전을 관리(**MVCC**)해야 하기 때문입니다.
*   **실무**: `Serializable`은 모든 읽기 작업에 잠금을 걸어 동시성 처리가 거의 불가능해지므로 특수한 경우가 아니면 사용하지 않습니다.

### Q2. DB는 내부적으로 이 현상들을 어떻게 막나요?
1.  **Lock (비관적 방식)**: 데이터를 읽거나 쓸 때 잠금을 걸어 다른 트랜잭션이 접근하지 못하게 차단합니다.
2.  **MVCC (Multi-Version Concurrency Control, 낙관적 방식)**: 데이터의 변경 이력을 Undo 로그에 기록하여, 각 트랜잭션이 자신의 시점에 맞는 데이터 버전을 읽게 합니다. (Lock 없이 읽기가 가능해 성능이 좋음)

### Q3. MySQL(InnoDB)은 Repeatable Read인데 왜 Phantom Read가 안 일어나나요?
*   **답변**: InnoDB는 **Next-Key Lock**(Record Lock + Gap Lock)이라는 기술을 사용하여 `INSERT`가 발생할 수 있는 '간격'까지 잠가버립니다. 또한 **MVCC**를 통해 스냅샷 읽기를 수행하므로 일반적인 `SELECT`에서는 Phantom Read가 발생하지 않습니다.
*   **주의**: `SELECT ... FOR UPDATE` 같은 배타적 잠금 읽기 시에는 실제 잠금이 걸리며 Phantom Read를 방지합니다.

## 4. 실무 예시 시나리오

### [은행 송금 시스템: Read Committed 권장]
*   **상황**: A가 B에게 10만원을 송금하는 중.
*   **문제**: 만약 `Read Uncommitted`라면, A의 잔액이 차감된 **커밋 전** 상태를 다른 트랜잭션이 읽어 잘못된 통계를 낼 수 있습니다.
*   **해결**: `Read Committed` 이상을 사용하여 커밋된 확정 데이터만 처리해야 합니다.

### [재고 수량 정합성: Repeatable Read 활용]
*   **상황**: 쇼핑몰에서 남은 재고를 확인하고 결제하는 과정.
*   **문제**: 재고를 확인(`SELECT`)한 후 결제 직전에 다른 트랜잭션이 재고를 수정하면 데이터가 꼬일 수 있습니다.
*   **해결**: MySQL의 기본값인 `Repeatable Read`를 사용하거나, `FOR UPDATE`를 활용한 명시적 잠금으로 데이터 정합성을 확보합니다.

### 요약
> **격리 수준 선택은 성능(Performance)과 정합성(Consistency) 사이의 저울질입니다.**
> 서비스의 특성에 따라 기본값을 사용하거나, 특정 트랜잭션에만 더 높은 격리 수준 혹은 잠금을 적용하여 최적의 성능을 끌어내는 것이 백엔드 개발자의 실력입니다.
