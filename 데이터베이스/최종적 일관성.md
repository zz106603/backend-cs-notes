### 최종적 일관성 (Eventual Consistency)

**1. 개념**
*   **정의**: 분산 시스템에서 데이터 변경 사항이 즉시 모든 노드에 반영되지 않더라도, **시간이 지나면 결국(Eventually) 모든 노드가 동일한 데이터(Consistent)를 갖게 되는 성질**을 의미
*   **목적**: 강한 일관성(Strong Consistency)을 포기하는 대신 **높은 가용성(High Availability)과 성능**을 확보하기 위해 사용 (CAP 이론의 AP 시스템에 해당)
*   **특징**:
    *   데이터 변경 시 비동기적으로 다른 노드에 전파됨
    *   따라서 일시적으로 노드 간 데이터 불일치가 발생할 수 있음
    *   사용자는 최신 데이터가 아닌 과거 데이터를 잠시 조회할 수도 있음

**2. 실무 예시 (시나리오)**

최종적 일관성은 "실시간성보다 시스템이 죽지 않고 응답하는 것이 더 중요한 서비스"에서 주로 사용됨

*   **SNS 타임라인 (페이스북, 인스타그램)**
    *   **상황**: 사용자가 게시글을 작성하거나 '좋아요'를 누름
    *   **현상**: 내 친구의 피드에는 이 게시글이 1~2초 뒤에 뜨거나, 새로고침을 해야 보일 수 있음
    *   **이유**: 전 세계 수많은 서버에 데이터를 즉시 동기화하는 것보다, 일부 사용자에게 조금 늦게 보이더라도 글 쓰기/읽기 기능이 멈추지 않는 것이 중요하기 때문

*   **유튜브 조회수**
    *   **상황**: BTS의 신곡이 발표되어 전 세계에서 동시에 접속
    *   **현상**: 영상 밑의 조회수는 `123,456회`로 표시되지만, 실제 데이터베이스에 집계된 정확한 수치는 `130,000회`일 수 있음. 각 지역 캐시 서버의 조회수가 중앙 서버로 합산되기까지 시간이 걸림
    *   **이유**: 조회수 1의 오차를 없애기 위해 영상을 못 보게 막는 것보다, 조회수가 조금 틀리더라도 영상을 끊김 없이 보여주는 것이 비즈니스적으로 중요함

*   **DNS (도메인 네임 시스템)**
    *   **상황**: 웹사이트의 IP 주소를 변경
    *   **현상**: 어떤 사람은 새 IP로 접속되지만, 어떤 사람은 여전히 옛날 IP로 접속을 시도함 (TTL 시간 동안 캐시됨)
    *   **이유**: 전 세계 모든 네임 서버에 변경 사항이 전파되는 데 시간이 걸리지만, 결국에는 모든 사용자가 변경된 IP로 접속하게 됨

**3. 강한 일관성(Strong Consistency)과의 비교**

| 특징 | 최종적 일관성 (Eventual Consistency) | 강한 일관성 (Strong Consistency) |
| :--- | :--- | :--- |
| **보장 내용** | 시간이 지나면 같아짐 | 언제나 최신 데이터 보장 |
| **동작 방식** | 변경 사항을 **비동기** 복제 | 변경 완료 전까지 읽기 **차단** (Lock) |
| **장점** | 높은 가용성 (빠른 응답) | 데이터 정확성 (신뢰성) |
| **단점** | 일시적 데이터 불일치 | 성능 저하, 응답 지연 가능성 |
| **사용 예시** | SNS, DNS, 댓글, 조회수 | 은행 계좌 이체, 재고 관리(결제 직전) |

**4. 결론**
*   실무에서는 **"이 데이터가 지금 당장 100% 정확해야 하는가?"** 를 기준으로 판단함 
*   만약 은행 잔고처럼 틀리면 큰일 나는 데이터는 강한 일관성을 유지해야 하지만, SNS 피드처럼 약간의 지연이 허용되는 서비스는 최종적 일관성을 선택하여 시스템의 성능과 안정성을 높이는 것이 일반적
