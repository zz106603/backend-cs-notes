# RDB 페이징 쿼리 (Paging Query)

대용량 데이터를 다루는 백엔드 시스템에서 페이징 쿼리는 선택이 아닌 필수

한 번에 수백만 건의 데이터를 조회하면 DB 부하, 네트워크 트래픽 증가, 애플리케이션 메모리 부족(OOM) 등 심각한 장애로 이어질 수 있기 때문임

---

## 1. 페이징 쿼리의 필요성 (실무 관점)

### 1) DB 리소스 효율화
*   **상황**: `SELECT * FROM orders` 처럼 조건 없이 전체 데이터를 조회하면, DB는 디스크에서 엄청난 양의 데이터를 읽어 메모리(Buffer Pool)에 올려야 함
*   **효과**: 필요한 만큼만 잘라서 조회하면 I/O 비용을 획기적으로 줄이고, 다른 쿼리를 처리할 여유 리소스를 확보할 수 있음

### 2) 애플리케이션 안정성 확보
*   **상황**: 100만 건의 주문 내역을 한 번에 List 객체로 로딩하면 힙 메모리가 가득 차서 `OutOfMemoryError`가 발생하고 서버가 다운될 수 있음
*   **효과**: 100건씩 나누어 조회하면 메모리 사용량을 예측 가능한 범위 내로 통제할 수 있음

### 3) 사용자 경험 (UX) 및 응답 속도 개선
*   **상황**: 게시판 목록을 보는데 10초가 걸린다면 사용자는 이탈함
*   **효과**: 첫 페이지(1~20번 게시글)만 빠르게 보여주면 사용자는 즉각적인 반응을 얻을 수 있음

---

## 2. 전통적인 방식: OFFSET & LIMIT

가장 흔하게 사용되는 방식이지만, 데이터가 많아질수록 치명적인 성능 문제가 발생

```sql
SELECT * 
FROM orders 
ORDER BY id DESC 
LIMIT 10 OFFSET 1000000;
```

### 문제점: "앞에서부터 다 읽고 버린다"
*   위 쿼리는 1,000,010건을 읽은 뒤, 앞의 1,000,000건을 버리고 마지막 10건만 반환함
*   **OFFSET이 커질수록 쿼리 속도는 선형적으로 느려짐** (Full Table Scan에 가까운 비용 발생)
*   실무에서는 데이터가 적은 초반에는 잘 동작하다가, 서비스가 성장하면서 갑자기 느려지는 시한폭탄이 될 수 있음

---

## 3. 성능 최적화: No-Offset (Keyset Pagination)

OFFSET의 성능 문제를 해결하기 위해, **"마지막으로 조회한 위치"** 를 조건으로 사용하는 방식

이를 **No-Offset** 또는 **Keyset Pagination**이라고 부름

### 동작 원리
*   페이지 번호(3페이지, 4페이지)로 이동하는 것이 아니라, **"이전 페이지의 마지막 데이터 다음부터 보여줘"** 라고 요청함
*   인덱스를 효율적으로 탈 수 있어 데이터 양이 아무리 많아져도 조회 속도가 일정하게 빠름

### 쿼리 예시
직전 페이지의 마지막 주문 ID가 `999,900`이었다면, 다음 페이지 쿼리는 아래와 같음

```sql
SELECT * 
FROM orders 
WHERE id < 999900  -- 이전 페이지의 마지막 ID보다 작은 것들 (내림차순 기준)
ORDER BY id DESC 
LIMIT 10;
```

*   **장점**: `OFFSET`을 건너뛰는 과정 없이 인덱스를 타고 바로 해당 위치로 이동하므로 매우 빠름
*   **단점**: "10페이지로 바로 이동" 같은 랜덤 액세스 기능은 구현하기 어려움 (주로 "더 보기" 버튼이나 무한 스크롤 UI에 적합)

---

## 4. 또 다른 방법: 슬라이딩 윈도우 (Sliding Window)

엄밀히 말하면 페이징 기법이라기보다, **대량의 데이터를 일괄 처리(Batch)** 할 때 사용하는 패턴

### 개념
*   전체 데이터를 처리해야 하는데 한 번에 로딩할 수 없을 때, 창문(Window)을 옆으로 밀듯이 데이터를 조금씩 이동하며 처리하는 방식
*   주로 ID 범위를 기준으로 데이터를 잘라서 처리함

### 실무 활용 예시: "전체 회원에게 포인트 지급하기"
회원이 1,000만 명일 때, `LIMIT/OFFSET`으로 처리하면 뒤로 갈수록 느려짐. 대신 ID 범위를 지정하여 처리함

1.  **1회차**: `SELECT * FROM users WHERE id BETWEEN 1 AND 10000`
2.  **2회차**: `SELECT * FROM users WHERE id BETWEEN 10001 AND 20000`
3.  ... 반복 ...

이 방식은 인덱스(PK)를 활용하므로 처음부터 끝까지 일정한 속도로 데이터를 처리할 수 있음
