# 데이터베이스 인덱스 (Database Index)

데이터베이스의 조회 성능을 비약적으로 향상시키기 위해 특정 컬럼을 기준으로 정렬된 자료구조를 생성하여 관리하는 기술

---

## 1. 인덱스의 핵심 원리

### 1) 왜 정렬이 중요한가?
인덱스는 책의 맨 뒤에 있는 **'색인'** 과 같음. 전체 페이지를 다 읽지 않아도 특정 단어가 어느 페이지에 있는지 바로 알 수 있는 이유는 색인이 **가나다순으로 정렬**되어 있기 때문임

### 2) B-Tree / B+Tree 구조
대부분의 관계형 데이터베이스(RDBMS)는 **B+Tree** 구조를 사용함
*   **조회 성능**: 데이터가 정렬된 상태를 유지하므로 이진 탐색과 유사한 원리로 조회 성능을 **O(log N)** 으로 보장함
*   **범위 검색**: 리프 노드(Leaf Node)끼리 연결 리스트로 이어져 있어 `BETWEEN`이나 `>` 같은 범위 검색에 매우 강력함

### 3) 클러스터드 vs 논-클러스터드 인덱스
*   **클러스터드 인덱스 (Clustered Index)**: 테이블당 하나만 존재(보통 PK). 실제 데이터 자체가 인덱스 순서로 물리적으로 정렬되어 저장됨
*   **논-클러스터드 인덱스 (Non-Clustered Index)**: 테이블당 여러 개 가능. 별도의 인덱스 페이지를 생성하며, 리프 노드에는 실제 데이터의 주소값(또는 PK)을 가짐

## 2. 인덱스 설계의 핵심 원칙 (실무 포인트)

### 1) 카디널리티 (Cardinality)가 높은 컬럼 선택
카디널리티는 **값의 중복도가 낮은 정도**를 말함
*   **Good**: 주민등록번호, 이메일, 유저 ID (중복이 거의 없음)
*   **Bad**: 성별(남/여), 활성화 여부(Y/N) (중복이 매우 많음)
*   **이유**: 인덱스로 걸러낸 후 남은 데이터 양이 적어야 인덱스 효율이 극대화 됨

### 2) 복합 인덱스 (Composite Index)의 순서
복합 인덱스는 컬럼의 순서가 성능을 결정하며, **"왼쪽 우선순위(Leftmost Prefix)"** 원칙을 따름

*   **인덱스 설정**: `(city, age)`
*   **활용 가능**: `WHERE city = 'Seoul'`, `WHERE city = 'Seoul' AND age = 20`
*   **활용 불가**: `WHERE age = 20` (첫 번째 컬럼인 city가 없으면 인덱스를 타지 못함)

## 3. 실무 예시 및 쿼리 최적화

### 1) 커버링 인덱스 (Covering Index)
실제 데이터 테이블에 접근하지 않고 **인덱스에 포함된 정보만으로 쿼리를 완료**하는 방식

```sql
-- 인덱스: (email, username)
-- 테이블 접근 없이 인덱스 페이지만 읽고 즉시 반환 (매우 빠름)
SELECT email, username 
FROM users 
WHERE email = 'test@test.com';
```

### 2) 인덱스를 타지 못하는 나쁜 쿼리 예시
인덱스가 걸려 있어도 다음과 같이 작성하면 **Full Table Scan**이 발생할 수 있음

```sql
-- 1. 컬럼을 가공하는 경우
SELECT * FROM users WHERE age * 10 > 200; -- (X)
SELECT * FROM users WHERE age > 20;       -- (O)

-- 2. LIKE 전방 일치(%)가 아닌 경우
SELECT * FROM users WHERE name LIKE '%kim'; -- (X)
SELECT * FROM users WHERE name LIKE 'kim%'; -- (O)

-- 3. 부정형 조건 (인덱스 효율이 극히 낮음)
SELECT * FROM users WHERE status != 'DELETED';
```

## 4. 인덱스 확인 및 관리

### 1) 실행 계획 (EXPLAIN) 확인
백엔드 개발자는 쿼리 앞에 `EXPLAIN`을 붙여서 인덱스가 실제로 사용되는지 확인하는 습관을 가져야 함

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 100;
```
*   `type`: `const`, `ref`, `range` 등이 나오면 인덱스를 잘 타는 것
*   `type`: `ALL`이 나오면 **Full Table Scan**이므로 튜닝이 필요함

### 2) 인덱스의 오버헤드 (Trade-off)
*   **쓰기 성능 저하**: `INSERT`, `UPDATE`, `DELETE` 시마다 인덱스 트리도 재정렬해야 하므로 쓰기 작업이 느려짐
*   **저장 공간**: 인덱스 역시 물리적인 저장 공간을 차지하므로 무분별한 인덱스 생성은 DB 용량 낭비를 초래함

## 요약 가이드

| 구분 | 인덱스 적용 전 | 인덱스 적용 후 |
| :--- | :--- | :--- |
| **조회 성능** | O(N) (Full Scan) | O(log N) (Index Scan) |
| **쓰기 성능** | 빠름 (데이터만 추가) | 느림 (인덱스 트리 갱신 필요) |
| **추천 컬럼** | - | 카디널리티가 높은 컬럼, WHERE/JOIN/ORDER BY에 자주 쓰이는 컬럼 |

### 결론
> **인덱스는 "읽기" 성능을 위해 "쓰기" 성능과 "공간"을 지불하는 트레이드오프 기술임.**
> 서비스의 조회 패턴을 분석하여 **읽기 부하가 높은 핵심 쿼리**를 타겟으로, 카디널리티와 복합 인덱스 순서를 고려한 **정예 인덱스**를 설계하는 것이 중요함
