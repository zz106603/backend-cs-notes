# MySQL 스키마 설계, SQL 작성, 인덱스 및 쿼리 최적화

## MySQL 스키마 설계

스키마 설계는 데이터를 어떤 테이블에 저장하고 테이블 간 관계와 제약조건을 어떻게 설정할지 정의하는 과정

- 데이터의 중복을 최소화하고 무결성을 유지할 수 있는가?
- 테이블 사이의 관계가 올바르게 표현되는가?
- 자주 수행하는 조회와 수정 작업에 적합한 구조인가?
- 데이터가 늘어나도 유지보수하기 편리한가?

### PK, FK, UNIQUE, NOT NULL

| 제약조건 | 역할 | 예시 |
| --- | --- | --- |
| PRIMARY KEY | 행을 고유하게 식별, NULL 불가 | 회원 ID |
| FOREIGN KEY | 다른 테이블과의 참조 무결성 유지 | 예약의 회원 ID |
| UNIQUE | 중복 값 제한 | 회원 이메일 |
| NOT NULL | NULL 저장 방지 | 예약 생성일 |

### PK와 UNIQUE 차이

- PK는 테이블에서 행을 식별하는 기본 키이며 테이블당 하나의 PK 제약조건만 정의할 수 있음
- UNIQUE는 다른 컬럼의 중복을 방지할 때 사용하며 여러 개를 정의할 수 있음

### FK를 사용하는 이유와 단점

- FK는 존재하지 않는 회원의 예약이 생성되는 등의 문제를 DB 수준에서 방지
- 다만 데이터를 INSERT, UPDATE, DELETE할 때 참조 무결성 검사에 따른 비용이 발생하며 테이블 간 의존성이 생김
    - `RESTRICT`: 참조하는 데이터가 있으면 삭제를 막음
    - `CASCADE`: 부모 데이터 삭제 시 관련 자식 데이터도 삭제
    - `SET NULL`: 부모 삭제 시 자식의 FK 값을 NULL로 변경. FK 컬럼이 NULL을 허용해야 함

### 테이블 관계

#### 1:1 관계

- 하나의 회원이 하나의 회원 상세정보를 가지는 관계
- 상세정보 테이블에 회원 ID를 FK로 두고 UNIQUE 제약조건으로 중복 연결을 막을 수 있음

#### 1:N 관계

- 한 명의 회원이 여러 건의 예약을 생성하는 관계
- 일반적으로 N쪽 테이블에 FK를 둠

#### N:M 관계

- 하나의 상품이 여러 주문에 포함되고, 하나의 주문에도 여러 상품이 포함되는 관계
- 중간 테이블을 만들어 두 개의 1:N 관계로 표현

### 정규화와 반정규화

#### 정규화

데이터 중복을 줄이고 삽입, 수정, 삭제 시 발생하는 이상 현상을 방지하기 위해 테이블을 분리하는 과정

- 1NF: 각 컬럼이 원자적인 값을 갖도록 구성
- 2NF: 1NF를 만족하고 기본 키 일부에만 종속되는 속성 제거
- 3NF: 2NF를 만족하고 기본 키가 아닌 속성 사이의 이행적 종속 제거

ex) 여러 예약 행에 회원의 이름과 연락처를 반복 저장하면 회원 연락처 변경 시 여러 행을 수정해야 함. 회원 정보를 별도 테이블로 분리하면 이런 문제를 줄일 수 있음

#### 반정규화

조회 성능이나 운영상 요구를 위해 중복 데이터를 허용하거나 테이블을 합치는 방식

ex) 자주 조회하는 주문 총액을 매번 주문 항목에서 계산하지 않고 주문 테이블에 저장. 다만 항목이 변경되었을  때 총액도 일치하도록 관리해야 함

> 일반적으로 정규화를 기본으로 하되, 실제 조회 병목과 데이터 정합성 유지 비용을 고려해 반정규화를 검토
>

## SQL 핵심 문법

### JOIN

서로 다른 테이블의 데이터를 연결해 조회하는 방법

- `INNER JOIN`: 조인 조건에 일치하는 행만 조회
- `LEFT JOIN`: 왼쪽 테이블의 모든 행을 유지하고 오른쪽에 일치하는 행이 없으면 해당 컬럼을 NULL로 반환

```java
SELECT m.name, r.id
FROM members m
INNER JOIN reservations r
    ON m.id = r.member_id;
```

- 예약이 존재하는 회원의 이름과 예약 ID를 조회
- 예약이 없는 회원은 결과에 포함되지 않음
- `LEFT JOIN`으로 변경하면 예약이 없는 회원도 조회되며 예약 ID는 NULL이 됨
- 단, LEFT JOIN에서 오른쪽 테이블에 대한 조건을 WHERE에 잘못 작성하면 NULL 행이 제외돼 INNER JOIN처럼 동작할 수 있음

### GROUP BY와 HAVING

`GROUP BY`는 데이터를 특정 컬럼으로 묶어 집계할 때 사용

`HAVING`은 집계된 결과에 조건을 적용

```java
SELECT member_id, COUNT(*) AS count
FROM reservations
WHERE status = 'CONFIRMED'
GROUP BY member_id
HAVING COUNT(*) >= 2;
```

- 확정 예약이 2건 이상인 회원의 ID와 예약 건수를 조회

#### WHERE와 HAVING의 차이

- WHERE: 그룹화 이전에 개별 행을 필터링
- HAVING: 그룹화한 이후 집계 결과를 필터링

조건을 GROUP BY 이전에 처리할 수 있다면 일반적으로 WHERE를 사용하는 것이 불필요한 집계 대상을 줄이는 데 유리

### SQL 논리적 처리 순서

```java
FROM / JOIN
    ↓
WHERE
    ↓
GROUP BY
    ↓
HAVING
    ↓
SELECT
    ↓
ORDER BY
    ↓
LIMIT
```

## 인덱스와 쿼리 최적화

### 인덱스

- 테이블의 특정 컬럼을 기준으로 검색을 빠르게 수행하도록 만든 자료구조
- 책의 목차나 색인처럼 전체 데이터를 순차적으로 확인하지 않고 원하는 데이터를 효율적으로 찾는 데 활용
- MySQL의 InnoDB에서는 일반적인 인덱스에 B+Tree 구조를 사용

**장점**

- 조건에 맞는 데이터 검색 속도 개선
- 범위 검색과 정렬에 활용 가능
- 적절한 인덱스를 통해 불필요한 데이터 접근 감소

**단점**

- 별도의 저장 공간 사용
- INSERT, UPDATE, DELETE 시 인덱스 유지 비용 발생
- 인덱스가 많다고 항상 조회 성능이 좋아지는 것은 아님

### B+Tree의 기본 구조

!download.svg

- 상위 노드에서 탐색 범위를 좁혀 리프 노드에 도달
- 리프 노드들은 순서대로 연결되어 있어 범위 조회에도 유리함
- InnoDB 기준으로는 PK는 클러스터드 인덱스를 구성하고, 보조 인덱스의 리프에는 해당 행을 찾기 위한 PK 값이 포함

### 단일 인덱스와 복합 인덱스

단일 인덱스는 하나의 컬럼을 기준으로 구성

```java
CREATE INDEX idx_member_id
ON reservations(member_id);
```

복합 인덱스는 여러 컬럼을 조합

```java
CREATE INDEX idx_member_status_date
ON reservations(member_id, status, created_at);
```

#### 복합 인덱스는 컬럼 순서가 중요

ex) `(member_id, status, created_at)`

| 조회 조건 | 인덱스 활용 |
| --- | --- |
| member_id | 효율적으로 활용 가능 |
| member_id + status | 효율적으로 활용 가능 |
| member_id + status + created_at | 효율적으로 활용 가능 |
| status만 조회 | 선두 컬럼이 없어 대체로 불리 |
| created만 조회 | 선두 컬럼이 없어 대체로 불리 |
- 이를 **왼쪽 접두어 원칙(Leftmost Prefix)**이라고 함
- 다만 MySQL 옵티마이저가 예외적으로 다른 접근 방식을 선택할 수 있으므로, 실제 사용 여부는 실행 계획으로 확인해야 함

### 인덱스 컬럼 순서

ex)

```java
SELECT *
FROM reservations
WHERE member_id = 10
  AND status = 'CONFIRMED'
ORDER BY created_at DESC
LIMIT 20;
```

```java
CREATE INDEX idx_reservation_search
ON reservations(member_id, status, created_at DESC);
```

1. `member_id`와 `status`는 동등 비교 조건
2. 두 컬럼으로 검색 범위를 좁힙
3. `create_at DESC`는 최신순 정렬에 사용
4. 적절한 실행 계획이 선택되면 별도 정렬 비용을 줄일 수 있음

단, 두 동등 비교 컬럼의 순서는 해당 쿼리 하나만으로 단정하지 않음. 다른 조회 패턴과 컬럼별 데이터 분포까지 고려해야 함

또한 인덱스가 있어도 데이터 분포, 조회 건수, 선택한 컬럼에 따라 전체 테이블 조회가 더 유리할 수 있음

### 인덱스를 사용해도 성능 개선이 어려운 이유

- 조회 조건에 맞는 행이 너무 많아 상당수 데이터를 읽어야 하는 경우
- 인덱스 선두 컬럼을 효율적으로 사용할 수 없는 경우
- 인덱스 컬럼에 함수를 적용해 일반적인 인덱스 탐색이 어려워지는 경우
- `LIKE '$keyword'`처럼 문자열 앞에 와일드카드가 있는 경우
- 인덱스를 사용하더라도 많은 행을 추가로 조회해야 하는 경우

인덱스를 생성하면 검색에는 도움이 될 수 있지만 쓰기 작업의 비용과 저장 공간이 증가하므로 조회 빈도와 데이터 분포를 함께 고려해야 함

### EXPLAIN과 실행 계획

MySQL이 SQL을 어떻게 실행할 계획인지 확인하는 기능

```java
EXPLAIN
SELECT *
FROM reservations
WHERE member_id = 10;
```

| **항목** | **의미** |
| --- | --- |
| type | 테이블에 접근하는 방식 |
| possible_keys | 사용 후보가 되는 인덱스 |
| key | 실제 선택한 인덱스 |
| rows | 읽을 것으로 추정하는 행 수 |
| Extra | 추가적인 실행 정보 |

#### type에서 알아둘 값

- `ALL`: 전체 테이블 스캔
- `range`: 인덱스를 활용한 범위 검색
- `ref`: 인덱스의 비고유 값 등을 이용한 조회
- `const`: PK 또는 UNIQUE 인덱스로 최대 한 행을 찾는 등의 조회

ALL이 무조건 나쁜 것은 아님. 데이터가 적거나 조건에 맞는 행이 대부분이면 전체 스캔이 더 효율적일 수 있음

`Extra`의 `Using filesort`는 인덱스 순서만으로 정렬을 해결하지 못해 별도 정렬 처리가 필요하다는 뜻. 반드시 디스크에 파일을 생성한다는 뜻은 아님

#### 쿼리가 느릴 때 확인 순서

1. 실행 시간과 느린 쿼리 확인
2. EXPLAIN으로 접근 방식과 사용 인덱스 확인
3. 읽을 것으로 예상되는 행 수와 필터 조건 검토
4. 인덱스 또는 쿼리 수정 검토
5. 변경 전후 실행 시간과 실행 계획 비교
