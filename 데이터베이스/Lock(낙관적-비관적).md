# 낙관적 락 vs 비관적 락

동시성 제어(Concurrency Control)는 여러 트랜잭션이 동일한 데이터에 동시에 접근할 때 데이터의 무결성을 지키기 위한 필수적인 기법

그중 대표적인 두 가지 방법이 바로 **낙관적 락**과 **비관적 락**

---

### 두 락의 차이를 화장실 사용법에 비유

*   **비관적 락 (Pessimistic Lock)  Pessimistic = 비관적인**
    > "분명 누가 들어올 거야. 일단 문부터 잠그고 보자."
    *   **동작 방식**: 데이터에 접근하기 전에 먼저 락을 걸어 다른 사람의 접근을 막음
    *   **핵심**: 충돌을 **미리 예방**


*   **낙관적 락 (Optimistic Lock) Optimistic = 낙관적인**
    > "아무도 안 쓰겠지? 일단 들어가서 쓰고, 나올 때 다른 사람이 쓴 흔적이 있으면 그때 해결하자."
    *   **동작 방식**: 일단 락 없이 작업을 시작하고, 작업을 마친 후 데이터를 수정할 때 다른 사람이 먼저 수정했는지 확인
    *   **핵심**: 충돌 발생 시 **감지하고 처리**

---

## 1. 비관적 락 (Pessimistic Lock)

데이터 경합이 자주 발생할 것이라고 비관적으로 가정하고, 데이터베이스가 제공하는 명시적인 락 기능을 사용함

### 실무 예시: "재고 관리 시스템"

**상황**: 인기 상품의 재고가 딱 1개 남았습니다. 동시에 여러 사용자가 이 상품을 주문하려고 합니다.

**동작 시나리오**:
1.  **사용자 A**가 주문을 시작하며 트랜잭션을 염
2.  재고를 확인하고 차감하기 위해, 데이터베이스에 해당 상품의 row에 **배타 락(Exclusive Lock)** 을 검
    *   `SELECT * FROM products WHERE id = 100 FOR UPDATE;`
3.  **사용자 B**가 동시에 주문을 시도하며 `FOR UPDATE`로 같은 row를 읽으려고 함
4.  하지만 사용자 A의 트랜잭션이 락을 쥐고 있으므로, **사용자 B는 락이 풀릴 때까지 대기(Wait) 상태**가 됨
5.  사용자 A가 재고를 1에서 0으로 변경하고 트랜잭션을 커밋(Commit)함. 락이 해제됨
6.  대기하던 사용자 B의 트랜잭션이 락을 얻고 row를 읽음. 하지만 재고는 이미 0이므로 "재고 부족" 처리를 하게 됨

> **결과**: 데이터 정합성이 완벽하게 지켜짐. 중복 결제나 마이너스 재고 같은 문제가 발생하지 않음

*   **장점**: 데이터 무결성을 확실하게 보장
*   **단점**: 락으로 인해 다른 트랜잭션이 대기하므로, 동시성이 떨어져 전체적인 시스템 성능 저하를 유발할 수 있음. 락이 길어지면 데드락의 원인이 되기도 함

---

## 2. 낙관적 락 (Optimistic Lock)

데이터 경합이 거의 발생하지 않을 것이라고 낙관적으로 가정하고, 데이터베이스 락 대신 애플리케이션 레벨에서 충돌을 감지함

### 실무 예시: "블로그 게시글 수정"

**상황**: 여러 관리자가 동시에 같은 게시글을 수정할 수 있습니다. 하지만 실제로 동시에 수정 버튼을 누를 확률은 매우 낮습니다.

**동작 시나리오**:
1.  `posts` 테이블에 `version`이라는 숫자 타입 컬럼을 추가함
2.  **관리자 A**가 ID가 1인 게시글을 수정하기 위해 "수정 페이지"에 들어감. 이때 애플리케이션은 게시글 내용과 함께 `version` 값(예: 5)을 읽어옴
3.  **관리자 B**도 거의 동시에 같은 게시글의 "수정 페이지"에 들어감. 역시 `version` 값 5를 읽어옴
4.  **관리자 A**가 수정을 마치고 "저장" 버튼을 누릅니다. 애플리케이션은 아래와 같은 쿼리를 실행함
    *   `UPDATE posts SET content = '수정된 내용 A', version = version + 1 WHERE id = 1 AND version = 5;`
    *   조건(`version = 5`)이 일치하므로 UPDATE는 성공하고, 1개의 row가 변경됨. 데이터베이스의 `version`은 6이 됨
5.  잠시 후, **관리자 B**도 수정을 마치고 "저장" 버튼을 누름. 애플리케이션은 똑같은 형식의 쿼리를 실행함
    *   `UPDATE posts SET content = '수정된 내용 B', version = version + 1 WHERE id = 1 AND version = 5;`
    *   하지만 데이터베이스의 `version`은 이미 6으로 변경된 상태. 조건(`version = 5`)이 불일치하여 **UPDATE는 실패하고, 0개의 row가 변경**됨
6.  애플리케이션은 UPDATE 결과가 0임을 확인하고, 관리자 B에게 "다른 사용자가 먼저 글을 수정했습니다. 페이지를 새로고침한 후 다시 시도해주세요." 라는 메시지를 보여줌

> **결과**: 불필요한 락 대기 없이 높은 동시성을 확보하면서도, 충돌이 발생했을 때 데이터를 덮어쓰는 문제를 막을 수 있음

*   **장점**: 락을 잡지 않으므로 읽기 성능이 좋고, 전체적인 시스템 처리량이 높음
*   **단점**: 충돌이 발생하면 애플리케이션에서 롤백 및 재시도 로직을 직접 구현해야 함. 충돌이 잦은 환경에서는 오히려 재시도 비용 때문에 성능이 더 나빠질 수 있음

---

## 3. 언제 무엇을 써야 할까?

| 구분 | **비관적 락 (Pessimistic Lock)**     | **낙관적 락 (Optimistic Lock)**          |
| :--- |:---------------------------------|:-------------------------------------|
| **가정** | 충돌이 **자주** 일어난다.                 | 충돌이 **거의** 일어나지 않는다.                 |
| **적합한 환경** | **쓰기(Write)** 가 많고, 충돌 확률이 높은 경우 | **읽기(Read)** 가 대부분이고, 가끔 쓰기가 일어나는 경우 |
| **대표 예시** | 재고 관리, 티켓 예매, 계좌 이체              | 게시글 수정, 위키 문서 편집                     |
| **장점** | 데이터 무결성 보장                       | 높은 동시성, 좋은 성능                        |
| **단점** | 성능 저하, 데드락 가능성                   | 개발자가 직접 재시도 처리 필요                    |
