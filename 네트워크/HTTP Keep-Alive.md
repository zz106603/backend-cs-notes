### Keep-Alive (연결 유지)

**정의**
- 네트워크 통신에서 **연결(Connection)을 끊지 않고 계속 유지**하여 성능을 높이거나 상태를 확인하는 기술
- HTTP와 TCP 두 계층에서 각각 다른 목적으로 사용됨

---

### 1. HTTP Keep-Alive (성능 최적화)

**목적:** **"매번 연결하기 귀찮으니까 한 번 연결해서 뽕을 뽑자"**
- 웹 페이지 하나를 로딩하려면 HTML, CSS, JS, 이미지 등 수십 개의 파일이 필요함
- 예전(HTTP/1.0)에는 파일 하나 받을 때마다 `연결 -> 요청 -> 응답 -> 끊기`를 반복 (비효율)
- **Keep-Alive (HTTP/1.1~):** 한 번 연결(`TCP Handshake`)하면, 그 연결 통로를 닫지 않고 계속 재사용해서 나머지 파일들도 다 받아옴

**동작 방식**
1.  클라이언트: `Connection: keep-alive` 헤더를 보내서 "나 아직 볼일 남았어, 끊지 마"라고 알림
2.  서버: 요청 처리 후 연결을 유지한 채로 응답을 보냄 (`Keep-Alive: timeout=5, max=100` 헤더로 유지 시간과 최대 요청 수 알려줌)
3.  일정 시간(Timeout) 동안 추가 요청이 없으면 연결을 끊음

**장점**
- **속도 향상:** 반복적인 3-Way Handshake 시간을 아낄 수 있음 (RTT 감소)
- **서버 부하 감소:** 연결/해제 과정에서 발생하는 CPU, 메모리 소모를 줄임

**단점**
- **동시 접속자 수 제한:** 놀고 있는(Idle) 연결도 계속 유지해야 하므로, 접속자가 많으면 서버의 가용 소켓이 금방 소모될 수 있음

---

### 2. TCP Keepalive (상태 확인)

**목적:** **"너 아직 살아있니? (좀비 연결 정리)"**
- 연결된 상태에서 오랫동안 아무 데이터도 안 주고받으면, 중간에 랜선이 뽑혔는지 상대방 PC가 꺼졌는지 알 방법이 없음
- 이를 확인하기 위해 운영체제(OS) 레벨에서 주기적으로 빈 패킷(Probe)을 보내봄

**동작 방식**
1.  일정 시간(기본 2시간, 설정 가능) 동안 데이터 교환이 없으면, OS가 자동으로 **Keepalive Probe** 패킷을 보냄
2.  상대방이 `ACK`를 보내면 "아, 살아있구나" 하고 연결 유지
3.  응답이 없으면 몇 번 더 보내보고, 그래도 없으면 연결을 강제로 끊음 (Dead Connection 정리)

**실무 예시: DB 커넥션 풀**
- WAS(스프링)와 DB 사이의 연결이 방화벽에 의해 끊겼는데, WAS는 그걸 모르고 있다가 요청을 보내면 에러가 터짐
- 이를 방지하기 위해 TCP Keepalive 설정을 켜두거나, 커넥션 풀(HikariCP)에서 `validationQuery`를 날려서 연결 상태를 주기적으로 확인함

### 요약: HTTP vs TCP 차이점

| 구분 | HTTP Keep-Alive | TCP Keepalive |
| :--- | :--- | :--- |
| **계층** | 7계층 (Application) | 4계층 (Transport) |
| **주체** | 웹 브라우저, 웹 서버 | 운영체제 (Kernel) |
| **목적** | **성능 최적화** (재사용) | **연결 상태 확인** (좀비 정리) |
| **방식** | 헤더(`Connection: keep-alive`) 사용 | 주기적인 빈 패킷(Probe) 전송 |
| **기본값** | HTTP/1.1부터 기본 활성화 (On) | 보통 기본 비활성화 (Off) |

**실무 팁:**
- 웹 서비스 성능을 높이려면 **Nginx** 같은 웹 서버에서 `keepalive_timeout` 설정을 적절히 조절해야 함 (너무 길면 소켓 고갈, 너무 짧으면 재연결 비용 발생)
- DB 연결 끊김 문제를 겪는다면 **TCP Keepalive** 설정이나 커넥션 풀의 `maxLifetime` 설정을 확인
