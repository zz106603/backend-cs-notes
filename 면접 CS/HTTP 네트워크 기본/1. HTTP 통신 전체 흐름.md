## HTTP 통신 전체 흐름

### HTTP 등장 이유

> HTTP (HyperText Transfer Protocol)는 **클라이언트와 서버가 데이터를 주고받기 위한 약속**(Protocol)
>

ex) 브라우저에서 로그인 버튼 클릭

- Client → 로그인 요청 → Server → 성공/실패 응답 → Client
- 어떤 형식으로 요청/응답할지, 성공/실패를 어떻게 표현할지 규칙이 필요함

---

### Protocol 필요 이유

- Protocol = 통신 규약

```java
POST /login HTTP/1.1
Content-Type: application/json

{
  "id": "user1",
  "password": "1234"
}
```

- 서버는 이 구조를 보고 해석이 가능함

---

### HTTP의 핵심 특징

#### 1. Stateless

- HTTP는 기본적으로 상태를 기억하지 않음
    - ex) Request 1: 로그인
    - ex) Request 2: 게시글 조회
    - 서버는 Reqeust 2만 보고는 로그인 한 사용자인지 모름
    - HTTP 요청은 각각 독립적
- 상태를 들고 있지 않으면 서버 확장이 쉬워짐
    - Stateful
        - User A가 Server 1에 로그인 정보를 저장하면 Server 2에는 로그인 정보 없음
    - Stateless
        - 인증 정보(JWT 등)를 매 요청마다 보내면 어느 서버가 받아도 처리 가능
        - Scale-out 유리
        - Load balancing 유리

#### 2. Request / Response 구조

- HTTP는 항상 Request → Response 패턴 (웹소켓은 예외)
- **Request 구조**

    ```java
    POST /login HTTP/1.1
    Host: example.com
    Authorization: Bearer xxx
    Content-Type: application/json
    
    {
      "email": "a@test.com"
    }
    ```

    - **Start Line**
        - POST /login HTTP/1.1
        - Method
        - Path
        - Version
    - **Header**
        - 메타데이터
        - Content-Type
        - Authorization
    - **Body**
        - 실제 데이터
        - ex) JSON
- **Response 구조**

    ```java
    HTTP/1.1 200 OK
    Content-Type: application/json
    
    {
      "result": "success"
    }
    ```

    - **Status line**
    - **Headers**
    - **Body**

#### 3. Resource 중심

- HTTP는 Resource 접근 관점
    - ex) 유저 → /users/1
    - ex) 게시글 → /posts/100
    - ex) 파일 → /files/abc
- 중요한 건 “행위”보다 “자원”

---

### HTTP Method

- Method는 “무슨 행동인지” 표현함

#### GET: 조회

- GET /users/1
- 유저 조회
- 특징
    - 데이터 조회
    - body 거의 없음
    - 멱등적

#### POST: 생성

- POST /users
- 유저 생성

#### PUT: 전체 수정

- PUT /users/1

#### DELETE: 삭제

- DELETE /users/1

---

### Status Code

- 2xx 성공
    - 200 OK: 성공
    - 201 Created: 생성 성공
- 4xx 클라이언트 오류
    - 400 Bad Request: 잘못된 요청
    - 401 Unauthorized: 인증 안됨
    - 403 Forbidden: 권한 없음
    - 404 Not Found: 없음
- 5xx 서버 오류
    - 500: 서버 내부 오류
    - 503: 서비스 불가

- Resource 중심

### 정리

#### HTTP가 Stateless인 이유?

- HTTP는 각 요청을 독립적으로 처리하는 Stateless 프로토콜
- Stateless 구조의 가장 큰 장점은 확장성(Scalability)
- 서버가 클라이언트 상태를 보관하지 않으면 어떤 요청이 어느 서버로 가더라도 동일하게 처리

Stateless면 로그인 상태는 어떻게 유지?

- Cookie + Session
- JWT
- Redis session store

#### GET과 POST 차이?

- HTTP 메소드이며 주 용도가 다름
- GET은 서버의 리소스를 조회할 때 사용
- POST는 새로운 리소스를 생성하거나 서버에 데이터를 전달해 처리 요청할 때 사용
- 중요한 차이는 멱등성
    - GET은 여러 번 호출해도 서버 상태가 변하지 않으므로 멱등적
    - POST는 호출할 때마다 새로운 데이터가 생성될 수 있어 일반적으로 멱등적
- GET은 보통 Query Parameter, POST는 Request Body

GET body 보내면 안되나?

- HTTP spec상 완전 금지는 아님
- 하지만 대부분 서버/프록시가 기대하지 않음
- 실무에서는 거의 사용 안 함

PUT과 POST 차이는?

- PUT은 보통 전체 교체 + 멱등적

#### 401과 403 차이?

- 401 Unauthorized는 **인증 실패**
    - 서버가 사용자를 식별하지 못한 상태
    - ex)
        - 로그인 안 함
        - JWT 만료
        - 토큰 없음
- 403 Forbidden은 **인가 실패**
    - 사용자가 누구인지는 알지만 해당 리소스에 접근 권한이 없음
    - ex)
        - 일반 유저가 관리자 API 접근
        - 권한 부족

JWT 만료면 401인가 403인가?

- 보통 401
- 유효한 인증이 아니기 때문
