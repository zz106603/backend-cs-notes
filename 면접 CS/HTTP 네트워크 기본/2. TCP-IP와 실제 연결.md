## TCP/IP와 실제 연결

#### 전체 흐름

- 브라우저에서 https://google.com 입력 후 엔터
    1. DNS 조회
    2. IP 획득
    3. TCP 연결
    4. TLS handshake (HTTPS)
    5. HTTP Request 전송
    6. Response 수신
    7. Connection 유지/종료

---

### IP

> **네트워크에서 장치를 식별하는 주소**
>

ex) `142.250.207.14`

- 사람으로 치면 이름 = 도메인, 집 주소 = IP
- google.com → `142.xxx.xxx.xxx`

---

### DNS

> **DNS(Domain Name System)는 도메인을 IP로 변환**
>

ex) google.com → `142.250.x.x`

- 이후 그 IP로 연결 시도

---

### Port

> IP가 “건물 주소”라면 Port는 “호수”
>

ex) 서버 한 대에서 동시에

- 웹 서버
- DB
- Redis

```java
80   -> HTTP
443  -> HTTPS
3306 -> MySQL
5432 -> PostgreSQL
6379 -> Redis
```

---

### TCP

> 안전하게 보내는 프로토콜
>
- HTTP는 보통 TCP 위에서 동작
- 특징
    - 연결 지향(Connection-oriented)
    - 신뢰성 보장
    - 순서 보장
    - 재전송

#### 필요 이유

- 인터넷은 패킷 단위로 쪼개져 전달됨
- ex) 파일 3개 조각
    - Packet1, Packet2, Packet3
    - 문제
        - 중간 손실
        - 순서 뒤바뀜
        - 중복 도착

---

### TCP가 보장하는 것

1. **순서 보장** = 보낸 순서대로 복원

2. **재전송** = 손실 시 다시 전송

3. **흐름 제어** = 너무 빨리 보내지 않음

---

### UDP

> 빠르지만 유실 가능
>
- 특징
    - 비연결
    - 빠름
    - 신뢰성 없음
    - 재전송 없음
- ex)
    - 실시간 스트리밍
    - 게임
    - 음성 통화

---

### TCP vs UDP

| 항목 | TCP | UDP |
| --- | --- | --- |
| 연결 | O | X |
| 신뢰성 | 높음 | 낮음 |
| 순서 보장 | O | X |
| 속도 | 상대적으로 느림 | 빠름 |

---

### 3-Way Handshake

> TCP는 양쪽 통신이 준비되었는지 확인하기 위해 데이터 전송 전에 연결을 만듬
>

#### 1. SYN

- Client: 연결 요청

#### 2. SYN + ACK

- Server: 요청 받고 서버도 준비됨

#### 3. ACK

- Client: 확인 완료

---

### 4-Way Handshake

> 연결 종료
>
- 종료는 송신/수신이 독립적이기 때문에 4번
    - FIN
    - ACK
    - FIN
    - ACK

---

### Keep Alive

> Connection 재사용
>
- 매 요청마다 TCP 연결 생성하면 비쌈
    - handshake 반복
    - latency 증가

---

### 정리

#### TCP와 UDP 차이?

- 둘 다 전송 계층 프로토콜이지만 목적이 다름
- TCP는 연결 지향 프로토콜
    - 데이터 전송 전에 연결을 수립하고 데이터의 순서와 신뢰성을 보장
    - 패킷 손실 시 재전송도 수행
    - 신뢰성이 중요한 HTTP, DB 통신에 주로 사용
- UDP는 비연결형 프로토콜
    - 연결 수립 과정 없이 데이터를 전송
    - 순서 보장이나 재전송 기능이 없음
    - 지연이 더 중요한 실시간 스트리밍이나 게임에 사용됨

HTTP는 TCP 위에서만 동작?

- 기본적으로 그렇지만 QUIC 기반 HTTP/3는 UDP 사용

#### 3-Way handshake인 이유?

- TCP는 양방향 통신이 가능해야 하므로 양쪽의 송수신 가능 상태를 확인해야 함
- 첫 번째 패킷으로 클라이언트가 연결 요청을 보냄
- 두 번째 패킷으로 서버가 요청 수신과 자신의 연결 가능 상태를 알림
- 세 번째 ACK를 통해 클라이언트가 서버 응답을 정상 수신했음을 알려 양측 모두 연결 준비가 완료

#### Port가 필요한 이유?

- IP 주소는 장치를 식별하지만 하나의 서버에서는 여러 애플리케이션이 동시에 실행될 수 있음
- 같은 IP 내에서 어떤 프로세스로 패킷을 전달할지 구분하는 역할
- 예를 들어 하나의 서버에서 웹 서버는 443, PSQL은 5432 포트 사용
