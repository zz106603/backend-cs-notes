## HTTPS / TLS / 인증

### HTTP의 문제점

- HTTP는 기본적으로 평문(Plain Text) 통신

```java
POST /login
id=yun
password=1234
```

- 위 데이터가 암호화되지 않고 네트워크를 흐름
- 중간에서 패킷을 볼 수 있다면 ID, PW 노출 가능
    - 도청
    - 변조
    - 위조

---

### HTTPS

> **HTTP + TLS(SSL)**
>
- HTTP를 암호화 터널 위로 보내는 구조

---

### 암호화 방식

#### 1. 대칭키 암호화

- 암호화와 복호화에 같은 키 사용
- ex) `Key = abc123`
- 장점
    - 빠름
    - CPU 효율 좋음

#### 2. 공개키 암호화

- Public Key → 공개키
- Private Key → 비밀키
- Public Key로 암호화한 데이터는 Private Key로만 복호화 가능
- 장점
    - 키 공유 문제 해결
- 문제는 느림

#### 두 개의 키 사용

- 초기 키 교환 → 공개키
- 실제 통신 → 대칭키

---

### TLS Handshake

ex) 브라우저가 HTTPS 서버 접속

1. Client → HTTPS 연결 원함
2. Server → 인증서 + 공개키 전달
    1. 인증서에 **서버 정보, 공개키, CA 서명** 포함
3. Client → 인증서 검증 성공하면 **대칭키 생성**
4. Client → **서버 공개키로 대칭키 암호화** 후 전달
5. Server → **Private Key로 복호화**

```java
Client               Server
  | ---- hello ------> |
  | <--- cert -------- |
  | -- encrypted key-> |
  | ==== secure ====== |
```

---

### Certificate / CA

- ex) 누군가 가짜 공개키를 보내면 속을 수 있음
    1. Client가 서버 공개키를 요청
    2. 공격자가 네트워크 중간에 끼어들어 가짜 공개키 제공
    3. Client는 가짜 공개키로 대칭키를 암호화해서 전달
    4. 공격자는 비밀키로 대칭키를 복호화
- CA는 신뢰기관
    - Let’s Encrypt
    - DigiCert

#### Certificate (인증서)

- domain: bank.com
- public key: ABC
- CA signature
    - 브라우저는 OS/브라우저 내부에 이미 신뢰하는 CA 목록을 가지고 있음

### 인증(Authentication) vs 인가(Authorization)

#### Authentication - 신원 확인

- 로그인
- 비밀번호
- OAuth

#### Authorization - 권한 확인

- admin 권한
- read only

---

### Cookie

> 브라우저가 저장하는 작은 데이터
>
- HTTP는 Stateless
    - 상태 유지 필요
    - 브라우저 저장소 필요
- ex) `sessionId=abc123`
    - 이후 요청마다 자동 포함
    - `Cookie: sessionId=abc123`

---

### Session

> 서버가 상태 저장
>
- ex) 로그인 성공 시
    - Server → sessionId 생성
    - DB / Memory / Redis 저장
    - Client는 Cookie만 보관
- 구조

    ```java
    Browser cookie
       |
    sessionId
       |
    Server session store
    ```

- 장점
    - 강제 로그아웃 쉬움
    - 서버 통제 쉬움
- 단점
    - 서버 메모리 사용
    - Scale-out 어려움

---

### JWT (Json Web Token)

> 토큰 기반 인증 `header.payload.signature`
>
- payload

    ```java
    {
      "userId": 123,
      "role": "admin"
    }
    ```

- 매 요청
    - `Authorization: Bearer token`
- 장점
    - Stateless
    - 서버가 세션 저장 안 해도 됨
    - Scale-out 쉬움
- 단점
    - 토큰 revoke 어려움
    - 발급 후 만료 전까지 유효

---

### Session vs JWT

| 항목 | Session | JWT |
| --- | --- | --- |
| 상태 저장 | 서버 | 클라이언트 |
| Scale-out | 불리 | 유리 |
| 강제 만료 | 쉬움 | 어려움 |

---

### 실무 예시

`Authorization: Bearer JWT`

- Spring Security Filter가
    1. Header 추출
    2. JWT 검증
    3. Authentication 생성
    4. SecurityContext 저장

### 정리

#### HTTPS는 왜 안전?

- HTTPS는 TLS를 사용해 클라이언트와 서버 간 통신을 암호화함
- 초기 연결 시 공개키 기반 암호화를 통해 안전하게 대칭키를 교환
- 이후 실제 데이터 통신은 성능이 좋은 대칭키 암호화로 수행
- 데이터 도청이나 변조를 방지할 수 있으며, 인증서를 통해 서버 신뢰성도 검증할 수 있음
- **공개키만 쓰면?**
    - 가능하지만 너무 느림

#### Session과 JWT 차이?

- Session은 서버가 사용자 상태를 저장하고 클라이언트는 sessionId만 보관
- JWT는 사용자 정보가 포함된 토큰 자체를 클라이언트가 보관하며 서버는 별도 상태를 저장하지 않음
- Session은 상태 기반, JWT는 Stateless 인증 방식
- **JWT 단점?**
    - 강제 로그아웃 어려움
    - 탈취 시 위험

#### Authentication과 Authorization 차이?

- Authentication은 사용자의 신원을 확인하는 과정 (로그인)
- Authorization은 인증된 사용자가 특정 리소스에 접근할 권한이 있는지 판단하는 과정 (관리자 페이지 접근 여부 판단)
