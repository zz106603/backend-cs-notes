## Concurrency / Race Condition / Lock

### Concurrency (동시성)

> 여러 작업이 동시에 진행되는 것처럼 다뤄지는 환경
>
- ex) Spring 서버
    - 동시에 요청 100개
    - 각 요청이 별도 Thread에서 처리될 수 있음
    - 즉 같은 코드가 동시에 실행됨

#### Parallelism과 차이

- Concurrency
    - 논리적 동시 처리
    - CPU 1개여도 Context Switching 기반으로 가능
- Parallelism
    - 물리적 동시 실행
    - CPU 코어 여러 개로 실제로 동시에 실행

---

### Race Condition

> 실행 순서에 따라 결과가 달라지는 문제
>
- ex) 계좌 잔액을 동시에 2개 처리
    - 차감 = A 요청이나 B 요청 모두 차감
    - 읽기 = 읽기 결과가 잘못됨
- 문제 원인
    - Read
    - Modify
    - Write 연산이 원자적(atomic)이지 않음

---

### Critical Section

> 공유 자원에 접근하는 위험 구간
>
- ex) `balance = balance - 10;`
    - 겉보기엔 한 줄이지만 실제로
        - read
        - calculate
        - write
        - 여러 단계
    - 이 구간 보호 필요

---

### Atomicity

> 더 이상 쪼갤 수 없는 연산
>
- 성공 or 실패
- DB Transaction이 Atomic 보장
- ACID의 A

---

### Lock

> 한 번에 하나만 접근 허용
>
- Race Condition 해결책
- 구조
    - Thread A lock 획득
    - Thread B 대기
    - Thread A 종료 후 unlock
    - Thread B  진행

---

### Mutex (Mutual Exclusion)

- 가장 기본 lock
- 규칙
    - 1 thread only
    - 한 순간 하나만 critical section 진입
- ex)

    ```java
    synchronized void withdraw(){
    	balance -= 10;
    }
    ```

    - JVM에서 monitor lock 사용

---

### Semaphore

- Mutex는 1개 허용
- Semaphore는 N개 허용
- ex) DB Connection pool이 10개면 동시 10개까지 허용

---

### Deadlock

> 서로 lock 해제 기다리며 영원히 대기
>

#### 조건

1. Mutual Exclusion (상호 배제)
    1. 자원을 동시에 여러 명이 못 씀
2. Hold and Wait
    1. 하나 쥔 채 다른걸 기다림
3. No Preemption
    1. 남이 lock을 강제로 뺏을 수 없음
4. Circular Wait
    1. 원형 대기
- 4개 모두 만족 시 발생

---

### Database Lock

- Application lock 만으로는 부족함
- 만약, 서버가 3대면 **각 JVM lock은 공유가 안됨**
- 즉 ditributed environment

---

### Pessimistic Lock

> 비관적 락 = 충돌 날 것 같으니 미리 잠금
>

```java
SELECT * FROM account
FOR UPDATE
```

- 안전하지만, 경합 시 느림

---

### Optimistic Lock

> 낙관적 락 = 충돌 적을 것 같음
>
- Version 사용
- ex) version = 5

    ```java
    WHERE version = 5
    ```

    - 누가 먼저 수정했다면 실패 및 재시도

---

### CAS (Compare And Swap)

> 값이 예상값이면 교체
>
- ex)
    - expected = 10
    - current = 10
    - 같으면 변경, 아니면 실패
    - Lock-free 구조에서 사용
- Java는 `AtomicInteger`

---

### Idempotency

> 여러 번 실행해도 결과 동일
>
- ex) `DELETE /users/1`
    - 한 번 삭제, 100번 삭제 최종 결과 동일

---

### 정리

#### Race Condition?

- 여러 Thread 또는 Process가 동시에 공유 자원에 접근할 때 **실행 순서에 따라 결과가 달라지는 문제**
- 읽기-수정-쓰기 연산이 원자적으로 수행되지 않을 때 발생하며 Lock이나 Atomic 연산으로 해결할 수 있음

#### Mutex와 Semaphore 차이?

- Mutex는 공유 자원에 한 번에 하나의 Thread만 접근하도록 제한하는 상호 배제 메커니즘
    - 1개 허용
- Semaphore는 정수 카운터 기반으로 동작하며 동시에 N개의 Thread가 접근하도록 제한할 수 있음
    - N개 허용

#### Optimistic Lock vs Pessimistic Lock

- Pessimistic Lock
    - 충돌 가능성이 높다고 가정하고 데이터를 읽을 때부터 잠금을 걸어 다른 트랜잭션의 접근을 제한
    - 안전하지만 성능 비용이 큼
- Optimistic Lock
    - 충돌 가능성이 낮다고 보고 잠금 없이 진행하다가 업데이트 시 version 검증 등을 통해 충돌 여부를 확인
    - 성능상 유리하지만 충돌 시 재시도가 필요
