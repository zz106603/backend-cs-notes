# 스레드 풀 포화 정책 (Thread Pool Saturation Policy)

스레드 풀이 더 이상 작업을 처리할 수 없는 **포화 상태**에 이르렀을 때, 새로 들어온 작업을 어떻게 처리할지 결정하는 정책

---

## 1. 스레드 풀은 언제 포화 상태가 되나?

`ThreadPoolExecutor`는 새로운 작업(`Task`)이 들어오면 아래 순서대로 처리함

1.  **Core Pool**: 기본 스레드(`corePoolSize`)에 여유가 있으면, 새 스레드를 만들어 작업을 할당함
2.  **Work Queue**: 기본 스레드가 모두 일하고 있으면, 작업을 큐(`workQueue`)에 쌓음
3.  **Max Pool**: 큐까지 꽉 차면, 최대 스레드(`maximumPoolSize`) 한도 내에서 새 스레드를 추가로 만들어 작업을 처리함
4.  **Saturation (포화)**: 최대 스레드까지 모두 일하고 큐도 꽉 찬 상태. 이때 새로 들어온 작업은 **포화 정책**에 따라 처리됨

---

## 2. 주요 포화 정책 (RejectedExecutionHandler)

### 1) AbortPolicy (기본값)
*   **전략**: "더 이상 처리 못 해! 예외를 던질게."
*   **동작**: `RejectedExecutionException` 예외를 발생시킴
*   **실무 예시**:
    *   가장 일반적인 정책. 예외를 받은 클라이언트(호출부)는 "아, 서버가 지금 매우 바쁘구나"라고 인지하고, 재시도를 하거나 사용자에게 "잠시 후 다시 시도해주세요" 같은 메시지를 보여줄 수 있음
    *   시스템이 감당할 수 없는 요청이 들어오고 있음을 명확히 알리는 신호가 됨

### 2) CallerRunsPolicy
*   **전략**: "스레드 풀이 바쁘니, 작업을 요청한 네(Caller)가 직접 처리해."
*   **동작**: 작업을 스레드 풀에 위임한 스레드(예: 웹 요청을 받은 Tomcat 스레드)가 직접 해당 작업을 실행함
*   **실무 예시**:
    *   비동기로 처리하려던 작업을 동기적으로 처리하게 되므로, 새로운 요청을 받는 스레드의 처리 속도가 자연스럽게 느려짐
    *   이는 스레드 풀에 더 이상 작업이 쌓이지 않도록 하는 **자연스러운 백 프레셔(Back-pressure)** 역할을 함. 무작정 요청을 거부하는 것보다 훨씬 안정적인 서비스 운영이 가능해짐

### 3) DiscardPolicy
*   **전략**: "바쁘니까 새로 온 작업은 그냥 버릴게."
*   **동작**: 새로 들어온 작업을 조용히 무시함. 아무런 예외도 발생하지 않음
*   **실무 예시**:
    *   중요도가 매우 낮은 로그를 남기거나, 없어져도 무방한 통계 데이터를 수집하는 경우에 사용할 수 있음
    *   **데이터 유실**이 발생하므로, 중요한 작업에는 절대 사용하면 안 됨

### 4) DiscardOldestPolicy
*   **전략**: "새 작업을 넣어야 하니, 큐에서 가장 오래된 작업을 버릴게."
*   **동작**: 큐의 맨 앞에 있는(가장 오래된) 작업을 버리고, 새로 들어온 작업을 큐에 넣으려고 시도함
*   **실무 예시**:
    *   실시간성이 중요하여 항상 최신 데이터를 처리해야 하는 경우에 사용될 수 있음 (예: 주식 시세 정보 처리)
    *   `DiscardPolicy`와 마찬가지로 **데이터 유실**이 발생하므로 신중하게 사용해야 함

---

## 3. 어떤 정책을 선택해야 할까?

| 정책 | 특징 | 추천 사용처 |
| :--- | :--- | :--- |
| **AbortPolicy** | 예외 발생, 명시적인 거부 | 일반적인 비즈니스 로직, 실패 처리가 명확해야 할 때 |
| **CallerRunsPolicy** | **안정적인 서비스 운영** (백 프레셔) | 처리 속도가 조금 느려져도 괜찮지만, 요청은 반드시 처리해야 할 때 |
| **DiscardPolicy** | 데이터 유실 감수 | 없어져도 되는 비핵심 데이터 처리 (로그, 통계 등) |
| **DiscardOldestPolicy** | 오래된 데이터 유실 감수 | 최신 데이터를 우선적으로 처리해야 할 때 |

**결론**: 대부분의 안정적인 서비스를 위해서는 **`AbortPolicy`** 로 시스템 한계를 명확히 인지하거나, **`CallerRunsPolicy`** 로 시스템 부하를 조절하는 방식이 권장됨. `Discard` 계열 정책은 데이터 유실의 위험을 반드시 인지하고 사용해야 함
