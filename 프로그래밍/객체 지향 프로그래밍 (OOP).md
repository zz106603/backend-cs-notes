# 객체 지향 프로그래밍 (OOP)

프로그램을 단순히 데이터와 처리 로직으로 나누는 것이 아니라, 

**상태(데이터)와 행위(로직)를 가진 객체(Object)** 들의 유기적인 협력으로 파악하는 프로그래밍 패러다임

---

## 1. OOP의 4대 특징

### 1) 캡슐화 (Encapsulation)
*   **개념**: 객체의 데이터(필드)를 외부에서 직접 접근하지 못하게 숨기고, 메서드를 통해서만 조작하게 하는 것
*   **목적**: 객체의 무결성을 보장하고, 내부 구현 변경이 외부에 영향을 주지 않도록 함
*   **실무 예시**:
    *   **Bad**: `account.balance -= 1000;` (외부에서 잔액을 마음대로 수정)
    *   **Good**: `account.withdraw(1000);` (객체에게 출금을 요청 -> 잔액 부족 체크 로직을 객체 내부에서 수행)

### 2) 상속 (Inheritance)
*   **개념**: 부모 클래스의 기능을 자식 클래스가 물려받아 사용하는 것
*   **목적**: 코드 중복을 제거하고 재사용성을 높임
*   **주의**: 상속은 결합도가 매우 높으므로, 단순히 코드 재사용을 위해서라면 **조합(Composition)** 을 사용하는 것이 더 좋음

### 3) 추상화 (Abstraction)
*   **개념**: 복잡한 시스템에서 불필요한 세부 사항은 숨기고, **중요한 특징(인터페이스)** 만 드러내는 것
*   **실무 예시**:
    *   운전자는 자동차가 내부적으로 엔진을 어떻게 돌리는지 몰라도, `엑셀 밟기()`, `브레이크 밟기()` 인터페이스만 알면 운전할 수 있음
    *   `Car` 인터페이스를 정의하고, `Sonata`, `Avante`가 이를 구현함

### 4) 다형성 (Polymorphism)
*   **개념**: 하나의 객체가 여러 가지 형태를 가질 수 있는 성질
*   **실무 예시 (전략 패턴)**:
    *   `Payment` 인터페이스를 만들고 `pay()` 메서드를 정의함
    *   `CreditCardPayment`, `KakaoPayPayment` 클래스가 이를 구현함
    *   클라이언트 코드는 `Payment payment` 타입으로 받아서 `payment.pay()`만 호출하면, 실제 객체에 따라 카드 결제가 되기도 하고 카카오페이 결제가 되기도 함
    *   **효과**: `NaverPayPayment`가 추가되어도 클라이언트 코드는 수정할 필요가 없음 (OCP 준수)

## 2. 객체 지향 설계 원칙 (SOLID)

좋은 객체 지향 설계를 위해 지켜야 할 5가지 원칙

1.  **SRP (단일 책임 원칙)**: 한 클래스는 하나의 책임만 가져야 한다. (변경의 이유가 하나여야 함)
2.  **OCP (개방-폐쇄 원칙)**: 확장에는 열려 있고, 변경에는 닫혀 있어야 한다. (다형성 활용)
3.  **LSP (리스코프 치환 원칙)**: 자식 클래스는 부모 클래스의 역할을 완벽하게 대체할 수 있어야 한다.
4.  **ISP (인터페이스 분리 원칙)**: 범용 인터페이스 하나보다는 구체적인 여러 개의 인터페이스가 낫다.
5.  **DIP (의존관계 역전 원칙)**: 구체적인 클래스보다 추상화된 인터페이스에 의존해야 한다.

---

## 3. TDA 원칙 (Tell, Don't Ask)

객체 지향의 핵심은 **"데이터를 달라고(Ask) 하지 말고, 작업을 수행하라고(Tell) 시키는 것"** 

### Bad: 데이터를 꺼내서 처리함 (절차 지향적)
```java
// 서비스 계층에서 로직 수행
if (account.getBalance() < amount) {
    throw new Exception("잔액 부족");
}
account.setBalance(account.getBalance() - amount);
```
*   문제점: `Account`는 데이터만 담고 있는 껍데기임. 로직이 서비스 계층에 흩어져 있어 유지보수가 어려움

### Good: 객체에게 시킴 (객체 지향적)
```java
// 서비스 계층
account.withdraw(amount);

// Account 클래스 내부
public void withdraw(long amount) {
    if (this.balance < amount) {
        throw new Exception("잔액 부족");
    }
    this.balance -= amount;
}
```
*   장점: 데이터와 로직이 한곳(`Account`)에 모여 있어 응집도가 높고, 재사용하기 좋음

## 4. 추상 클래스 vs 인터페이스

| 구분 | 추상 클래스 (Abstract Class) | 인터페이스 (Interface) |
| :--- | :--- | :--- |
| **목적** | **기능 확장 및 재사용** (Is-A) | **행위의 강제 및 구현** (Can-Do) |
| **다중 상속** | 불가능 | 가능 |
| **구성 요소** | 일반 메서드, 멤버 변수, 생성자 가능 | 상수, 추상 메서드, default 메서드 |
| **사용 예시** | `Animal` (동물의 공통 기능 상속) | `Flyable` (날 수 있는 기능 구현) |
